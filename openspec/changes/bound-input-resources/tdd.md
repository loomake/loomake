# TDD実行記録

## 1.1 共通reader

探索・バイト境界・合計・型・ハンドル解放・不正な予算の16件を先に追加し、共通APIがない状態の失敗を確認した。実装後に、対象と理由の表示順を整えた。さらに従来の除外対象がリンクである場合の互換性を追加し、1件の失敗を確認した後、除外名をたどらない処理へ直した。

追加後は17件と型検査が成功した。開いた後のサイズ情報が古い場合も実際のバイト数で停止し、読み取りの例外でもファイル記述子が閉じていることを確認した。既存のテストや品質設定は変更していない。

## 1.2 コマンドへの接続

過大な設定・文書・タスク・指示、specsの循環、JSONと証拠の合計、開始前の副作用を確認する12件を先に追加し、現行実装ですべてが失敗した。共通readerへ接続した後は単体17件と合わせて29件が成功した。文書の合計とPR本文のJSONの2件も追加し、既存を含む関連284件が成功した。

verifyは内部の文書を検査してから外部のOpenSpec検証を呼ぶ。trace reportは証拠を逐次検証し、最新だけを保持する。runのロック所有情報も同じバイト上限で読む。ルートがリンクを通る既存テストを維持した。型検査でルートテストのimport先を修正し、lintが指摘した統合後の未使用importを除いた。既存の期待値と品質設定は変更していない。

## 1.3 指示全体の予算

検証の失敗情報はファイルのreaderを通らず指示へ追加されることを確認し、REQ-173とタスクを追加して仕様ゲートを再度通した。指示の上限ちょうど、マルチバイトの対象、検証失敗情報の3件を追加し、修正前は超過の2件が失敗した。

組み立てた指示をエンジンへ渡す前にUTF-8で16MiBまでに制限し、追加後は入力の統合17件と単体17件の計34件、型検査とlintが成功した。

## 2.1 予算と測定

文書とJSON・探索・指示の予算と対象外の資源をdocs/resources.mdに記載し、security・compatibility・architectureの説明を実装と揃えた。以前に受け付けた入力にも制限を追加するため、changesetは対象4パッケージのminorとした。

benchmark.mjsで9条件を独立したプロセスで測定した。小規模・中規模・上限ちょうどは受理し、ファイル・合計・深さ・項目数・JSONの合計・指示全体の超過は拒否した。結果はresults.jsonに保存した。事前の時間とピークRSSの目安を全条件が満たした。時間は入力処理、ピークRSSはモジュールの読み込みとfixture作成も含む値であり、製品のRSSの強制上限ではない。

最終のソースで16MiBの読み取りは14.92ms・ピーク120.21MiB、証拠の合計超過は91.21ms・367.61MiB、指示の超過は23.34ms・136.83MiBだった。このLinux・Node 24ホストの測定であり、CLI全体や別環境での性能を主張しない。
