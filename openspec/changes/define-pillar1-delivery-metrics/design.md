# Design: define-pillar1-delivery-metrics

## Context

動機と範囲はproposalを参照する。設計の正本は専用treeの `.loomake/claude/b8493859-45ae-4fde-8b5e-445c3c5703d8/result.md`。管理役がB案とQ279-00〜07のおすすめを採用し、[公開の採用記録](https://github.com/loomake/loomake/issues/279#issuecomment-6552310806)でREQ-364・365を予約した。

基点を最新mainへ更新したが、定義対象の既存様式・metrics文書・development-decisions仕様と試験・FR-50・CLI/effort周辺・規範に設計時点からの差分はない。意味を選び直さず採用設計を再利用する。文書の値・状態と既存様式の保全にまたがる判断を残すためdesignを置く。

## Goals / Non-Goals

**Goals:**

- 手書きで同じ5項目を記録でき、未取得・非該当・観測中を0と混ぜないようにする。
- 定義表・対応表・記録様式の実物を読む試験で、欄の不足と状態に合わない値を検出する。
- 人の実作業と暦時間、推定比較と人力実測、Loomakeの有無を別々に保つ。

**Non-Goals:**

- CLIの `--effort`・Evidence/schema・効率表の自動生成は#68のまま。FR-50・7.8・REQ-229/230本文は変えない。
- dashboard・metrics-data・既存収集scriptの拡張や実行、私的ログの読取、外の案件の実測は行わない。
- AGENTS・ADR・レビュー規則・既存assert・skip・timeout・品質設定は変えない。

## Decisions

### D1：独立changeを文書と直接試験で完了する

Bを採用する。proposalだけで止めるAでは#279の正常done条件を満たせず、CLIまで実装するCは#68の所有を侵す。既存development-decisionsへのADDED2件に限定し、空specやnoneを使わない。柱4との違いは、より具体的な#279の指示を優先するQ279-00へ記録する。

### D2：5項目の基準を固定する

M1は仕様ゲート初回成功後の最初の実装コミットの親にあるtraceの `(change,Q-ID)` を数え、回答済みも含む。後発の問いは別記する。M2は非0のspec-only停止を同SHA・同失敗項目集合でまとめ、blocking内訳を持つ。現在の未回答数や実行回数へ置き換えない。

M3は最後のPRのmergeから14日間、原因が同じ修理を1件とし、追加要望を分ける。M4は既存の人の5区分の分数と、要件書を読み始めてから最後のPRのmergeまでの暦時間を分けて書く。再openは追記する。M5は実額USD・推計・定額・トークンのみを混ぜず、取得範囲・出典・日付を記録する。日次token数やPR作成からmergeの時間をchange全体の値へ流用しない。

### D3：状態と比較を表で記録する

状態は記録あり・不明・非該当・観測中。記録あり以外は値を空にし、不明/非該当は理由、観測中は終了予定日を必須にする。0は取得された記録ありだけに使う。LoomakeなしのM2は非該当とする。

比較の組・規模・Loomake利用の有無を追加し、既存の比較方式/比較の種類と混ぜない。人力実測がない推定との差はそのまま区別する。M4(a)と人の実績、M5と費用の対応を示し、M1と判断要求、M2と試行は別項目と明記する。

### D4：既存様式を追記だけで保つ

`docs/effort/template.md` の既存全文をprefixとして保持し、新節を末尾へ足す。既存testsの本文・名前・期待値は保ち、新describeに文書表のparserと正例/負例を足す。記録が0件でも捏造せず成功でき、後に柱1節を持つ実記録が増えたら同じ検査をかける。テンプレートの記入例と実記録を分ける。

公開リポジトリへの今回のコード・証跡更新は利用者が明示承認済みであり、非公開前提を理由に再質問しない。計測文書には匿名化した対象名と集計値だけを記録し、セッション本文や自由なログを含めない。外案件の匿名化資料は利用者が用意する。

## Risks / Trade-offs

- [ローカルspec-onlyの履歴が自動保存されない] → 停止表へ手で足し、書き漏れは不明とする。収集機能を足さない。
- [定額と推計を混ぜて費用が歪む] → 区分・単位・取得範囲を分け、同区分だけ合計する。
- [14日が終わる前の0を成功と読む] → 終了日まで観測中とし、期間の異なる記録を同列にしない。
- [様式変更で過去の推定を書き換える] → 追記だけにし、既存REQ-229/230の試験とprefix保全を確認する。

## Migration Plan

仕様ゲート成功後、tasksの順で定義文書・様式追記・追加試験・READMEを実装する。正常local doneの全件試験は1回にまとめ、他担当の重い検証と管理役が調整する。正常CI/必須5チェック/新しい独立レビューを経てmainへ採用してから11月7日以降の記録に使う。実測値はこのchangeへ入れない。

文書と試験だけでpackage変更はなく、changesetは不要。Requirementを追加するため通常L3とし、3 OSと最終CIを管理役が確認する。後から戻す場合も通常changeで扱い、元の推定と過去の記録は書き換えない。
