# Design

## Context
エンジンの終了は中断、出力上限、時間上限、質問、終了コードの順で判定する。HEADやブランチの変更、Git内部の変更を見つけた場合は、その理由を先に書く。中断の状態は保持する。完了ゲートは作業状態の変更を先に確認し、合格、期限、修正回数の上限、再修正の順で選ぶ。これは現在のphases.tsの順序である。

## Decisions
- runner内のrun/decision-policy.tsに、観測値と判定結果の型と純粋関数を置く。戻り値は判別可能なunionとし、続行と停止を区別する。
- エンジン実行、Gitの観測、時計、記録、表示、タスク更新とコミットはphases.tsに残す。既存のHEAD変更を見つけた場合にはGit内部を追加で読まない。
- coreは合意と検証、runnerは自動実装の規則を所有する。実行固有のモデルをcoreへ移さない。
- 公開API、JSON Schema、設定と依存方向を維持する。

## Verification
観測値の重なり、合格と期限の重なり、修正回数の直前・一致・超過を直接試験する。元の入力をfreezeして変更されないことも確認する。規則を逆転したコピーを既存の直接試験へ渡し、assertion失敗を確認する。実際の副作用の順序は既存のrunとguardsの統合試験で確認する。
