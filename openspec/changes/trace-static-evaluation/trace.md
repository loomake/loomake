- token喪失時はhistory・attempts・索引を変更せず、残ったstartedを次の正当な実行者が回収する。ledger.lock取得不能でも受付済み要求を正本に残し、未記録を正常完了にしない。
- receiptは完了した実行の事実だけにする。時間切れ・中断・起動失敗・bail等の未完了にはnullを渡し、部分的なレポートを適格な測定値にしない。正常完了した失敗のテスト結果は実際の失敗件数として保持する。

## 完了通知の前提と実測の限界

- `expose-quality-command-outcomes` はREQ-455・456を所有する独立前提である。管理役がC2の200KiB上限を守るため分割を採用した。main受入・同期archiveの確認までQ70-21を未回答とし、本C2の実装を止める。元の12要件・35 Scenarioを保持し、補足Scenarioを追加しても部分完了としない。
- P1はVitest5.0.5を既存ローカル依存から使い、同じ3ファイル各2試験を通常失敗・bail1・それぞれのshellラッパーで実測した。通常は全6件（成功5/失敗1）、bailはpendingと空ファイルが残り条件Eが不成立だった。両方のラッパーは0を返し、終了0がbailなしの証明にならないと確認した。原本は`.loomake/c2-plan/p1/`へ保持した。
- このfixtureでは条件Eがbailを排除したが、すべてのhidden bailを排除した証明ではない。Jestはローカル未導入でP2未実測。未知producer/未実測版の失敗は未確認とし、正常0も明示的不完全性があれば測定に使わない。正常失敗件数を無条件には捨てず、取得不能を0/1で代用しない。
- 79b4d2aa §3.5手順8〜9の結果だけによる完了推定は4d721b5dと管理役決定で置き換える。4d721b5dの「0ならbailなし」はP1で反例があり不採用。台帳・FIFO・履歴・C3移管の採用済み設計は維持する。
