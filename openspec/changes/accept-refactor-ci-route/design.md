# Design

## Context

動機と範囲は proposal.md にある。先例は spec-fix の経路（archive の `2026-11-05-accept-spec-fix-ci-route`）で、宣言の読み方・評価する段階・失敗の案内の形をそろえる。新しい依存やワークフローの変更は要らない。

## Goals / Non-Goals

条件の判定を `scripts/ci-refactor.mjs` に分け、gate の L3 の拒否分岐から呼ぶ。L1・L2 と change のある L3 の処理は変えない。振る舞いが変わっていないことは機械では判定せず、独立レビューで確かめる。

## Decisions

- **評価する段階**：spec-fix と同じく、L3 で `loomake-change: none` を明示したときだけ評価する。L2 はもともと change なしで進められるので、宣言があっても判定を変えない。
- **経路の選び方**：`loomake-route:` の行のどれかが大文字小文字を区別せず `refactor` なら、リファクタの判定に進む。ほかの値（`spec-fix` や空を含む）が混じれば、食い違いとして理由に示して拒む。`refactor` が一つもなければ、今までどおり spec-fix の判定に進む。こうすると、spec-fix と同時に名乗る宣言はどちらの経路でも通らない。
- **`openspec/` の変更**：spec-fix と同じく、raw diff の変更前と変更後のパスのどちらかが `openspec/` で始まれば拒む。
- **既存のファイルの範囲（許可リスト）**：既存のファイルを変えてよい場所を `packages/<名前>/src/` と `docs/` の下に限り、それ以外の既存のファイルの変更・削除・改名をすべて拒む。最初は「既存のテストファイル」を `tests/`・`packages/*/test/`・`vitest.config.ts` と列挙して拒んでいた。独立レビュー（Claude Opus 5.5、2026-11-20、重大 S-1）で、この列挙の外にも試験を実行から外せるファイルが残ると分かった。例は `scripts/lib/test-partition.mjs`（`vitest.config.ts` が import して exclude に使う）、`package.json` の test スクリプト、`loomake.config.json` の `commands.test`、`scripts/ci-quarantine.mjs`、`eslint.config.js`、`tsconfig*.json`、`.github/workflows/ci.yml`。拒むものを列挙する方式では漏れが残るので、監督役の判断で、認めるものを列挙する方式に変えた。条件を厳しくする方向の変更で、承認された条件 2（既存のテストファイルを変更・削除しない）を含む。
  - 変更（`M`）と種類の変更（`T`）は、パスが `packages/*/src/` か `docs/` の下なら認める。
  - 削除（`D`）は `packages/*/src/` の下だけ認める。リファクタではファイルの分割・統合で削除が起こるため。
  - 名前の変更（`R`）は、変更前のパスが削除してよい範囲（`packages/*/src/`）の下で、変更後のパスが追加してよい範囲の下にあるときだけ認める。`docs/` から外への改名で文書を実質消せるため、変更前は削除と同じ範囲にそろえた（再レビューの情報-1）。gate の差分は `-M` だけで `-C` を使わないので `C` は出ないが、出れば `R` と同じに扱う。
  - 追加（`A`）は `packages/*/src/`・`packages/*/test/`・`tests/`・`docs/`・`.changeset/` の下だけ認める。新しい試験ファイル、`.changeset/*.md`、`docs/worklog/` の記録などが当たる。最初は追加をどこでも認めていたが、再レビュー（Claude Opus 5.5、2026-11-20、軽微-1）で、入れ子の設定ファイル（例：`packages/kit/src/eslint.config.js`）を足すと root の lint の違反が通ると再現されたため絞った。
  - 範囲の中でも、次のパスは変更・削除・改名・追加のどれも拒む。設定ファイルの基本名（`eslint.config.*`・`vitest.config.*`・`vite.config.*`・`vitest.workspace.*`・`tsconfig*.json`・`package.json`・`.npmrc`・`.pnpmfile.cjs`・`.gitattributes`、大文字小文字は区別しない）、`node_modules` という名前の要素を含むパス（`tests/node_modules` そのものも含む。大文字小文字は区別しない）、`docs/guide/3.reference/` の下（大文字小文字は区別しない。`tests/cli-reference.test.ts`・`tests/quality-reference.test.ts` が照合する正本のため。再レビューの軽微-2）。lint や試験の道具を足すときは、その道具が読む設定ファイルの基本名をこの一覧に足すか見直す（3 回目のレビューの情報-2）。
  - 変更後の mode が `120000` のエントリ（シンボリックリンクの追加・改名・複写・種類の変更・変更）は、場所を問わず拒む。`tests/node_modules` という名前のシンボリックリンクを足すと、依存の解決先を差し替えられると再現されたため（3 回目のレビューの軽微 M-1）。
  - 状態が `A`・`M`・`T`・`D`・`R`・`C` のどれでもないエントリ（`X`・`U`・空文字など）は拒む。gate の差分の読み取りはこれらを先に拒むが、判定の側でも安全な側に倒す（情報-4）。
  - 1 本目の PR #469 は、既存の試験に足した試験を新しい試験ファイルへ移し、`AGENTS.md` の変更を外せば、残りは `packages/core/src/` の変更と新しいファイルの追加だけになり、この範囲で通る。
- **大文字小文字だけが違うパス**：追加したパスが、PR の先頭（HEAD）のツリーにある別のパスと大文字小文字だけ違うときは拒む（独立レビューの軽微 M-1）。大文字小文字を区別しないファイルシステムでは、既存のファイルの上書きになるため。判定には `scripts/ci-tier.mjs` の `caseTwins`（REQ-281）を使い、ツリーは gate が読む `git ls-tree -r -z --name-only HEAD` を使う。ツリーを読めなければ、追加か改名があるときは条件を満たさないとして拒み、git の失敗の詳細か、一覧が NUL で終わっていないことを理由に添える（再レビューの情報-3）。
- **独立レビューの証跡**：PR 本文の `## 証跡` の節（`scripts/process-evidence.mjs` の `evidenceSection` で取り出す）に、状態が `実施済み` の `review:` の行が 1 つ以上あることを求める。行の項目の形（`round`・`by`・`session`・`model`・`head`・件数）は、同じ gate の工程行の検査が L2・L3 で調べる。重大の件数がゼロであること、レビュー担当が実装担当と別であること、`head=` がマージする head と一致することは、spec-fix と同じく機械では判定せず、管理役がマージ前に確かめる。
- **失敗の案内**：spec-fix と同じく「L3 では change が必須です」に「リファクタとして受け付けません：」と不足する条件をすべて続ける。成立したときは、品質コマンドの理由に「リファクタ（振る舞いを変えない整理）」と書く。
- **関数の大きさ**：新しく書く関数は本体を 5 行以内にする。gate の本体の分岐は既存のコードで、経路の選択を足すのに必要な行だけを変える。

## Risks / Trade-offs

- テストの追加で振る舞いを固定したかどうか、リファクタが本当に振る舞いを変えていないかは機械では分からない。独立レビューと既存のテスト・3 OS の CI で確かめる。
- 許可の範囲を `packages/*/src/` と `docs/` に絞ったので、試験の補助や設定、スクリプトの小さな修正もリファクタの経路では拒む。必要なら change を持つ通常の L3 で進めるか、別の PR に分ける。
- 試験を弱める変更を、scripts だけを変える L2 の別の PR に分けて先に入れると、この経路の判定をすり抜けられる。PR をまたぐすり抜けは機械では防げないので、独立レビューで確かめる。
- `docs/` の下の変更は認めるので、規則の文書（`docs/dev/` など）の変更も通る。規則の変更が混じっていないかは独立レビューで確かめる。
- 本文の宣言は行単位で読み、Markdown のフェンスを区別しない（spec-fix と同じ）。証跡の節はフェンスの中の行も読む（工程行の検査と同じ）。

## Migration Plan

この change は通常の L3 として受け入れる。main へのマージ後に、リファクタの PR が `loomake-route: refactor` を使える。公開 API と package の配布物は変えない。
