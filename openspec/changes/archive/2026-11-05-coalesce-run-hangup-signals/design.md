## Context

元changeの独立Opus R1（1b6920aa-818e-498f-908d-cec54bf28f52）で挙がった信号の二重配送を実PTYで調べた。npxの単発Ctrl+Cは未再現だったが、端末closeのSIGHUP二重配送で記録とエンジン停止を失う回帰が再現した。元archiveの同期済みREQ-427を対象に追補する。

## Goals / Non-Goals

- 初回SIGHUPから100ms未満の重複だけを初回の中断として終え、その他の強制終了と既存4入力を保持する。
- ほかの初回INT/TERMや異種信号へ時間窓を広げない。送り主の推定、大きな停止機構の変更、既存期待・期限の緩和は行わない。

## Decisions

独立Opus追補設計6b65d074-d5bb-4f6d-aad6-0c272f4f174d（実モデルclaude-opus-5-5）とQ-416-03の利用者承認を採用する。同じイベントループの配送回をまとめる前案はQ-416-02で承認されたが、一時fixtureで12例中10例が失敗し、不適用とした。承認を新しい時間窓へ転用しない。

実測済みのprocess.hrtime.bigintを単調な時計として使い、初回の信号と時刻を保存する。初回HUPかつ追加HUPの差が100_000_000ns未満なら無視し、始点を更新しない。それ以外の2回目は実受信信号の130/143/129で即座に終了する。新しいruntime依存やタイマーは追加しない。

承認済みのsecond-signal-input-change.patchどおり、既存5試験のHUP→HUPだけ2回目をaborted通知後200msにする。期待129、watchdog2000ms、全assertと他4入力は保持し、追加timerはfinallyでclearする。窓内の2配送、100ms境界、期間の非延長を別試験で追加する。型だけ除いたCLI全体とmain fixture、疑似単調時計を使い、Windowsでも同じ製品listenerと実終了コードを検査する。

## Risks / Trade-offs

手動で100ms未満にHUPを2回送った場合も重複扱いになる。窓外へ遅れた重複は強制終了する。通常PTY12例と負荷PTY10例で記録・停止は全成功だが、負荷時の実二重配送は2例で最大2.030042msにすぎず、全OS・shell・負荷の遅延分布は保証しない。Node24で疑似時計の差替えを確認し、製品試験は3 OSのCIで確認する。
