# Design

## Context

base は main `7d7f69b5`。Opus 設計 `76929070-e3be-41fd-829f-bcdfa4ea8d3e` の①を使い、誤読と予算漏れは evaluation.md の訂正を優先する。

## Goals / Non-Goals

Issue の Markdown を既存の要件書処理へ渡す。品質定義・quality.yaml・parser・公開型・認証設定は変更しない。実装は #74 の後とする。

## Decisions

- 配布 Skill と `.agents/skills/req-to-openspec/` を同時追随する。既存の一致試験が両者のずれを検出する。
- Issue は本文だけへ狭めず全コメントを扱う。利用可能な読み取り手段を使い、ページングを含む全件確認ができなければ止まる。取得方法を単一 CLI に固定しない。
- REQ-025/026 は変更しない。Issue の本文・コメントは Markdown で、1 Issue を 1 冊とし、既存の文書名・章と行へ URL・本文/コメント・位置を対応させる。
- 入力文書 3 列と出典の例を両 trace 雛形へ追加する。取得時点の記録を、内容の恒久保存や真正性の保証へ広げない。
- 指定外取得や外部命令は採らず、未取得資料と矛盾は既存 Q に残す。既存 6 分類、通し番号、分割合意と gate 印を維持する。

## Independent review criteria

- REQ-402 の 4 Scenario、403 の 3 Scenario、404 の 2 Scenarioを確認する。構造試験は範囲・停止・矛盾・出典・入力文書・命令区別を個別に検査する。
- verify の既存 fixture で本文/コメント出典それぞれに未回答 1→回答後 0 を観測する。既存 REQ-025〜033/055/059/136・034、旧 assert・期待・skip・期限・設定を変えない。
- A-01 の既承認は引用だけとし新仮定を承認しない。静的指示の成功と AI の実生成・人の案件確認を区別し、#66 の受入へ新しい必須人操作を足さない。

## Risks / Trade-offs

Issue は取得後に更新されるため、出典・取得範囲・取得時点を残す。全件不明の部分入力から完成を報告しない。

## Migration Plan

仕様ゲート後に新試験→両 Skill/雛形/案内→回帰と通常 local done を進める。自身の同期・archiveを実装 PR に同梱し、最終 CI・3 OS・独立レビューで受け入れる。

## Open Questions

本子にブロッキングな未定はない。品質側の既存更新/不在時方針・不足項目の扱いは後続で照合し、本子の決定へ転用しない。

## Scope budget

全計画160行＋同期約50行＋両Skill32行＋雛形2行＋全試験45行＋案内2行＋日誌7行＋changeset3行で301行見込、余裕0。管理役は #66 全体の Issue/品質分割内の本子を採用した。実差分が増えたら早期報告し、試験・文書の圧縮や既存 Markdown 全体へのデータ境界ルール追加で合わせない。
