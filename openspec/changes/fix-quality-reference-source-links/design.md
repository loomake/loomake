# Design

## Context

動機と変更範囲はproposalを参照する。main `f4e3edb7145f35dac49fd139902ab17c5592a5d5` のrendererと生成済みページには生成元として `../../../packages/core/schema/quality.schema.json` と `../../../packages/core/src/quality-schema.ts` がある。GitHubの文書URLを基準にすればmainのソースURLになるが、サイトのURLを基準にすると同じサイトの `/packages/` へ解決される。

既存REQ-322試験には前者の相対URLを含むことを求めるassertionが1つある。T-URL-01の人の承認前はrenderer・生成ページ・試験を編集しない。本designと差分仕様は承認待ちの案であり、URLの採用や試験変更を決定済みにしない。

## Goals / Non-Goals

**Goals:** 同じ2ソースをGitHubとサイトから参照できるようにし、リンクと実ファイルの対応を試験で確認する。

**Non-Goals:** source URLを設定で切り替える機能、siteのルーティング修正、公開、C-001、CLI生成器の変更は含めない。生成表の内容や他の文書リンクを変更しない。

## Decisions

### rendererの2リンクだけをGitHubの完全なURLにする案

共通の前置き `https://github.com/loomake/loomake/blob/main/` と既存の各ソースパスを使う。出力する2 URLは差分仕様のScenarioに示したとおりとし、新しい設定や依存を追加しない。生成ページを手で直さず、rendererを修正して既存コマンドで再生成する。

site内にソースのコピーや専用ルートを増やす方法は、別リポジトリの変更と追加の同期が必要になるため採らない。相対パスをさらに調整する方法も、GitHubとサイトで同じ生成元に解決される条件を満たさない。mainの現行定義を指すことはこの案の一部であり、T-URL-01の採否と切り離して実装しない。

### 既存assertionは承認された1つだけを置き換える

正確な変更前後はproposalのコード例とT-URL-01に対応する。承認後もtitle/description、再生成方法、表、既存ページへの導線、checkの非書込や他の期待値を保持する。

追加試験はrendererの出力と生成済みページの両方から、ラベルquality.schema.jsonとquality-schema.tsに対応するhrefを抽出する。各組が1回だけあり、完全なURLに一致することを確かめる。URLのパスを既知の2ソースパスに対応付け、通常ファイルとして存在することを確認する。古い相対hrefは許さない。

GitHubの文書URLと使い方サイトのページURLをそれぞれbaseにして解決し、同じ期待URLになることも確かめる。単体試験はネットワークやHTTPの可用性に依存させない。既存コードで新しい宛先の試験が失敗することを先に確認し、修正後に同じ試験を成功させる。試験名にはREQ-322を付ける。

### サイトとの照合は固定した入力で行う

管理役が扱う既存siteのローカルbuildで、対象site SHAと修正後のdocs SHAを固定し、描画されたqualityページの2 hrefを照合する。siteコード・公開設定の変更やpushは含めず、公開サイトでの受入と区別する。この修理で#103全体を完了扱いにしない。

## Risks / Trade-offs

- mainへのリンクは現行のソースを指す。参照する2パスの存在と正確なhrefを確認し、パスを変えるときに試験が失敗するようにする。
- 相対URLを要求する既存試験の変更には人の承認が必要である。T-URL-01をブロッキングとして残し、未回答では仕様ゲートを通さない。
- ローカルのURL解決とファイル存在だけでは、公開サイトのHTTP到達を証明しない。固定siteでの描画確認と、公開の受入を別に記録する。

## Migration Plan

T-URL-01の承認を記録して仕様ゲートを通した後に、1 assertionの置換と追加回帰試験、rendererの修正、再生成を順に行う。変更箇所を2リンクに限定し、既存の生成物一致と読み取り専用checkを保持する。問題があれば修正を戻し、品質設定や他の試験期待値を変えて成功扱いにしない。
