# Design

## Context

startRecordingはprompt・出力・verify・PR本文を個別にwriteFileSyncし、finishも同じsaveでsummaryを書く。量の計上と停止用の予約がなく、保存失敗でsummaryまで例外になる。

## Goals / Non-Goals

管理する記録の合計を制限し、停止理由の保存か保存不可の説明を残す。履歴の自動削除、他のプロセスによる変更やエンジンが直接書くファイルをOSで制限することは対象にしない。

## Decisions

- 設定の既定値と予約量、保存の可否はlog-policy.tsの純粋な関数へ分離し、ファイルI/Oはlogs.tsで扱う。
- 履歴は共通readerのentriesを使い、全項目のメタデータと深さを検査する。開始前に予約と新しいディレクトリ・gitignoreの容量を確保できるか調べ、ブランチ切替より前に拒否する。dry-runは書かないためこの確認を省く。
- 作成時に履歴の使用量を読み、管理する書き込みを加算する。64KiBと1項目をsummaryまたはstop用に残す。外部の変更と競合するOSのquotaではない。
- 記録名はファイル名だけに制限し、wxで新規作成する。失敗した自分の部分ファイルは片付けを試み、I/O失敗後のstoreは書き込みを止める。既存のファイルは削除しない。
- finishは通常summaryが大きすぎる場合、別形式のstop.jsonへ短い理由・件数・最後の検証結果と元の操作状態を残す。元の配列を欠落させたsummaryは作らない。
- I/Oエラーで停止情報を保存できない場合は、コンソールへ確認先と保存不可を表示する。すでに行った外部操作や実装を取り消さず、終了コード1にする。

## Risks / Trade-offs

予約は論理的な記録予算で、保存装置の空き容量を事前割当する仕組みではない。実際のディスク不足ではファイルを保存できない場合がある。履歴を整理しても上限まで自動復旧するわけではなく、利用者が保存方針と移動先を判断する。記録は証拠公開と異なり、強制終了時の完全なログを保証しない。
