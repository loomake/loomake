# Design

## Context

Windows で監視役が強制終了すると、監視役が shell で起動した cmd.exe も一緒に終わり、cmd.exe が起動した品質コマンドが親のいない状態で残る（run 40242169987、PR #24 の run 40243055420）。libuv は Windows で detached でない子を job object に入れ、job が閉じると中のプロセスを止める一方、子が起動したプロセスは job から外れるように設定する、という推定で、CI では確かめていない。親が受け取った PID は cmd.exe のものなので、`taskkill /pid <PID> /T` は not found で失敗し、孫に届かない。対象が Node のときは、対象自身の job が閉じて孫も止まるので、process.test.ts の試験は通っている。

レビューの回答（Q-02）で、監視役が結果を書かずに終わったときの後片付けだけを変える方針になった。親の PID と作成時刻の範囲だけでは、対象が終わったあとに同じ PID を取った別のプロセスの子と区別できない（P1、r4384461918）。Q-04 の A（環境変数の印を PEB から読む）は Windows の CI で条件を満たせず、打ち切った（trace の Q-04・Q-05）。この design は Q-05 の B（対象のハンドルを持ち続ける保持役）を書く。B の形は、Q-05 で利用者が B-3 を選んだ（2026-10-27）。

## Decisions

### 識別の考え方

あるプロセスのオブジェクトが残っている間、その PID はほかのプロセスに割り当てられない（Microsoft の PROCESS_INFORMATION の説明）。オブジェクトは、プロセスが動いているか、どこかにハンドルが開いている間は残る。そこで、対象の作成から後片付けまで、対象のオブジェクトを途切れずに残す。後片付けのときに、対象の PID を開いて得た作成時刻が、保持役が受け取った作成時刻 `c_T` と同じなら、対象のオブジェクトは作成から今まで途切れずに残っていた。この間、PID `P` は対象だけのものなので、親の PID が `P` で、作成時刻が `c_T` より後のプロセスは、確かに対象の子である。子孫も同じ考え方でたどる（「深い子孫」）。

他のプロセスのメモリ（PEB・環境変数・コマンド行）は読まない。使う情報は、プロセスのハンドルから読める作成時刻（GetProcessTimes）と親の PID（NtQueryInformationProcess の ProcessBasicInformation の InheritedFromUniqueProcessId。PEB の位置の欄は使わず、その先も読まない）だけである。

### 保持役の形（B-3、Q-05）

保持役は Windows PowerShell 5.1 のスクリプト（`supervisor/windows-holder.ps1`）で、loomake のプロセス（runExternal を呼ぶ Node のプロセス）ごとに 1 つ起動して使い回す。

- 起動：Windows で最初に runExternal を呼んだとき、親が `child_process.spawn` で起動する（detached にしない。stdin はパイプ、stdout・stderr は捨てる、windowsHide）。保持役は、プロセスごとの乱数を含む名前つきパイプ（`\\.\pipe\loomake-holder-<乱数>`）を開き、準備ができたら親が作った作業用のディレクトリに `ready` を書く
- 準備の待ち（Q-06）：親は `ready` を同期で待つ。待つのは loomake のプロセスごとに最初の 1 回だけで、上限は 10 秒とする。待った時間は、操作の期限（REQ-180）にも run の共有予算（REQ-182）にも含めない。そのため、親は待った時間を、期限を計る時計から差し引く（期限そのものは動かさない）
- 待ったあと、親は今までどおり残り時間を計り、残りがなければ監視役も対象も起動せず、時間の上限を示す実行時の失敗（ProcessLimitError の timeout）にする（REQ-180）。監視役も、対象を起動する直前に残り時間を確かめ直す
- 準備の失敗：準備が上限の 10 秒に間に合わないか、保持役が起動できないか途中で終わったときに、残り時間があれば、保護なしで対象を起動する。その実行で監視役が結果を書かずに終わったら、後片付けは何も止めずに「保持役の準備ができていない」を理由とする未確認とする。2 回目以降の操作では待たず、その時点で準備ができていれば使う。準備の失敗に限り、子孫を止める保証が狭まる（利用者が Q-06 で承認）
- 親が先に終わったとき：保持役は stdin の終わり（EOF）で親の終了を知り、すべての保持を解放して終わる
- 保持役が途中で終わったとき：親は次の runExternal で起動し直すが、準備は待たない
- 監視役との関係：保持役は監視役の子ではないので、監視役が終わっても保持を続ける。レビューの条件 2 の「detached で親が終わったあとも保持できること」は、B-3 では「監視役が強制終了したあとも保持を続けること」として確かめる

B-1（対象ごとの保持役を、対象を起動した直後に起動する）と B-2（対象ごとの保持役を、対象を起動する前に準備させる）との違いは、trace の Q-05 に書いた。

### 保持の手順と順序

1. 親は、保持役のパイプの名前と、保持の期限（後述）を監視役の引数に入れる
2. 監視役は、起動したらすぐ保持役のパイプにつなぐ（対象を起動する前）
3. 監視役は、対象を起動する直前に、fd 3 に `{"spawning":true}` を書く。親は、この行があって対象の PID がない結果を「対象を識別する前に監視役が終わった」として未確認にする
4. 監視役は対象を起動し、同じ JavaScript の処理の中で、保持役に `{pid, expiresAt}` を送る
5. 保持役は、PID を `PROCESS_QUERY_LIMITED_INFORMATION | SYNCHRONIZE` で開き、作成時刻 `c` を読んで、ハンドルを持ったまま `{pid, created: c}` を返す。開けなければ理由を返す
6. 監視役は、返事を受け取った時点で対象の `exit` をまだ処理していなければ、保持を確かめたものとし、fd 3 に `{pid, created: c}` を書く。Node は対象の `exit` を JavaScript で処理するまで、CreateProcess で得た対象のハンドルを閉じない（試作の PR #37 で確かめた）。そのため、保持役が開いたときには対象のオブジェクトが残っていて、開いたのは対象そのものである
7. 返事が 1 秒以内に来ない、開けなかった、または先に `exit` を処理していた場合は、`{pid, unprotected: <理由>}` を書く。POSIX では今までどおり、起動の直後に `{pid}` を書く

手順 4〜6 の間に監視役が終わると、保持を確かめられないので、後片付けは未確認になる。この間はパイプの 1 往復（試作で 11〜22ms）で、REQ-254 の「対象を起動してから PID を親へ渡すまで」に入る。

### 保持の解放と期限

- 保持の期限 `expiresAt` は、親が監視役を起動するときに、対象の期限（`startedAt + timeout`）に、監視役の停止の猶予（250ms と 1 秒の待機と出力の書き出しで 2 秒）と、後片付けの上限（10 秒）と、余裕の 5 秒を足して、壁時計の時刻に直したものとする。対象の期限は共有予算の残りまでなので、長い品質コマンドでも途中で切れない。起動から固定の時間では切らない
- 親は、監視役が終わったあと、fd 3 から有効な通常の結果（`status` の行）を読めたら、保持役に解放を頼む。監視役が結果を書いたことだけでは解放しない。親が結果を読めず後片付けを始める場合に、保持がなくならないようにするためである
- 結果を読めないときは、親は保持役に後片付けを頼み、保持役は保持したまま後片付けを行い、終えてから解放する
- 保持役は、期限を過ぎた保持を解放する。親が終わったら（stdin の EOF）すべて解放して終わる
- 期限切れ・保持役の異常終了・パイプの切断で保持が途切れた場合、後片付けの最初の確認（対象の PID を開いて作成時刻が `c_T` と同じか）が失敗するので、何も止めずに未確認とする

親から保持役への頼み（解放と後片付け）は、作業用のディレクトリに頼みのファイルを置き、後片付けでは結果のファイルを待つ（試作の PR #37 で動いた方法）。

### 後片付けの流れ

後片付けは、起動済みの保持役が行う。PowerShell の起動と P/Invoke の宣言は済んでいるので、冷えた条件の起動の時間（A では 4〜7 秒）を使わない。親は頼んでから結果を受け取るまでを 10 秒で打ち切る（REQ-253）。保持役が応答しなければ「保持役が応答しません」として未確認にする。

1. 対象の確認：保持役が持つ対象のハンドルで、作成時刻が `c_T` と同じかを確かめる。保持がない（期限切れ・解放済み・保持役が起動し直した）なら、何も止めずに未確認として終える
2. 探索：`Process.GetProcesses()` で PID の一覧を取り、各プロセスを `PROCESS_QUERY_LIMITED_INFORMATION | PROCESS_TERMINATE | SYNCHRONIZE` で 1 回だけ開く（権限不足なら `PROCESS_QUERY_LIMITED_INFORMATION` だけで開き直す）。ハンドルから作成時刻と親の PID を読む。識別済みの集合（最初は対象だけ）のどれかが親で、作成時刻が親より後のものを子孫とし、ハンドルを持ったまま識別済みに加える。加えたものの子も同じ探索の中でたどる。作成時刻が親と同じ（時計の刻みで前後を決められない）ものは、止めずに未確認とする。子孫でないものはすぐハンドルを閉じる。開けないもの（作成時刻や親の PID を読めないものを含む）は、`NtQuerySystemInformation` の SystemProcessInformation の一覧で、開かずに親の PID と作成時刻を読む。子孫なら、止めずに「開けない子孫」として未確認にし、その子もたどる。一覧を読めなければ、開けないものが子孫かどうかを確かめられないとして未確認にする（Q-08）
3. 停止：識別したものを、識別に使ったのと同じハンドルで TerminateProcess する。すべてのハンドルを取ってから止めるので、止めたことで中間のプロセスの PID が空くことはない。TerminateProcess が失敗しても、同じハンドルの待機で終了を確かめられれば、止まったとして扱う（A-05）。確かめられなければ未確認にする。TERMINATE の権限なしでしか開けなかったものは「権限不足」として未確認にする
4. 探し直し：止めたあとも識別済みのハンドルは持ったままなので、その PID は再利用されない。2 と 3 を繰り返し、新しい子孫が見つからない探索を 1 回終えたら、停止を確認できたとする。その前に期限に達したら、時間切れとして未確認にする（レビューの P2：最後の探索のあとに生まれた子を見落としたまま確認済みにしない）
5. 待機：止めたプロセスの終了を、同じハンドルで期限まで待ち、終わったらハンドルを閉じる

保持役は、プロセスごとに、PID・親の PID・作成時刻・識別の結果（子孫・刻みが同じ・開けない・権限不足）・開いた回数・識別と停止と待機に使ったハンドルの値・停止と待機の結果と、探索の回数と、各手順と合計の時間を返す。どれを未確認とするかは、TypeScript の関数で決める。

### 深い子孫

- たどれる子孫：対象から、後片付けがハンドルを取った時点で残っている中間のプロセス（動いているか、まだオブジェクトが残っているもの）を経てつながる子孫は、各段で作成時刻を確かめたハンドルを持ちながらたどるので、深さによらず止める。cmd.exe → 品質コマンド → さらに子、の 3 段も、cmd.exe が先に終わっていても、品質コマンドが生きていれば止める
- たどれない子孫：中間のプロセス（対象を除く）が、後片付けがそのハンドルを取る前に終わってオブジェクトもなくなると、その子の親の PID はほかのプロセスに再利用されたかもしれないので、帰属を確かめられない。こうした子孫は止めない。親の PID が一覧にないので、見つけたことも分からず、報告もできない。これは REQ-254 がすでに保証外としている「子孫の途中のプロセスが先に終わって親の PID をたどれない孫」と同じ範囲である
- 対象自身は、保持役が持つので、先に終わってもたどれる。A の差分で「親がもういない読めないプロセス」を未確認として報告していたが、B ではそうしたプロセスを見分けられない。これは REQ-254 の保証外の範囲の中の報告の差で、REQ-181・REQ-250・REQ-254 の保証は狭めない
- 新しく狭める範囲：B-3 では、保持を確かめるまでの間はパイプの 1 往復（試作で 11〜22ms）で、REQ-254 の「PID を親へ渡すまで」の範囲に入る。保持役の準備に失敗した実行だけは、子孫を止めず未確認として返す（Q-06 で利用者が承認）

### 報告

後片付けの結果は `{ confirmed, detail }` のままにし、detail に探索・停止・待機と合計の時間と探索の回数を残す。停止を確認できなかったとき（保持役の準備ができていない・保持がない・保持を確かめられない・対象の作成時刻が合わない・保持役が応答しない・開けない・権限不足・刻みが同じ・時間切れ・待機のあとも残っている・対象を識別する前に監視役が終わった）は、中断の理由に「子孫の停止を確認できません：<理由>」を加え、`ProcessLimitError.cleanup` にも結果を入れる。POSIX は今までどおり。

後片付けの結果によらず、`state.interrupted` を立て、同じ共有予算の後続の外部操作を起動しない。後片付けの 10 秒は共有予算から引かず、共有予算の期限も延ばさない。

## Verification

### 試作の結果（PR #37、run 40580870326、windows-latest の 5 job）

試作の holder.mjs は最後に終了コード 0 を返すので、job の成否ではなく、各検証の記録で判断した。

- 前提：監視役のイベントループを止めたまま、終わった対象を保持役が開くと、15 回とも開けた（終了コード 0）。`exit` を処理したあとでは、10 回とも開けなかった（エラー 87）。Node は対象の `exit` を処理するまで対象のハンドルを閉じない、という前提は成り立った
- 保持の継続と子の識別：cmd.exe → 品質コマンド → さらに子、で監視役を強制終了したあと、15 回とも保持役が対象を保ち、2 段をたどって同じハンドルで止め、終了を確かめた。ただし 3 回は、さらに子の TerminateProcess がエラー 5 で、試作の判定は confirmed:false だった。同じハンドルで終了を確かめたものを止まったとする扱いは、この design で決め、製品の試験で確かめる
- 通常の結果のあとの解放：5 回のうち 4 回は、対象がすぐ終わって保持の取得がエラー 87 になり、「保持してから通常の結果を受け取り、解放する」経路を確かめられなかった。製品の試験で、保持の開始を確かめてから正常に終わる場合を確かめる
- 保持の前後に監視役が終わる、保持がない、保持役を強制終了する、親が終わる：どれも保護済みにならないか、保持役が残らなかった。detached で起動した保持役は準備の前に終わった（原因は調べていない。製品では detached を使わない）
- 時間：保持の往復は 11〜22ms、後片付けは親から見て 82〜394ms。冷えた条件の最初の待ちは 3.0〜9.6 秒、温まった条件は 0.44〜0.59 秒

### 製品の試験

- Linux：差し替えた保持役（Unix ドメインソケットで返事をする偽物）で、保持の確認（保護済み・開けない・返事の前に対象が終わる・返事が来ない）、fd 3 の行の読み取り、通常の結果のあとの解放と後片付けのあとの解放の順序、準備の待ちを期限から差し引くこと、準備の失敗で保護なしに起動して未確認を返すこと、予算が尽きていれば準備の失敗でも起動しないことを試験する。後片付けの結果から未確認を決める関数（刻みが同じ・時間切れ・止められず終了も確かめられない・止められなかったが同じハンドルで終了を確かめた）も試験する
- Windows の CI では、ほかの試験と並行して動く通常の試験の中で、非同期の待機で次を確かめる
  - cmd.exe を経た品質コマンドを止める。品質コマンド自身が消え、後続の操作を始めない（`[REQ-183][REQ-250]`、期待は変えない）
  - cmd.exe → 品質コマンド → さらに子を止め、同じハンドルで識別・停止・待機する（開いた回数が 1 回）
  - 保持の開始を確かめてから正常に終わった操作の保持を、結果を受け取ったあとに解放する
  - 保持のない ID の後片付けは、何も止めずに未確認として返す
  - 後片付けの期限を短くすると、時間切れとして停止を確認できないと返す
  - 既存の短い予算の試験（process.test.ts・process-startup.test.ts など）が、期待を変えずに通る
- 冷えた条件を含めて 5 回以上流し、各試験の結果で判断する

## Risks and limits

- 監視役が対象の `exit` を処理するまで対象のハンドルを閉じない、という点は Node と libuv の実装に頼る。試作では成り立ったが、Node の版で変わり得る
- プロセスの作成時刻は時計の刻みで記録されることがあり、親と子の作成時刻が同じになり得る。その子は止めずに未確認とするので、子をすぐ作るコマンドでは未確認が増えるかもしれない。試作の 15 回では起きなかった
- B-3 は、Windows の loomake のプロセスごとに PowerShell が 1 つ常駐し、最初の外部操作が保持役の準備を最大 10 秒待つ（Q-05・Q-06 で利用者が受け入れた）。待ちは期限に含めないが、実時間はその分延びる
- 親の PID と作成時刻の範囲だけの判定（P1）と、環境変数の印（A）は使わない
- C（対象が不在のときの子をすべて未確認とする）は、保持がないときの安全側の扱いにとどめ、解決とはみなさない
