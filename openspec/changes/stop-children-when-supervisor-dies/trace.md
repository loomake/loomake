| A-01 | REQ-250 | 監視役が結果を書かずに終わったときは、kind を `interrupted` にし、理由を `reason` とメッセージに入れる。新しい kind は足さない | 外からの強制終了（Windows の `process.kill(pid, 'SIGINT')`）は、利用者や上位の処理による中断と同じに扱い、後続の操作を止めるのが安全。既存の呼び出し元（verify・run）は kind で分岐しているので、新しい kind を足すと分岐の漏れが起きる。利用者の中断とは `reason` の有無とメッセージで区別できる | | | |
| A-02 | REQ-250, REQ-252 | PID の再利用は扱う（Q-02 の回答で変更）。Windows では、監視役が対象を起動する直前と直後の時刻を作成時刻の範囲として親へ渡す。親はプロセスの一覧の作成時刻と親の PID で対象とその子孫を識別し、止める直前にハンドルを開いて作成時刻を確かめ、ハンドルを持ったまま止める。同一性を確認できないものは止めず、理由を中断の理由に入れる。区別できないまま残るのは、監視役が終わってから親が終了を受け取るまでの間（ふつう数十ミリ秒）に対象の PID を再利用し、子を作って、すでに終わったプロセスの子だけとする。POSIX はプロセスグループへ送るので、グループに生きたメンバーがいる限り再利用されない | 対象の正確な作成時刻を起動時に知るには、Windows では PowerShell などを毎回起動する必要があり、通常の run が遅くなる。起動の直前と直後の時刻で挟めば、通常の run は変えずに、再利用したプロセスと区別できる | | | |
| A-03 | REQ-181, REQ-250 | この change は REQ-181 だけを MODIFIED にし、PR #13 が archive する count-supervisor-startup-budget（REQ-180 を MODIFIED）とは別の Requirement を変える。PR #13 のマージを待たずに進める | Issue #5 コメント 2 では、同じファイルを変えるので PR #13 のマージのあとに始めるとしていた。count-supervisor-startup-budget のコードはすでに main にあり、差分仕様も別の Requirement なので、archive の順番によらず重ならない | | | |
| A-04 | REQ-252 | Windows で作成時刻を比べるときは、時計の刻みの差として 50ms の余裕を見込む | プロセスの作成時刻は OS の時計の刻み（既定 15.6ms）で記録されることがあり、Node の Date.now() と最大で 1 刻みずれる。余裕がないと、対象の子を対象より前に作られたと判断して取りこぼす。50ms の範囲で、前の PID の持ち主が子を作り、終わり、同じ PID が対象に割り当てられる見込みは小さい | | | |
