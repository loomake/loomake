# TDD実行記録

## 3.3 B-3 の保持役が Windows で成り立つか

使い捨ての PR を 2 つ使い、windows-latest で測った。どちらも製品のコードと試験は変えていない。保持役が使うのは、ハンドルから読める作成時刻・親の PID・終了コードと、停止・待機だけで、ほかのプロセスのメモリは読まない。

- PR #37（ブランチ probe/windows-holder、run 40580870326、5 job）：前提（libuv が対象のハンドルを閉じる時期）、保持の確保と継続、子の識別、保持役の終わり方、時間。親は非同期の待機で保持役に頼んだ
- PR #38（ブランチ probe/windows-holder-sync、run 40584691802、6 job）：runExternal と同じ同期の親から使う形。親は保持役の準備を同期で待ち、監視役を spawnSync で起動し、解放と後片付けを、ファイルを置いて結果のファイルを同期で待つ方法で頼む。この間、親のイベントループは動かない

各 job の最初の保持役はその job で最初に起動する PowerShell なので、冷えた条件として扱う。

### 保持の取得と継続

| 項目 | 結果 | 合否 |
|---|---|---|
| 前提：監視役のイベントループを止めたまま対象が終わっても、exit を処理する前なら保持役が開ける（#37 E1b） | 15 回とも開け、終了コード 0 と作成時刻を読めた。exit を処理したあとに開くと、10 回とも開けなかった（エラー 87） | 合格 |
| 保持を確かめる前に対象が終わる場合（#37 E1・E5） | 名前つきパイプへの書き込みは非同期なので、すぐ終わる対象（`exit 0`）では exit の処理が先に来る。監視役は保護済みとせず、`unprotected` を書いた（19 回） | 合格（設計どおり未確認になる） |
| 保持の往復（監視役が PID を送ってから返事を受け取るまで） | #37 は 11〜22ms。#38 は 9〜249ms（S2・S3 の 36 回）。設計の 1 秒の上限に収まる | 合格 |
| 監視役の強制終了のあとの継続（#37 E2） | 15 回とも、cmd.exe が終わったあとも保持役が対象のオブジェクトを保ち、別のプロセスから同じ作成時刻を読めた | 合格 |

### 子の識別

| 項目 | 結果 | 合否 |
|---|---|---|
| cmd.exe → 品質コマンド → さらに子。監視役が保持を確かめたあとに強制終了し、cmd.exe が終わってから後片付けする（#37 E2 の 15 回、#38 S3 の 18 回） | 33 回とも、品質コマンドとその子を識別し、同じハンドル（開いた回数 1、識別・停止・待機のハンドルの値が同じ）で止めて待ち、どちらも消えた。監視役は結果の行を書かずに終わった | 合格 |
| 停止の失敗（エラー 5）で未確認になった回 | #37 で 3 回、#38 で 2 回（各 job の 1 回目）。さらに子の TerminateProcess がエラー 5 で失敗したが、同じハンドルの待機では終了していた。品質コマンドの job object によって、すでに終わりかけていたためと推定する（確かめていない） | 注意（下の所見） |
| 保持がないとき（#37 E3） | 何も止めず、`no-hold` を返した（5 回） | 合格 |
| 保持の前後に監視役が終わったとき（#37 E4） | PID を送る前に終わると保持はない。返事を処理する前に終わると保持は残るが、保護済みとは書かれず、期限で解放された（各 5 回） | 合格 |

#38 の S3 の判定は監視役の `signal` が `SIGKILL` であることも条件にしていたので、18 回とも不合格と出た。Windows では、Node が自分に送った SIGKILL は TerminateProcess になり、spawnSync の `signal` は null になる。監視役が結果の行を書かずに終わったことは記録で確かめた。この条件を除くと、18 回とも上の表のとおりだった。

### 終わり方

| 項目 | 結果 | 合否 |
|---|---|---|
| 通常の結果のあとの解放（#38 S2。対象は 400ms 動く） | 18 回とも、保護済みになり、同期の解放の依頼で保持がなくなり、その後は対象の PID を開けなかった（エラー 87）。解放の依頼は 5〜73ms | 合格 |
| 後片付けのあとの解放（#38 S3） | 18 回とも、後片付けのあとに保持が残らなかった | 合格 |
| 期限切れ（#37 E4） | 期限で保持を解放した（5 回） | 合格 |
| stdin の EOF（#38 S4。生きた対象を保持したまま、親が stdin を閉じる） | 6 回とも、保持を `parent-gone` で解放して終わった。閉じてから保持役が消えるまで 26〜48ms | 合格 |
| 親の通常の終了（#38 S5。保持したまま process.exit） | 6 回とも、親の終了を待ったあと、保持役はもういなかった | 合格 |
| 親の強制終了（#37 E6、detached でない） | 5 回とも、保持役もすぐ消えた（親の job object によると推定） | 合格 |
| 保持役の強制終了（#37 E7） | 依頼に答えず（親は未確認として扱う）、保持役も残らなかった（5 回） | 合格 |
| ほかの保持役が残っていないか（#38 S6） | S4・S5 のあと、job の中の保持役は本体の 1 つだけだった（6 回） | 合格 |

親と監視役の両方がいなくなった場合は、親の終了（通常・強制）で保持役も終わり、親が生きていて監視役だけがいなくなった場合は、期限で保持を解放する。どの終わり方でも、有限の時間で終わり、保持役は残らなかった。detached で起動した保持役は、#37 で 5 回とも準備の前に終わった。原因は調べていない。B-3 では detached を使わない。

### 同期の手段

design.md で試作で決めるとしていた、親から保持役への頼み（解放と後片付け）の受け渡しは、作業用のディレクトリに依頼のファイルを置き（一時ファイルを書いてから名前を変える）、結果のファイルを `Atomics.wait` で待つ方法で、同期の親から使えた（#38）。監視役から保持役への保持の依頼は名前つきパイプで送った。

### 所見

保持役の方式は確かめた範囲で成り立った。3.4 の実装の前に、次の 2 点を決める必要がある。

- 停止の失敗（エラー 5）の扱い：design.md の手順 3 は「TERMINATE の権限がないものは権限不足として未確認」としている。今回のエラー 5 は TERMINATE の権限つきで開けたハンドルで起きており、同じハンドルの待機で終了を確かめられた。「停止に失敗しても、同じハンドルの待機で終了を確かめられれば止まったとする」と design に書くかどうか（trace の仮定 A-05、未承認）
- 最初の待ちの扱い：最初の待ちを REQ-180 のとおり操作の期限に含めると、2〜3 秒の予算で成功を期待する既存の試験が、その worker で最初の外部操作になったときに Windows で時間切れになる見込みが高い（計算による推定で、製品の試験は流していない）。たとえば `packages/kit/test/process.test.ts` の 2000ms・3000ms の予算と、`packages/kit/test/process-startup.test.ts` の 3000ms の予算（trace の Q-06）
