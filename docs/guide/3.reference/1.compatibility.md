## 実行環境

| 対象 | 宣言・CIの対象 | 今回のローカル確認 |
|---|---|---|
| 配布物 | package.jsonのenginesはNode.js 22.12以上 | Linux ARM64のNode.js 24と22.12.0でtarballから主要コマンドを確認 |
| 開発 | Node.js 24、package.jsonのpackageManagerにあるpnpm | 同じ環境で型・lint・テスト・ビルドを確認 |
| OS | GitHub ActionsのLinux・macOS・Windows | 現在のLinuxホストで確認。別OSのCI成功は未確認 |
| Node下限 | Node.js 22.12.0で配布物を確認するCIジョブと、Node20の追加試験 | 公式の22.12.0をチェックサムと照合し、Linux ARM64の通信拒否下で配布物とrunの中断を確認 |
| runのエンジン | claude-code | 代替コマンドで接続を試験。実エンジンの検証とは区別 |
| テストレポート | Vitest・Jest形式のJSON | fixtureと実際のVitestの結果を検査 |

CLIと利用者向けのメッセージ・規約は日本語を対象とする。Nodeの宣言範囲と、各OS・各Node版で実際に試験した範囲は区別する。変更を公開する前に、対象コミットのCIと配布物の結果を確認する。

## 維持する契約

- CLIの終了コードは、合格0、不合格や安全な停止1、使い方・設定の誤り2、実行時の失敗3とする。外部操作の時間・出力の上限や中断による停止は、以前は2だったが、close-cli-gapsで3に変えた。runを始めたあとの停止は、これまでどおり記録を残して1になる。
- verify JSONのschemaVersionは現在`1.0.0`。証拠は1、リリースレポートは2である。利用側は版を確認して読み、未対応の版を黙って解釈しない。
- 文書のスナップショットを含まない旧証拠はreportで読める。現在の仕様との厳密な対応は確認できないため、runの自動再利用では対象外とする。
- 公開するexports、型宣言、JSONスキーマ、CLIのbin、initのテンプレートは、配布したtarballから検査する。開発専用のソース条件を配布物へ残さない。
- 旧形式の完了ゲートタスクも扱うが、新規のタスクでは明示した`<!-- loomake:gate=done -->`を使う。

入力予算の導入により、文書・JSON・探索の上限を超える入力や、specs内のリンクは受け付けない。プロジェクトルートのリンク互換性とJSONの版は維持する。対象と移行時の確認は[resources.md](2.resources.md)を参照する。

証拠の保存は、同じディレクトリに一時ファイルを作り、完全に書いた後にハードリンクで上書きせず公開する。trace recordとrunの証拠保存には、ハードリンクを作れる保存先が必要である。対応しない場合は停止する。保存失敗と強制終了の確認は[run-recovery.md](../2.guides/3.run-recovery.md)を参照する。

実行記録は既定で1回128MiB、履歴全体512MiBまでとする。既存履歴が多い環境では、開始前に止まる場合がある。設定と整理の方法は[resources.md](2.resources.md)を参照する。通常のsummary.jsonの契約は維持する。summaryを予約容量へ保存できない場合に使うstop.jsonは、schemaVersion 1・kind run-stopの別形式であり、summaryとして解釈しない。

Git・gh・エンジンの存在確認・OpenSpec検証には1操作30秒の上限を追加した。以前は終了を待ち続けていた遅い操作も停止する。runでは準備と証拠・PR公開も全体の残り時間に含める。通常の非ゼロ終了とCLI不存在の判定、JSONの版は維持する。期限を指定しない単独verifyの品質コマンドには上限を追加しない。変更の範囲は[resources.md](2.resources.md)、遠隔操作の結果が不明な場合は[run-recovery.md](../2.guides/3.run-recovery.md)を参照する。

doctorは単純なnpm・pnpmのscriptの存在、POSIXの実行権限、導入パスの種類を確認する。以前は合格したscript欠落や非実行ファイルも問題になる。複雑なシェル構文や解決先を確認できないYarnの呼び出しは、未確認の注意として示す。DoctorCheckの形と終了コードを維持する。確認範囲と移行は[doctor.md](../2.guides/2.doctor.md)を参照する。

## 変更を公開する判断

利用者に影響する変更にはchangesetと移行の説明を付ける。現在の0.xでは、破壊的変更はminorの変更として扱い、単にpatchへ含めない。JSONの互換性を壊す場合はschemaVersionの変更と旧形式への対応範囲を明記する。

古い形式を維持する判断にはfixtureを使う。対応を外す場合は、出典・差分仕様・移行手順・テストを同じ変更に含める。すべての古い版を永久に維持する方針ではない。現在はnpm公開前で、修正対象はmainとする。

具体的な検証手順は[testing.md](https://github.com/loomake/loomake/blob/main/docs/testing.md)、報告は[SUPPORT.md](https://github.com/loomake/loomake/blob/main/SUPPORT.md)、公開時の確認は[publishing.md](https://github.com/loomake/loomake/blob/main/docs/publishing.md)を参照する。

## 下限Nodeと通信拒否下の確認

2026-10-24に、Node 24で準備した5パッケージを、公式のNode 20.19.0で実行した。Linux ARM64版のアーカイブを[公式のチェックサム](https://nodejs.org/dist/v20.19.0/SHASUMS256.txt)と照合した。主要コマンド・公開API・証拠の保存とレポートの25行、runのタスクコミットとSIGINT後の変更保持を確認した。

この検証ではLinuxのseccompを子プロセスへ継承し、通信システムコールをEPERMで拒否した。通常のローカル接続がECONNREFUSEDとなる対照と、制限下の接続がEPERMとなる対照を確認している。同じ制限下でtrace recordとreportが成功した。Linuxのネットワーク名前空間を作成する権限はなかったため、この方法を使った。

結果と実行ファイル・検証スクリプト・配布物のハッシュは[検証記録](https://github.com/loomake/loomake/blob/main/openspec/changes/archive/2026-10-24-audit-scenario-evidence/runtime20-results.json)に保存した。手順は[testing.md](https://github.com/loomake/loomake/blob/main/docs/testing.md)に記載した。これはLinux ARM64での実行結果であり、別OSのCI成功や、実際のClaude Code・GitHub接続の成功を示す結果ではない。

## スキーマと公開型の確認範囲

スキーマの版は、現行の検査へ破壊的変更を実際に渡して確認する。1.0.0の履歴に対し、ルート・配列要素の必須プロパティを削除・改名した場合と、minor・majorの変更を与える8ケースを試験した。[結果](https://github.com/loomake/loomake/blob/main/openspec/changes/archive/2026-10-24-audit-scenario-evidence/schema-contract-results.json)に拒否・許可の成否と元ファイルのハッシュを保存した。enumや型の変更を含む、JSON Schema全体の互換性検査は残っている。

公開型は、配布されたd.tsだけで4ライブラリの利用例を厳密にコンパイルした。配布物の型を壊した場合のTS2322と復元後の成功も[記録](https://github.com/loomake/loomake/blob/main/openspec/changes/archive/2026-10-24-audit-scenario-evidence/public-types-results.json)へ残した。利用例は主な型と署名を選んだもので、全公開APIの棚卸しは続ける。ワークスペースでのsource条件と、配布物からsource条件が除かれることも別の試験で確認する。

PR #47でmainを取り込んだ後は、mainのrequire-node-22に従い、配布物の宣言する下限を22.12へ揃えた。上のNode20の測定は過去の実行結果として残す。現在の下限での確認結果は、[PRの統合記録](https://github.com/loomake/loomake/blob/main/openspec/changes/archive/2026-10-24-isolate-run-decisions/merge-results.json)を参照する。

## 判定関数の公開元

WBS v1.4 の J04 に従い、`evaluateAgreement`・`evaluateTestCoverage` と結果型 `AgreementDecision`・`TestCoverageDecision` の公開元を `@loomake/core` から `@loomake/kit` へ移した。利用側は import 元を kit に変える。npm 公開前の変更のため、core での再公開や互換期間は設けない。

`createAgreement` と入力モデル `Agreement`・`RequirementId` は core から引き続き利用する。判定の入力と結果、入力を変更しない契約は変わらない。4値判定や新しい verify JSON は、この移管に含めない。
