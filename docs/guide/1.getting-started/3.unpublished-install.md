---
title: 未公開の Loomake を tarball から導入する
description: 5 パッケージをローカルで pack し、別のプロジェクトで init を実行する
---

`loomake` と `@loomake/*` はまだ npm に公開していない。このページでは、同じ checkout から作った 5 個の tarball を専用ディレクトリに入れ、利用先のプロジェクトから実行する。`npm install -D loomake` の案内は、公開するまでこの手順に置き換える。

配布物の実行には Node.js 22.12 以上が必要。ソースのビルドには開発用の Node.js 24 と、このリポジトリの `packageManager` にある版の pnpm を使う。以下のコマンドは POSIX シェル向けで、Linux・Node.js 24・npm 11 で確認した。Windows のシェル向けの書き換えや devcontainer の起動は、この手順では確認していない。

## 1. 5 個の tarball を作る

Loomake リポジトリのルートで実行する。`LOOMAKE_LOCAL` は、リポジトリと利用先の両方の外にある、まだ存在しない絶対パスに置き換える。同じシェルで次の手順へ進む。

```sh
LOOMAKE_LOCAL=/absolute/path/local-loomake
mkdir -p "$LOOMAKE_LOCAL/tarballs"
pnpm install --frozen-lockfile
pnpm build
for loomake_package in core kit trace runner cli; do
  pnpm --dir "packages/$loomake_package" pack --pack-destination "$LOOMAKE_LOCAL/tarballs"
done
```

`pnpm pack` は `workspace:*` をパッケージの版に置き換える。`npm pack` ではこの workspace 依存が残るため、この手順では使わない。生成されるのは `loomake` と `@loomake/core`・`@loomake/kit`・`@loomake/trace`・`@loomake/runner` の 5 個。pack はローカルのファイルを作る操作で、公開は行わない。

## 2. 未公開の内部依存もローカルから入れる

`$LOOMAKE_LOCAL/package.json` を次の内容で作る。これは利用先の package.json とは別のファイルである。以下は 5 パッケージがすべて `0.0.0` の例なので、手元の tarball の名前に合わせる。

```json
{
  "name": "local-loomake-tool",
  "private": true,
  "devDependencies": {
    "loomake": "file:tarballs/loomake-0.0.0.tgz",
    "@loomake/core": "file:tarballs/loomake-core-0.0.0.tgz",
    "@loomake/kit": "file:tarballs/loomake-kit-0.0.0.tgz",
    "@loomake/trace": "file:tarballs/loomake-trace-0.0.0.tgz",
    "@loomake/runner": "file:tarballs/loomake-runner-0.0.0.tgz"
  },
  "overrides": {
    "@loomake/core": "$@loomake/core",
    "@loomake/kit": "$@loomake/kit",
    "@loomake/trace": "$@loomake/trace",
    "@loomake/runner": "$@loomake/runner"
  }
}
```

`file:` は tarball の場所、`overrides` の `$@loomake/core` などは同じ package.json の直接依存の指定を参照する。これで内部依存も同じローカル配布物へそろえる。

```sh
cd "$LOOMAKE_LOCAL"
npm install --ignore-scripts --no-audit --no-fund
```

外部の実行時依存（zod・yaml）は npm から取得する。既に npm のキャッシュにある場合だけ `--offline` も指定できる。tarballs・package.json・package-lock.json は一緒に保持する。

## 3. 利用先で init を実行する

利用先のプロジェクトのルートへ移って実行する。`--prefix` は上で導入した版を選び、init がファイルを置く場所は現在のディレクトリになる。

```sh
cd /absolute/path/your-project
npx --offline --prefix "$LOOMAKE_LOCAL" loomake --version
npx --offline --prefix "$LOOMAKE_LOCAL" loomake init --codex --devcontainer
```

以後も、このプロジェクトではガイドや Skill の `npx loomake` を `npx --offline --prefix "$LOOMAKE_LOCAL" loomake` に置き換える。init は利用先の package.json を作成・変更しないため、最後に表示される `npm install -D loomake` などの公開パッケージを入れる案内は、この専用ディレクトリへの導入で置き換える。

tarball を npx のパッケージとして指定する構文は `npx -p /absolute/path/loomake-0.0.0.tgz loomake init` である。ただし CLI の tarball だけを渡すと、未公開の `@loomake/*` を npm へ探しに行く。`-p` を付けるだけでは内部依存はそろわないため、上の 5 個を導入した場所から実行する。

package.json がない空のプロジェクトでは、品質コマンドは npm の既定値で残る。init が案内するとおり、`loomake.config.json` の commands を使うコマンドへ書き換えるか、package.json に対応する scripts を用意する。それまでは doctor が問題として示す。OpenSpec の初期化、テストレポート、AGENTS.md の設定は [導入のあとにすること](2.usage.md#導入のあとにすること)へ進む。

## devcontainer が作られなかったとき

`loomake init` は、`--devcontainer` を指定した場合だけ `.devcontainer/devcontainer.json` を置く。省略時に `.devcontainer/` がないのは仕様どおりであり、tarball からの実行でも同じである。Codex 用の Skill を足す `--codex` とは別のオプションなので、`--codex` だけでは devcontainer は置かれない。

必要なら利用先で `npx --offline --prefix "$LOOMAKE_LOCAL" loomake init --devcontainer` を実行する。既存ファイルに差があれば [上書きの確認](2.usage.md#既にファイルがあるとき)がある。

配置されるのは Node.js 24・Claude Code・GitHub CLI・OpenSpec CLI を使うための雛形であり、コンテナの起動は行わない。内容を確認してから、VS Code / Cursor の「コンテナーで再度開く」を使う。Loomake リポジトリ自身の開発用 devcontainer とは別のファイルである。
