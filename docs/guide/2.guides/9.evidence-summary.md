# 検証の要約と本体の参照

`loomake trace record --change <id>` は、Evidence 2 の既存欄に `summaryVersion: 1` の拡張を加えて記録する。検証結果、実際に検証したコミット SHA、保存した仕様文書は従来どおり残る。要約を追加したコミットの SHA へ置き換えない。

## 要約に残す事実

`execution` は実行 ID、評価器の版、基準のハッシュ、Node・OS・アーキテクチャ、検証前後の時刻を持つ。GitHub Actions の実行 ID と試行番号を環境値から確認できた場合は、最上位の `ci` に記録する。試行番号は先頭0のない正の安全整数の十進文字列を保つ。この環境値だけで生成元の真正性を証明したとは扱わない。

コマンド本文と任意のコマンド名は新しい欄に保存しない。`execution.commands` は設定ファイルの raw SHA-256 と出典を持ち、設定省略時は `defaults` とハッシュの `null` を残す。現在の書き手は訪問順を専用に観測していないため、`nameRefs` は `null` と理由を記録する。設定の順序から実行順序を推測しない。

確認できない既知の欄は `null` とし、`gaps` に理由を残す。未確認の件数を 0 で補わない。既存の検証結果や保存文書を含めた全データの秘密情報保護を、この参照欄だけで保証するものではない。

## 本体との照合

`artifacts` はテストレポートの相対パス、加工前の bytes に対する SHA-256 とバイト数を持つ。本体の内容は要約に複製しない。検証時のレポートハッシュと、同じ表現として比較できる記録時のハッシュが異なる場合は、要約を公開せず終了コード 1 を返す。

同じ実行の開始時刻・品質コマンド・レポート構造などを照合できた場合だけ、`sameRun.status` を `verified` とし、観測した 6 種類の件数を残す。この値は全試験の完了、生成元の真正性、品質の合格を保証しない。古い開始時刻、既知の部分出力、不正 UTF-8 などは未確認と理由を残し、元の検証結果を保つ。

現在の `record` は共有保存先へのアップロード・取得を行わない。`availability` は `not-uploaded`、`location`・`expiresAt`・`retrieval` は `null` と理由を残す。同じCIの本体を実取得する運用、リリース記録、失敗試行と既存の大きな記録の整理は [Issue #69](https://github.com/loomake/loomake/issues/69) の後続作業である。

## 取得済みの本体を API で照合する

kit の `checkArtifactBody(ref, bytes)` は、渡した `Uint8Array`（Buffer を含む）の view の範囲だけを、参照のハッシュ・バイト数へ照合する。ファイルの取得や品質判定は行わない。

`artifactRetention(ref, policy, now)` は、参照の `location.createdAt` と `expiresAt` から当時の保持期間を `retention` に、明示した現在時刻から期限の状態を `current` に返す。前者は `satisfied`・`insufficient`・`unverified`、後者は `available`・`expired`・`unverified` である。実際の 7 日と方針の 90 日を混同せず、期限切れでも当時の判定を書き換えない。`available` は期限だけの状態で、取得権限や本体の存在を証明しない。

## 旧形式と公開スキーマ

拡張の目印がない Evidence 1・2 は従来どおり閲覧でき、旧記録は書き換えない。拡張の目印が不正な最新記録は終了コード 2 で止め、古い成功記録へ戻らない。

拡張の構造は core の `loadSummarySchemas()` で遅延ロードし、`@loomake/core/schema/summary/evidence-summary-1.schema.json` からも参照できる。既存の 12 本の JSON Schema と Evidence・Report 自体の形式版は変わらない。


## 固定要約へ本体の索引を追加する

取得済みの本体を参照する記録は、`indexVersion: 1` のreceiptとして別に追加する。固定した要約のbytesは変更しない。receiptは本体・要約のraw SHA-256とバイト数、CI実行・試行、実checkoutとworkflow head、GitHub artifactのlocator、ZIPのdigest、実createdAt/expiresAt、実取得時刻を分けて持つ。本体本文、認証情報、actorのloginやメール、署名付きURLを定義欄へ複製しない。

traceの同期API `bodyReceiptProblem(receipt)` は形式の問題を返す。`appendBodyReceipt(root, receipt)` は、次の場所へ整形JSONを原子的に追加する。

```text
.loomake/evidence/_index/body/<body.sha256>/<UTC秒>-<artifactId>-<entryのSHA-256先頭8桁>.json
```

UTC秒はreceiptの`retrieval.retrievedAt`から作る。同名があれば上書きせず`false`を返し、呼出側は記録なしを終了コード1へ対応させる。入力や保存先の拒否は、入力内容を含まない日本語の`UsageError`になる。共有`maskValue`が値やown keyを変えるreceiptは拒否し、参照のpathやhashをマスクした別の値として保存しない。未知の秘密や個人情報をすべて検出できるとは保証しない。

kitの`checkBodyReceipt(summaryBytes, receipt, bodyBytes?)`は純粋な照合関数である。要約のraw hash/bytes、strict UTF-8のJSONと要約版、実checkout、CIの各識別、一意な本体の参照、ZIPのdigest、渡された場合だけ本体のraw hash/bytesを照合する。ZIPの一致を展開後本体の一致へ読み替えない。本体を渡さなければ、今回本体を取得・照合したことにはならない。

## 保存済みの索引を解決する

`resolveArtifactBody({root, summaryPath, policy, now})`はtraceの同期APIである。`summaryPath`はroot相対の正規POSIXパス、`policy`は`QualityEvidencePolicy`、`now`は実在するUTCのISO日時を明示する。設定ファイルや現在時計を暗黙に読まない。要約と全receiptで128MiB、各file64MiB、探索4096項目・深さ32の予算を共有し、リンクを拒否する。読取例外のあとに残予算を復活させて別候補へ進まない。

結果の`artifacts`は要約の元順序で、各本体の`body`・`status`・`locators`・`paths`・`retention`・`access`・理由を持つ。`locators`は同じrepository・artifactId・entryをまとめる。`paths`は全receiptの正規パスを辞書順で残し、`retention`は同じ順序の`{path, retention, current, retentionReason, currentReason}`の配列になる。異なる期限を1つの保持判定に集約しない。取得時刻などの事実は、各pathから元receiptの値を読む。異なる正規ファイル名に同内容があっても、その名前から新しい取得事実を作らない。

| status | 意味 |
|---|---|
| `resolved` | 固定要約と索引の結び付けが一致した |
| `not-indexed` | 対応する索引がない。0本体の場合も同じ |
| `mismatch` | 要約が不正、または候補と要約の結び付けが違う |
| `invalid-index` | 候補の形式・整合性・安全な読取りを確認できない |

全体のstatusは`invalid-index`、`mismatch`、`not-indexed`、`resolved`の順で優先する。不正な候補や同じlocatorのbody・expiresAt・summaryの矛盾を、正常な別候補で隠さない。`access`は`unverified`のままで、保持期限の`available`と取得権限を分ける。

`resolved`は実取得、生成元の真正性、品質合格を意味しない。receipt内の要約hashを、#71の`checkFixedSummary`に渡す外部の信頼anchorの代わりにしない。限定手動CI、bundle/fetch、同じCI本体の実取得、実保持期間と閲覧権限の運用確認、release/attempts、旧raw整理は親#69の残作業である。既存データ全体の秘密情報保護は#65 P3に残り、この索引追加だけで親Issueの完成とはしない。

receiptの構造は`(await loadSummarySchemas()).bodyReceiptSchema`と`@loomake/core/schema/summary/body-receipt-1.schema.json`で公開する。既存13本のSchema（元12本と要約1本）、旧Evidence1/2の閲覧、同期report/serialize、runnerのsummary1件だけのcommit再利用は維持する。索引だけを追加したcommitは再利用の対象を広げず、通常の再検証へ進む。
