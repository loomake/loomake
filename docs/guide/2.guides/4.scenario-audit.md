title: Scenarioと試験の対応を確認する
description: Scenario と試験の対応を確かめる方法
---

Loomakeのverifyは、RequirementのSourceと、成功したテストの名前にあるREQ-IDの対応を確認する。同じRequirementには複数のScenarioがあるため、各条件と結果をassertしているかは、試験内容を読んで確認する。

## 実行する

リポジトリのルートで、全体の試験を実行してから新しい出力先を指定する。

```sh
pnpm build
pnpm test
node scripts/scenario-audit.mjs .loomake/quality/scenario-audit-new
```

主仕様のScenarioが確認済みか有効な置換だけなら終了コード0、未確認や無効な根拠があれば1になる。入力を読めない場合も1で理由を表示する。既存の出力先を上書きしない。これはリポジトリの品質確認用であり、製品のverifyの合否や設定は変更しない。

監査の対象は主仕様（openspec/specs）のScenarioだけで、コード例の見出しは数えない。archiveしていないchange（`openspec/changes/<id>/specs`）のScenarioは一覧に入れず、changeごとの件数を「未着手」として出す。未着手の件数は終了コードに影響しない。changeのScenarioはarchiveで主仕様へ入ったときに監査の対象になる。archiveの差分仕様は主仕様へ反映済みなので数えない。未着手のScenarioへのレビューを対応表に書いても、未知の参照とは扱わない。

既定の入力は[scenarios.json](https://github.com/loomake/loomake/blob/main/docs/quality/scenarios.json)とloomake.config.jsonのtests.reportである。別の入力を指定する場合は、出力先の後にレビュー表とテストレポートを渡す。

```sh
node scripts/scenario-audit.mjs .loomake/quality/scenario-audit-other docs/quality/scenarios.json .loomake/test-report.json
```

出力はaudit.jsonとaudit.mdで、全件数・状態・仕様の場所・理由・対応試験と、changeごとの未着手の件数を含む。JSONには候補と入力ハッシュも残す。

## CIで確かめる

CIのジョブ `scenario-audit` は、qualityジョブのubuntuが保存した全体試験のレポートで監査を実行する。いまは警告の扱いで、監査が終了コード1でもジョブは失敗しない。結果は `scenario-audit-<run ID>-<試行回数>` という名前のartifactに7日間残る。文書だけのPRでは全体試験のレポートがないため、監査を飛ばす。

[docs/quality/scenario-audit.md](https://github.com/loomake/loomake/blob/main/docs/quality/scenario-audit.md)は、全490件だった時点の出力を残した古い記録である。現在の件数はCIのartifactか、手元で実行した出力で確かめる。

## レビューを記録する

対応表の各IDは、文書・Requirement名・Scenario名で決まる。同名でも別文書や別Requirementなら別IDになる。行の移動だけではIDは変わらない。規則やScenario、規則内のコード例が変われば内容のハッシュが変わり、以前のレビューは無効になる。

未精査の行はunreviewedで残す。候補のREQ-IDが一致するだけでreviewedへ変えない。条件を与える準備と、結果を確かめるassertionを読み、対応を確認できた行だけに次を記録する。

- statusはreviewed、scenarioSha256は現在の内容のハッシュ
- reasonには、どの条件と結果をどのassertionで確かめるかを書く
- sourcesには、そのScenarioで確認するSourceのIDを明示する。Requirementに複数のSourceがある場合は対象を説明する
- testsにはテストファイル・fullNameに含む選択文字列・試験の本文ブロックのハッシュと `"hashScope": "block"` を書く

本文ブロックは選択文字列に一致した試験ごとの `it(`・`test(` の呼び出しで、先頭から対応する閉じ括弧までを指す。`it.each` の引数に直接書いた表、`.skip` などの修飾、型引数も含む。変数に置いた表は含まない。`posixIt` のように、小文字で始まり `It`・`Test` で終わる名前の試験関数も同じに扱う。試験名は最初の引数の文字列リテラルから読み、テンプレート文字列の `${...}` と、`%s`・`$name` などの置換は任意の文字列とみなす。`%s` だけ、`${n}` だけのように、置換と式を除くと固定の文字が残らない試験名のブロックは、どの試験名にも当たるので照合に使わない。同じ名前に一致するブロックが複数あれば、すべてを元の順に連結してハッシュにする。

同じファイルの別の試験を足したり直したりしても、対応は無効にならない。選んだ試験の本文か、`it.each` の引数に直接書いた表が変わると無効になる。試験名がリテラルでない、一致するブロックがない、括弧が閉じていない場合も、本文ブロックを特定できないとして無効になる。

照合の対象は試験ブロックの本文だけである。beforeEach、ヘルパー関数、ファイル先頭の定数、変数に置いた `it.each` の表、vi.mock の変更は検出しない。これらを変えたときは、レビューで該当するScenarioを見直す。

ハッシュを手で計算する必要はない。`hashScope` を書かずにテストファイル全体のsha256を書いてから、下の移行を実行すると、本文ブロックのハッシュに書き換わる。

選択文字列がパラメーター化した複数の試験へ一致する場合、そのすべてが成功している必要がある。失敗・skip・todoを成功した一部で覆い隠さない。試験が実行結果にない、ハッシュが違う、Sourceが違う場合も無効になる。

## 旧形式の対応を移行する

`hashScope` のない対応は旧形式で、従来どおりテストファイル全体のハッシュで照合する。次のコマンドで、旧形式を本文ブロックのハッシュに書き換える。先に全体の試験を実行しておく。

```sh
node scripts/scenario-audit.mjs --migrate --dry-run
node scripts/scenario-audit.mjs --migrate
```

`--dry-run` は対応表を書き換えず、理由ごとの件数だけを出す。レビュー表とテストレポートは、監査と同じく後ろに続けて指定できる。

書き換えるのは、選んだ試験の本文ブロックが記録時から変わっていないと確かめられた対応だけである。現在のテストファイル全体のハッシュが記録と同じなら、そのまま書き換える（`unchangedFile`）。違うときは、gitの履歴から同じパスで記録と同じハッシュの版を探し、その版の本文ブロックが現在と同じなら書き換える（`sameBlock`）。試験を実行していない（`notExecuted`）、ファイルがない（`missingFile`）、本文ブロックを特定できない（`unextractable`）、履歴に版がない（`historyNotFound`）、本文ブロックが変わった（`blockChanged`）ものは旧形式のまま残す。残った対応は試験を読み直して記録し直す。

変更後のScenarioが元のScenarioを置き換える場合は、statusをsupersededにし、理由とreplacementのIDを記録する。同じ一覧にある、確認済みのScenarioまでたどれる必要がある。未知の参照や循環を有効にしない。

## 根拠の範囲

監査は、対応の記録と実行結果の整合性を確認する。reasonが十分な説明か、assertionが振る舞いを十分に確かめるかはレビュー上の判断である。入力のテストレポートが、現在の実装全体を本当に実行して得られたかまでは自動で証明しない。必ず全体の試験を実行し、その範囲と入力ハッシュも保存する。

未確認には、試験が存在するか内容をまだ精査していないものが含まれる。すべてを不具合と断定せず、条件と結果の不足を調べる。Linux上の静的検査を、別OS・実エンジン・実際のGitHub接続の成功の根拠として使わない。

直近の件数はCIのartifactで確かめる。2026-10-24時点の検証は[実行結果](https://github.com/loomake/loomake/blob/main/openspec/changes/archive/2026-10-24-audit-scenario-evidence/results.json)に残っている。独立したコピーで検証した場合は、そのコミットと追加したファイルのハッシュを記録する。後続の変更を、そのコピーの成功結果から合格扱いにしない。未確認が残る間は、全Scenarioの検証や全評価90点の達成とは報告しない。

## 別のNodeで実行した確認を加える

`runtime-compatibility.mjs`は、実際に成功したチェックをreport.jsonのtestResultsへ出す。Node下限とオフラインの確認を通常の全体レポートへ合わせる場合は、両方のtestResultsを残し、元のレポートのハッシュと実行範囲も保存する。通常のVitestの件数と、別環境の4チェックは区別する。失敗・skipを除外したり、同じテスト名の成功だけを採用したりしない。

照合前には、runtimeの結果にあるスクリプト・通信拒否フィルター・配布物のハッシュを確認する。レポートのパスは実行した作業コピーの中を指す必要がある。Nodeの宣言や候補のREQ-IDだけで、別環境での成功を補わない。今回のNode20の根拠は[実行結果](https://github.com/loomake/loomake/blob/main/openspec/changes/archive/2026-10-24-audit-scenario-evidence/runtime20-results.json)に保存した。
