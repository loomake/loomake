# 人の実作業時間を記録する

作業ツリーをコミットしてから、次を実行する。

```sh
loomake trace record --change add-x --effort 90m
loomake trace record --change add-x --effort instruct=30m,review=20m,rework=0m,run=10m,wait=5m,search=8m --decisions 2 --attempts 3 --cost actual-usd:1.25,tokens:12000 --note '再開後の作業'
```

`--effort` は総計、または instruct（指示）・review（レビュー）・rework（手戻り）・run（実行）・wait（待機）の区分を受け付ける。search（判断根拠の探索）は指定した5区分の既知合計の内数で、合計へ再加算しない。searchだけの指定はできない。省略した値は欠測として残し、0で補わない。`review=0m` はレビュー時間を0分と申告した値である。

時間には `m`（分）か `h`（時間）を付ける。`1.5h` は90分、`0.05h` は3分で、各値は0〜100000分の整数へ正確に変換できるものに限る。`0.01h`、先頭ゼロ、空白、符号、指数表記、単位なしは拒否する。`--effort=90m` の構文も使え、同じオプションを繰り返すと最後の値を使う。`--scope` と併用しない。

判断要求と試行は任意の非負の安全な整数で、M1の問いの数やM2のゲート停止から自動で求めない。費用は actual-usd（実額）・estimated-usd（推計）・tokens を区別し、USDは小数最大2桁を整数centsへ、tokensは整数countへ変換する。同じ区分の反復や定額の配賦は受け付けず、異なる区分を合算しない。費用入力だけでM5の単価出典・日付・取得範囲・トークン内訳がそろったことにはならない。

メモはUnicode codepointで500文字以内で、改行と制御文字を含めない。秘密情報や個人情報を入力しない。既知の秘密の形は共有処理で置換するが、任意の秘密や個人情報の検出は保証しない。

記録は `.loomake/evidence/<change-id>/effort/<UTC秒>-<HEAD先頭12文字>.json` へ追記し、以前の内容を変えない。保存したファイルをgitへコミットしてから、追加の時間を記録する。active changeのほか、一意に見つかるarchive済みchangeも指定できる。activeを優先し、不正・不在・あいまいなchangeは拒否する。

終了コードは保存成功が0、未コミットの変更や同じ保存名の衝突が1、保存前の使い方・git・保存の誤りが2である。最終名への保存後に一時ファイルの片付けや結果の表示が失敗したときは3となり、保存済みの相対パスを示す。この場合はもう一度記録せず、示されたファイルを確認してgitへコミットする。これは人の申告値を残す操作で、verify・品質コマンド・検証文書の読取を行わず、品質合格やローカル完了の証拠を作らない。`--effort` を付けない従来のrecordは品質検証を行う。

Issue #68では記録の入口（PR1）に続き、PR2aで入力検査と保存前後の診断をそろえた。手書きの読取と9列の表（PR2b）、品質状況レポートへの接続（PR3）は残っている。C-001の固定見積もり24〜58時間と「未作成」、空の実績を変えず、C-002・C-003の原本は回答待ちのため親Issueを閉じない。経過時間を実作業時間へ転用せず、FR-49の自動推定はW7に残す。

## API入力の移行

coreとtraceの今回のminor更新では、以前受理していた `cost: []` を拒否する。費用が不明な場合は `cost` 自体を省略する。実額0を観測した場合は `cost: [{ kind: 'actual-usd', cents: 0 }]` と明記する。空配列を0や省略と同じ意味には扱わない。CLIの費用の文法は変わらない。

`recordedAt` は秒を含むISO 8601に限る。`2026-11-06T00:00Z` は拒否し、`2026-11-06T00:00:00Z`、小数秒つき、オフセットつきは受け付ける。書込みAPIは引き続き `toISOString()` を使うため、生成する日時の形は変わらない。Effortの `schemaVersion` は1のままで、公開JSON Schema13本も変更しない。

追記専用の保存済み原本は書き換えない。空配列が何を意味したか、分精度の日時の秒が何だったかは原本から確定できないため、費用や日時を推測で補わない。APIの呼出し側で今後の入力を直し、保存済み原本はそのまま保管する。
