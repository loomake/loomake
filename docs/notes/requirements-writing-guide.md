# 要求・要件のまとめ方

最終更新：2026-10-25（v0.1 初版）
関連：`docs/requirements/loomake-v0.11.md`（適用対象）、`docs/architecture.md`

本書は、システムの要求・要件をまとめるときの共通の指針（1 章）と、それを Loomake の要件定義に当てはめた結果（2 章）を分けて書く。2 章の評価は対象版を固定した確認結果であり、要件定義を更新したら評価も版を付けて追記する。

## 1. 共通の指針

要件をまとめるときに効くのは、書式そのものより、何を決めて、何を決めていなくて、どう確かめるかを、あとから読む人がたどれることである。

### 1.1 要求・要件・設計を分ける

「要求」「要件」の使い方は組織で違うので、文書の冒頭で意味を決める。本書では次の区分を使う。

| 区分 | 答える問い |
|---|---|
| 目的・成果 | 何を改善したいか |
| 要求 | 誰が、何を実現したいか |
| 要件 | システムが何を満たす必要があるか |
| 受入基準 | 何を確認すれば満たしたと言えるか |
| 設計・実装方針 | どう実現するか |

要望をそのまま機能一覧にしない。用途と現在の作業まで確認すると、別の解決策が適切な場合がある。実装方法を要件に書くのは、それが本当に制約であるときに限り、理由を添える。

### 1.2 目的と対象外から書く

要件を並べる前に、誰のどんな課題を、どこまで解決するかを書く。個々の要件を採るか捨てるかで迷ったとき、戻る場所になる。対象外も明記する。やらないことを書いておくと、あとから「これも当然入るはず」という形で要求が増えるのを防げる。

成果指標とシステム要件は分けて扱う。「作業時間を半減する」は導入後の業務評価、「一括出力できる」はシステムの検証対象である。

### 1.3 独立して合否を判定できる形にする

1 要件につき、独立して合否を判定できる 1 つの義務か振る舞いを書く。基本形は「誰／何が、どの条件で、何をする／どの状態を満たす」である。前提条件が複数あることや、「および」「または」の使用そのものは問題ではない。複数の義務を 1 つの要件に束ねると、どれが未達か追えなくなる。

性能要件は「p95 で 2 秒以内」のように指標と閾値を定め、対象操作、データ量、同時負荷、測定環境、測定区間を添える。数値は根拠と合意に基づいて決め、書式を埋めるために仮の値を置かない。

### 1.4 要件と受入基準をセットで作る

要件を書いた直後に、どう確かめるかを書く。そこで判定方法が決まらなければ、条件か期待結果が足りていない。正常系だけでなく、0 件、権限なし、失敗、再試行の扱いも受入基準に含める。

検証方法が決まらない要件は、要件一覧から外さず、ID を付けて「検証方法未決」と記録する。保留するのは、その未決事項に依存する実装と合意に限り、独立した作業は進める。

### 1.5 状態と拘束力を分ける

同じ文書の中でも、記述ごとに決まり具合と重みが違う。次の 2 つの軸を独立させる。

| 軸 | 値の例 | 意味 |
|---|---|---|
| 状態 | 草案／レビュー中／合意済み／未決／廃止 | どこまで決まったか |
| 拘束力 | 必須／推奨／裁量 | 守る強さ |

「合意済みだが裁量」「必須だが未決」はどちらもあり得る。見直してよい記述には、見直す条件と手続きを添える。未決は一覧にまとめ、項目ごとに決める人、次の確認方法、時期を書く。

### 1.6 優先度と実装段階を分ける

優先度（Must／Should／Could など）と、どの段階で実装するかは別の項目にする。重要度が高くても、依存関係によって後の段階になる要件はある。全部を一度に作らない前提で、最初に成立させる範囲と、各段階を閉じる条件を書く。

### 1.7 要求から検証結果まで追えるようにする

要求 ID → 要件 ID → 受入基準 ID → 検証方法 → 検証結果、の対応を残す。一対一でなくてよい。目的は、変更時に影響範囲を調べられることと、要求の実現漏れを見つけられることである。検証方法は受入シナリオに限らず、静的検査、設計レビュー、運用訓練も含める。

対応表の基本の列は次のとおり。

| 要件ID | 受入基準ID | 検証方法・参照先 | 優先度 | 実装段階 | 未決事項ID |
|---|---|---|---|---|---|

検証結果は実行ごとに増えるので、この表には入れず、表から参照する別の記録に置く。

### 1.8 ID と用語と変更履歴

要件、受入基準、受入シナリオ、未決事項に ID を振り、振り直さない。削除した番号は欠番にする。文書内で特別な意味で使う語は定義表に置く。版、日付、変更履歴を持ち、合意済みの要件を変えるときは理由、影響、承認者、対象版を残し、過去の検証結果が変更後も有効か確かめる。

### 1.9 小さく始める

小規模なら、目的・背景、スコープ、利用シナリオ、要件一覧、受入・検証、管理情報（優先度、状態、未決、変更履歴）の構成で足りる。着手が近いもの、失敗時の影響が大きいもの、関係者の認識が割れているものから詳しくする。

AI に下書きさせる場合は、AI が補った内容を提案として扱い、合意済みの要件と区別する。要件の正本を 1 つ決め、Issue や実装指示にはその参照を持たせる。

## 2. Loomake への適用

対象：要件定義 v0.7（2026-10-25）とアーキテクチャ v2.1（2026-10-25）を対象に確認した。文書を更新したら、この節に版を付けて追記する。

評価した版の所在：v0.7 と v2.1 はプロジェクト側で書いていた時点の版で、本文はリポジトリにも他の場所にも保存していない。リポジトリにある正本（`docs/requirements/loomake-v0.11.md` v0.11.1、`docs/architecture.md` v2.5.3）は、それ以降の改訂を含む。v0.7 からの改訂の内容は要件定義の末尾の変更履歴に、v2.1 からの改訂はアーキテクチャの冒頭の版の記載にある。この節の評価は最新版で確かめ直していないので、現行の正本と照合するときは、その改訂分を差し引いて読む。

### 2.1 すでに満たしている点

- 方針・提案・未決の区別を要件定義の冒頭で宣言している
- FR・NFR・A・O の ID を使い分け、未決事項に次の確認方法を付けている
- 段階ごとに受入シナリオで出口を置き、変更履歴を残している
- 検証方法が決まらない要件は FR-03 の「ブロッキング確認事項」として要件に紐づけて残す設計になっている
- 検証結果は `.loomake/evidence/` の判定の要約として、要件とは別の記録に置く設計になっている（要件定義 7.9）

### 2.2 追加・整理の案

要求の層：1 章の目的と 2 章の背景と課題がその役割を担っている。2 章の課題に ID を振り、FR に要求元として付けると、要件の採否を判断する根拠が行単位でたどれる。

状態と拘束力：要件定義の「方針・提案・未決」は内容の種類にも読める。1.5 の 2 軸に揃え、状態は「草案／レビュー中／合意済み／未決／廃止」、拘束力は「必須／推奨／裁量」とし、アーキテクチャ 0 章の「必須ルール／現時点の方針」を拘束力の軸に対応づける。「現時点の方針」の再検討条件は付録 A にあるので、見直す手続き（誰が決めるか）を添える。

要件と受入シナリオの対応表：10 章の表は段階から受入シナリオへの対応だけを持ち、FR-01〜47 のそれぞれがどの受入シナリオや検証方法で確かめられるかは文書内にない。アーキテクチャの付録 A の対応表は設計原則からのもので、FR からのものではない。1.7 の列で対応表を足すと、検証方法が決まっていない要件が見えてくる。

優先度と実装段階：要件ごとの優先度と、段階 1〜6 のどこで実装するかを別の列で持つ。

要件と設計の分離：NFR-01 の「実行時の依存は zod と yaml に限る」はシステムが満たす性質というより設計上の制約で、アーキテクチャ 0.1 と同じ内容を 2 か所に持っている。制約として意図的に要件側に置くなら理由を添え、そうでなければ NFR-04 だけを残して依存の数は付録 A に任せる。

性能の例：quality.yaml の `target` には指標と閾値に加え、対象操作、データ量、同時負荷、測定環境、測定区間を持たせる余地がある。`context` と `min_samples` が一部を担っているので、不足分を O04 と合わせて決める。

### 2.3 対応表の雛形

要件定義 10 章の受入シナリオを使って埋める。検証結果は書かず、`.loomake/evidence/` の判定の要約を参照する。

| 要件ID | 受入基準ID | 検証方法・参照先 | 優先度 | 実装段階 | 未決事項ID |
|---|---|---|---|---|---|
| FR-08 | （未定） | 受入シナリオ A03、A04 | Must | 1 | |
| FR-13 | （未定） | 受入シナリオ A07 | Must | 3 | |
| FR-16 | （未定） | 受入シナリオ A05、A06、障害注入 | Must | 3 | O02 |
| FR-29 | （未定） | 受入シナリオ A15 | Must | 1 | |
| FR-44 | （未定） | 設計レビュー、受入シナリオ A17、A19 | Must | 1 | O14、O16 |

受入基準 ID は、FR ごとに受入基準を書き起こした時点で付ける。優先度と実装段階は仮置きで、要件定義の段階計画から写した。
