## 1. 目的

利用時の品質（利用者が明示した利用状況で、目的を正確に、少ない負担で、納得して、許容できるリスクの範囲内で達成できること）を最終目的とし、それを支えるソフトウェア製品品質を、人の作業を最小にして継続的に満たす開発の仕組みを作る。

AIに品質を作らせるのではなく、人が決めた目標を計測可能にし、「作って、測って、直す」一周をAIで速く安くする。生成コード量、タスク完了数、テスト通過数だけを成功指標にしない。

### 1.1 Loomake自身の成功指標

対象製品の品質目標と、Loomake自身の運用指標を分ける。数値目標は試行運用で基準値を測ってから置く。

| 観点 | 指標 | 測定方法 |
|---|---|---|
| 人の負担 | 変更1件あたりの人の作業時間、判断要求数 | `trace record --effort`の記録、`decision`の履歴 |
| 判断根拠を探す時間 | 判断対象を提示されてから、必要な仕様・証跡を見つけるまでの時間。その後の判断・修正の時間とは分けて記録し、人の総作業時間に加算するときは二重に数えない | 最初は手動計測（`--effort`の内訳として記録） |
| 開発効率 | 変更1件あたりの、AIが推定した人力工数の幅に対する、Loomake利用時の人の実作業時間の差（削減率の幅）。これは「推定との差」であり、人力開発との実測比較ではない。推定の精度は人力で実施した比較タスクの実績がある場合だけ評価する | changeの`estimate`（FR-49）と`--effort`の記録（FR-50） |
| 判定の信頼性 | 証跡不足や古い証跡による誤合格件数 | 判定の監査 |
| 継続実行 | 再開の成功率、重複した副作用の件数 | 実行履歴 |
| 成果 | 対象製品の利用時の品質の改善 | 利用者評価、利用計測 |
| 効率 | 採用された変更あたりの実行費用と所要時間 | 実行・費用記録 |
| 回帰 | 公開後の品質悪化、切り戻し件数 | 公開と障害の記録 |

自動化率だけを最大化せず、品質悪化や確認漏れが増えていないかを同時に見る。開発効率は「人力より何倍」を言うための人力実測がないので、AIが推定した人力工数を仮の基準にする。測れるのは「推定した人力工数に対して、人の実作業時間をどれだけ減らせたか」までで、人力開発との実測比較とは区別して表示する。推定と実績の差が推定の誤りか自動化の効果かは、人力実測がない間は判別できない。推定は参考値で、1人の記録なので統計的な優劣は言わない。効率の数字は常に回帰の件数と並べて読む。

## 2. 背景と課題

- AI駆動開発の各段階（仕様駆動、クラウドエージェント、AIレビュー）は既存ツールで揃っているが、「構想や要件からの入口」「仕様を満たしたかの判定」「リリースの根拠の記録」は人手に残っている
- CIのテストだけを完了判定にすると、テストに書いていない受け入れ条件が抜ける。AIは「テストが通る」で止まる
- AIが実装を完了しても、利用者の課題が解決したかを確認しにくい。目的、仕様、品質条件、テスト、実利用の評価が別々に管理される
- テスト未実施、古い結果、基準の緩和が完了報告に紛れ込む
- 品質は仕様に書かれた範囲でしか見られず、保守性やセキュリティのように仕様に現れにくい特性は放置される
- 製品全体の品質が今どうなっているかを、定期的にまとめて見る場所がない
- 1人で自社プロダクトやOSSを作ると、作った理由と確かめた結果が記録に残らず、あとから「なぜこの判断をしたか」を自分でも追えなくなる

## 3. 前提とスコープ

前提
- 開発者は1人。自社プロダクトとOSS（Loomake自身を含む）の開発に使う。目標を決めるのも達成を認めるのも自分。最初は1人・1リポジトリ・1つの主要利用シナリオで一周を成立させる。受託で足す差分は付録B
- 言語はTypeScript/Node.js。仕様の書式はOpenSpecを使い、自作しない（方針。適合性の確認と判断はO17、他のSDDツールへの対応はO18、再検討条件はアーキテクチャ付録A）
- GitHubとGitHub Actionsを使う
- 実装エージェントはClaude Codeを既定とし、アダプター経由でCodex、OpenHandsに切り替えられる
- AIの完了宣言と、検証に基づく判定を分離する（方針）
- 標準機能を優先し、自作が複雑になる部分だけライブラリに任せる（方針。原則はアーキテクチャ0章）

対象
- Issue・構想メモ・Markdownの要件メモから仕様を起こす入口
- 完了判定（verify）と、それが通るまで実装を回す仕組み
- JIS X 25010:2013（ISO/IEC 25010:2011）の品質モデルによる定期評価、品質状況レポート、未達からの改善提案
- 要件・実装・検証・利用結果をつなぐ証跡とリリースレポート

対象外
- 仕様の書式そのもの（OpenSpecに委ねる）
- 実装エージェント本体、AIレビュー本体、計測基盤本体、エディター、Git、テストランナー（借りる）
- 利用者と利用状況の決定、目標値の合意、トレードオフの判断（人が行う）
- 本人の判断なしに目的、品質基準、許容リスクを変えること
- 満足性や実用上の成果を、AIの模擬利用だけで合格にすること
- 複数エージェントの大量並列運転、規格認証の自動取得、収益モデルや公開形態の決定

## 4. 用語

| 用語 | 意味 |
|---|---|
| 利用時の品質 | JIS X 25010の5特性（有効性、効率性、満足性、リスク回避性、利用状況網羅性） |
| 製品品質 | JIS X 25010の8特性・31副特性 |
| 利用時品質目標 | 利用者の目的と利用状況に対して置く目標。quality.yamlの`objectives` |
| 製品品質要件 | 利用時品質目標を支えるために副特性に置く要件。quality.yamlの`product` |
| 合格証拠 | 判定にPASSを与えるために必要な証跡。要件ごとに定義する |
| 参考指標 | 傾向を見るために集計するが、それだけでPASSにしない指標 |
| change | OpenSpecの変更単位（proposal、specs、tasks、trace.md） |
| 受け入れ条件 | 要件ごとの検証可能な条件。品質指標の形で書く |
| verify | changeに対する完了判定コマンド。終了コードで結果を返す |
| 評価ジョブ | 定期に指標と証跡を集め、目標と照らすジョブ |
| 判定 | PASS、FAIL、INSUFFICIENT_EVIDENCE、NOT_APPLICABLE の4値 |
| 証跡 | 判定の根拠。対象コミット、環境、手順、時刻、保存先、ハッシュ、保存期限を持つ |
| 判定の要約 | verifyが本体を確認して生成するJSON。評価対象、実行条件、結果、判定理由、本体への参照を持つ（7.9） |
| 実行記録の本体 | テストレポート、トレース、コマンド出力など、要約が参照する元の記録。Gitには入れない |
| リリース記録 | リリースの判断に採用した要約と承認の記録。承認状態を持つのはこの記録だけ（7.9）。受託ではこれを検収記録として使う（付録B） |
| 評価単位 | 対象コミット、仕様の版、quality.yamlの版、環境、検証方法の組み合わせ。1つでも違えば別の評価 |
| リリースレポート | 特定のchangeまたはリリース時点で、要件IDごとに何を満たしたかを、公開の根拠として利用者と将来の自分に示す文書 |
| 品質状況レポート | 製品全体の品質を定点で見る内部向けの定期文書 |
| 提案 | 未達から起こすproposalの下書き。人がPRをマージした時点でchangeになる |
| 自動実行条件 | 人の承認なしに実装・マージしてよい範囲を決める条件の組み合わせ（7.5） |
| 目的単位のE2E | 利用者の目的（例：月次締めを終える）を1本のシナリオとして最初から最後まで自動操作するテスト。機能単位ではない |

## 5. 全体像

品質の鎖
```
開発プロセスの品質 → 内部品質（コード） → 外部品質（動作） → 利用時の品質
```
AIが直接速くできるのは左の3つで、右端は利用者が使って初めて決まる。目標は右から左へ分解し、証跡は左から右へ集計する。目的と製品品質の関係は多対多で、1つの目的を複数の副特性が支え、同じ副特性が複数の目的を支える。

3つのループ
| ループ | 範囲 | 自動化 |
|---|---|---|
| 内側（実装） | 実装 ↔ verify --done | 完全自動 |
| 中（品質設計） | 製品品質の未達 → 自動change → 実装。コードで解決できなければ目標と条件の対応まで戻る | 自動実行条件を満たす変更のみ自動。回帰の疑いが出たら原因を切り分けてから進む |
| 外側（目的） | 利用時の品質の評価 → 未達 → 原因仮説 → 提案の下書き → 人が採用 | 提案まで自動。要件の変更は人 |

最初の一周
```
目的と品質条件を登録 → verify --spec-only → run（実装） → gate（検証と証跡の確認）
  → 未達で上限内なら run へ戻る → 達成でプレビューと公開判断
  → evaluate（製品品質と利用時の品質、品質状況レポート） → propose（改善案） → 採用で spec-only へ
```

4つのジョブ（GitHub Actions。方針。実行基盤の拡張は11章）
| ジョブ | 起動 | 内容 |
|---|---|---|
| run | changeがmainにマージ、Issueの`loomake:run`ラベル、または`loomake:auto`のIssueが自動実行条件を満たしたとき | verify --spec-only → エージェントに実装させる → ローカル実施項目のverify --done（`scope: local`） → push・Draft PR → CIのverify --doneの結果を取得して修正 → 必須チェック合格でレビュー可能にする |
| gate | PR | CI、verify --done、AIレビュー、自動実行条件の判定（実差分で再判定）。条件を満たせば自動マージ、それ以外は人へ |
| evaluate | 毎晩、デプロイ後。週次で状況レポート | 指標と証跡を集計 → 4値で判定 → quality-report.json → 未達を起票 → 品質状況レポートを出す |
| propose | `loomake:unmet`のIssue | 証跡を添えてproposalの下書きPRを作る |

自動化レベル（製品ごとに設定。MVPはA2まで実装し、初期設定はA1。A1では実装・検証・PR作成まで自動化し、A2を明示的に有効にした場合だけ条件付きの自動マージを許可する）
| レベル | 自動で行うこと | 人が担当すること |
|---|---|---|
| A0 提案 | 仕様案、品質要件案、改善案の生成 | 実行と公開 |
| A1 実装支援 | 実装、検証、修正、PR作成 | 重要な設計判断と公開 |
| A2 条件付き反映 | 自動実行条件を満たす変更の自動マージ | 対象外の変更と公開方針 |
| A3 条件付き公開 | 公開条件に基づく限定公開、監視、定義済みの切り戻し（公開条件そのものはA1・A2でも定義し、人が確認して公開する） | 重大例外と品質水準の変更 |
| A4 継続改善 | 計測から許可範囲の改善実験まで | 目的、優先順位、許容リスク |

## 6. 要件

### 6.1 機能要件

入口（kit）
- FR-01 Issue、構想メモ、Markdownの要件メモからOpenSpecのchange（proposal、specs、tasks、trace.md）を生成する。PDF・docxの要件書は付録B
- FR-02 生成時に、要件ごとの利用者の目的、利用状況（利用者の能力・経験、作業、端末、ネットワーク、環境）、受け入れ条件、計測方法、該当する品質副特性を質問し、答えを要件IDに紐づけて残す
- FR-03 受け入れ条件に落とせない要件は「ブロッキング確認事項」として残し、verify --spec-onlyで止める
- FR-04 共通ルール（CLAUDE.md、AGENTS.md）とSkillsを`npx loomake init`で導入できる。共通ルールの正本を1つにし、他ツール向けには参照か薄い設定を生成する
- FR-05 31副特性をすべて検討対象とし、適用しない項目にはNOT_APPLICABLEの理由と確認者を残す
- FR-49 changeを起こすとき、AIが人力で実装した場合の工数を幅（最小・最大・根拠）で推定し、changeの`estimate`に残す。推定は実装を始める前に固定し、実装後に書き換えない。推定の作業範囲は実績（FR-50）と同じで、実装に加えて指示・レビュー・手直し・判断対応を含める。比較方式（AIなしの人力か、人がAIを操作する方式か）を`estimate.baseline`に記録する

完了判定（kit verify）
- FR-06 `verify --spec-only`：ブロッキング確認事項がゼロであること
- FR-07 `verify --done`：tasksが全て完了、受け入れ条件ごとに合格証拠がある、trace.mdに要件IDと実装・検証の対応がある、ブロッキング確認事項がゼロ
- FR-08 証跡の適格性を確かめる。対象コミットと仕様の版が一致し、必要な検証が実際に実行され、環境・実施日時・結果を確認できること。古いコミットの結果や対象不一致の結果を最新版の合格に流用しない。未評価・証跡不足はPASSにしない
- FR-09 テストを緩める変更（テストファイルの削除、アサーションの減少、skipの増加、基準値の緩和）を検知する。検知したら即失敗にせず、その変更を「基準の緩和」の変更種別として分離し、人が判定する。正当なテスト整理は人の承認で通す
- FR-10 エージェントの自己申告（tests_reported）だけで合格にしない。CIの実行結果と成果物を照合する
- FR-11 結果をJSONで出し、スキーマにversionを持つ。判定は入力から結果を返す通常の関数で実装し、runnerとtraceが同じ関数を使う。後続のgate・eval・trace reportは、verifyが生成した判定の要約を同じ照合関数で確認してから再利用し、リポジトリにあるJSONをそのまま信頼しない。結果には、本体を確認した判定か、要約の整合性だけを確認した再利用かを区別して持つ

実装の実行（runner）
- FR-12 changeのIDを渡すとエージェントが実装し、検証計画のうちローカル実施項目（`required_by: local`）の完了を確認したらDraft PRを作る。CIで実行したverify --doneの結果を取得して修正を繰り返し、CI必須項目（`required_by: ci`）を含む全条件で合格した時点でレビュー可能にする。ローカルとCIは同じ判定関数を使い、ローカルの確認結果は`scope: local`の要約として残すが、最終合格（`verdict`）としては保存しない
- FR-13 修正回数、累積時間、費用見積り、同時実行数の上限を持ち、超えたら「要確認」として原因・試したこと・選択肢を添えて人へ戻す。初期値は修正5回、60分、同時実行1（実案件の計測で見直す暫定値。runner-v0.1のRUN-Q-02）
- FR-14 エージェントをClaude Code、Codex、OpenHandsから設定で切り替えられる。接続の契約は7.4に限定する
- FR-15 devcontainerを実行環境に使い、ネットワークを許可ドメインに絞る
- FR-16 外部イベント（Webhook）に一意のIDを付け、同じPRや公開を二重に作らない。PR作成直後に停止しても、再開時に外部状態を照合して既存PRを使う

PRの判定（gate）
- FR-17 CI（lint、型、テスト）、verify --done、AIレビューを必須チェックにする
- FR-18 自動実行条件（7.5）を、実装前（実装を始めてよい条件）とマージ前（マージしてよい条件）の2段階で判定する。実装前は予定（changeの範囲）で、マージ前は実差分で判定し、予定では条件内でも実差分が条件を外れたら人へ戻す。検証済みコミットとマージするコミットの対応は7.9の再利用条件に従い、マージ直前にgateが再確認する。実差分が許可された証跡ファイルだけの場合は変更種別「証跡の追加」とし、アプリケーションの再検証を省略できるが、要約のスキーマ・生成元・整合性・固定済み記録の改変・参照関係の検査は省略しない
- FR-19 品質基準・評価手順・CIの緩和は、通常の修正とは別の変更種別として扱い、独立して人が判断する。`tests/`と受け入れテストの変更はCODEOWNERSで人の承認を必須にする
- FR-20 確認済みの操作を毎回聞き直さない。確認の範囲・版・有効期限を保持し、内容が変わったら再評価する

評価（trace eval）
- FR-21 quality.yamlの各目標・要件について、合格証拠と参考指標を出どころ（CI成果物、静的解析、依存監査、負荷テスト、E2E、時系列DB、利用者評価の取り込み）から集め、4値で判定する
- FR-22 合格証拠がそろって初めてPASSにする。参考指標の達成だけではPASSにしない。未実施、証跡不足、評価対象の不一致、標本不足はINSUFFICIENT_EVIDENCE
- FR-23 重大な未達を総合点で相殺しない。公開を阻止する条件を個別に持つ
- FR-24 製品品質のPASSから利用時の品質のPASSを推論しない。公開可否、製品品質、利用時の品質の達成状況を別々に表示する
- FR-25 利用時品質目標ごと、製品品質要件ごと、要件IDごとの達成度をquality-report.jsonに出し、履歴（`reports/quality/history.jsonl`）に追記する
- FR-26 未達のうち自動実行条件を満たす見込みの項目は`loomake:auto`、それ以外は`loomake:unmet`のIssueにする。`loomake:auto`は、runの起動前に自動実行条件を予定で判定し、満たさなければ`loomake:unmet`に切り替える
- FR-27 直前のchange以降に別の指標が悪化していたら、まず「回帰の疑い」として記録し、同一条件での再検証か変更前後の比較で原因を切り分ける。原因と確認できたchangeに`regression`を付けて止める。切り分けできない間は自動changeを起こさない
- FR-28 最低サンプル数と比較期間を満たさない指標は判定しない

品質状況レポート（trace report --status）
- FR-29 評価ジョブの結果から、製品全体の品質状況レポートを定期（既定は週次。設定で日次）に生成し、週次は`reports/quality/YYYY-WW.md`、日次は`reports/quality/YYYY-MM-DD.md`としてリポジトリに残す。日次設定でも週次ファイルは生成し、日次ファイルは週次に含めない差分だけを持つ。同じ内容をGitHubのDiscussionまたはIssueに投稿できる
- FR-30 レポートは次の順で構成する。(1) 一行の結論：利用時品質目標と製品品質要件それぞれの達成数、INSUFFICIENT_EVIDENCEの数、公開を阻止する未達の有無。(2) 利用時品質目標ごとの目標値、現在値、前回比、判定、証跡の出どころと標本数。(3) 製品品質の8特性ごとの副特性の判定と参考指標の推移。悪化した指標を先頭に出す。(4) 回帰の疑いと切り分けの状況。(5) 開発効率：changeごとの推定と実績（FR-50）。(6) 未評価の一覧と理由（未計測、標本不足、古い証跡）。(7) 進行中の提案（`loomake:unmet`／`loomake:auto`のIssue、提案PR）。(8) 前回からの変化（マージされたchange、quality.yamlの版）
- FR-31 リリースレポートと品質状況レポートは同じquality-report.jsonと履歴から生成し、見せ方だけを変える。判定を別々に計算しない
- FR-32 レポートに載せる数値は、出どころと取得時刻を添える。推移はhistory.jsonlから描く。時系列の画面は段階1では作らない

提案（propose）
- FR-33 未達の目標・要件と証跡（指標の推移、該当ログ、関連コード）をエージェントに渡し、proposal.mdの下書きを`openspec/changes/`へのPRとして作る
- FR-34 1回の評価で起こす提案は層ごとに1つまで
- FR-35 1目標あたりの自動change回数と1日のrun回数に上限を持つ
- FR-36 比較実験では、主指標、悪化を防ぐ指標、観測期間、判断方法を事前に決める。結果が有利なときだけ観測を打ち切らない

証跡（trace）
- FR-37 trace.md、verifyの結果、QAの実行証跡（コマンド出力、スクリーンショット）、評価結果を突き合わせ、要件IDごとのリリースレポートを出す。リリースレポートはリリース記録（7.9）を読み、採用した要約の識別子・ハッシュ、承認者、判断日時、対象範囲、承認状態を示す。複数changeをまとめてリリースするときは、リリース版のコミットに対して採用した各要約が適用できるかを7.9の再利用条件で照合し、満たさない要約はリリース版で再検証する。初期実装はリリース版で必要な検証を一括で再実行する方式でよく、影響範囲を解析して部分的に再利用する仕組みは後回しにする
- FR-38 リリースレポートに、利用時の品質の目標と計測方法を「このリリースで追う指標」として含める。リリースの対象外とした目標も、達成状況は「未評価」または判定結果として示し、達成済みとは表示しない。保存期限切れなどで証跡を再確認できなくなっても過去のリリース判断は書き換えず、「当時の判断」と「現在の再確認可否」を分けて示す
- FR-39 利用時の品質の証跡には、対象者、利用状況、観測期間、公開版、標本数、収集方法を持たせる。個人の評価回答を必要以上に複製しない

証跡の保管（7.9）
- FR-44 検証の記録を「判定の要約」「実行記録の本体」「リリース記録」に分け、保存先と保持条件を7.9に従って定める。本体はGitに入れず、Gitに残すのは小さな構造化記録とテストに必要な固定fixtureに限る。実行のたびに増える記録を`openspec/changes/<change>/`に置かない
- FR-45 評価条件は対象コミット・仕様の版・quality.yamlの版・環境・検証方法の組み合わせとし、評価要求（要求ID、起動元、要求時刻）、評価の実施（実行ID、試行番号、実施日時）、観測データ（観測期間、取得時刻、対象の公開版、必要ならデータの識別子）とは分けて識別する。同じ実行ID・試行番号の二重取り込みだけを排除し、異なる試行の結果はすべて記録に残す（FR-47）。評価条件と観測期間の組ごとの代表結果は索引で選び、履歴を消して選ばない。同一期間でもデータが更新されうるので、取得時刻とデータの識別子も残す。最新結果への索引は更新してよいが、リリースに採用した要約とリリース記録は固定し、訂正・再評価・用途の変更は元の記録を参照する別の記録として追加する
- FR-46 リリースの判断に採用する実行記録の本体は、リリースレポートを承認可能にする前に長期保管先へ保存し、想定する閲覧者の権限で取得できることとSHA-256の一致を確認して、保存先・保存期間・確認日時をリリース記録に残す。例外承認の根拠となった失敗結果も対象にする
- FR-47 失敗した試行は、試行ID・評価対象の識別子・結果・失敗理由の分類・要約への参照を`attempts.jsonl`に1行ずつ追記する。最後の成功で未解決の失敗を隠さず、過去に失敗があったことだけを理由に修正後の合格を妨げない
- FR-48 evaluateは起動時に評価要求（要求ID、対象コミット、基準の版、要求時刻、起動元）を受付済みとして記録し、実行中・評価済み・再評価待ち・取消・回収不能のいずれかに状態を更新する。実行開始前に取り消された要求は起動時の記録では拾えないので、次回のevaluateが、前回に照合と記録の保存まで成功した位置から現在までのActions実行一覧と保存済みの要求を照合し、未記録の取消実行も要求として取り込む。照合は最低7日分を重ねて行い、照合完了位置は記録の保存に成功したあとで更新する。実行一覧を全件取得できなかった場合は完了位置を進めない。要求IDはActionsの実行IDと試行番号で、二重取り込みの排除はこのIDで行う。取り消された要求は再評価するが、再評価の結果を元の時刻の結果として記録しない。当時の指標や環境が失われていて再評価できない要求は回収不能として残す

利用時の品質の評価
- FR-40 受け入れ条件から目的単位のE2Eテストを生成し、verify --doneの検証に含める。合否に加えて手数と所要時間をtrace.mdに記録する
- FR-41 E2Eのシナリオに利用状況の組み合わせ（端末、権限、データ量、ネットワーク条件）をパラメータとして持たせる
- FR-42 本番計測がある場合はそれを正とし、E2Eの値との差を利用時の品質の指標として評価ジョブで追う。差が大きい目的から提案を起こす
- FR-50 changeを閉じるとき、人の作業時間（Loomakeへの指示、質問への回答、レビュー、手直し、判断対応）を`loomake trace record --effort <時間> --change <id>`で記録する。再オープン後の追加作業は同じコマンドで追記し、合計と内訳を残す。品質状況レポートに、changeごとの比較方式、推定の幅、Loomake利用時の人の実績、推定に対する削減率の幅、比較の種類（推定との比較・人力実測なし／人力実測あり）、判断要求数、試行回数、実行費用を並べた効率の表を載せる（7.8）。効率の表は回帰の疑いの節の後に置き、単独で読ませない。人力で実施した比較タスクの実績があるときだけ「人力実測との比較」として別の行に出し、推定との差と混ぜない
- FR-43 本番計測がない場合も、利用者によるタスク実施の観察、所要時間の測定、アンケート、業務記録、OSSではGitHubのIssue・Discussionの具体的な利用報告を証跡として取り込み（`loomake trace record --observation`）、利用時の品質を評価する。ダウンロード数・ドキュメントの参照数・Issue件数は原則として参考指標で、それだけでPASSにしない。利用者が少ない場合は統計的な優劣を断定せず、タスク観察と定性評価を併用する

### 6.2 非機能要件

- NFR-01 実行時の依存は`@loomake/core`の`zod`と`@loomake/kit`の`yaml`に限る。増やすときは、標準機能で足りないこと、自作よりコードと保守が減ること、実行経路に必要なことを文書に書く
- NFR-02 契約（trace.mdの書式、verify JSON、quality-report JSON、quality.yaml）はZodスキーマで定義し、型を導出し、重複定義しない。スキーマにversionを持ち、後方互換の方針を文書化する。外部ツール向けにJSON Schemaを書き出す。品質モデルの識別子と版を保存し、現行版（ISO/IEC 25010:2023）への対応は別プロファイルとして追加して判定履歴を上書きしない
- NFR-03 エージェントの実行環境に本番の資格情報を渡さない。計測は読み取り専用APIで取る。開発、検証、公開の権限を分離する
- NFR-04 一人で保守できる規模に保つ。自作はCLIとActionsの定義に限り、エージェント、レビュー、計測基盤は借りる。クラス階層、DIコンテナ、汎用プラグイン基盤は具体的な必要が出るまで入れない
- NFR-05 Loomake自身の開発にLoomakeを使う（openspec/で自分の仕様を管理する）
- NFR-06 E2Eは目的単位に絞る。31副特性の検証をE2Eに寄せず、テストの保守がループの最大コストにならないようにする
- NFR-07 証跡と基準の内容変更をハッシュと版で検出できる。誰が何を判断・実行したかを追跡できる
- NFR-08 プロセス再起動後に保存済みの状態から再開でき、副作用の重複を照合できる。ロック・再試行・復旧はActionsの再実行で足りる範囲に限定し、複雑になったら実績ある仕組みに任せる
- NFR-09 ログ、トレース、画面、利用者回答に保持期間とアクセス権を設定し、秘密情報をマスキングする。保持期間・閲覧権限・削除条件はquality.yamlの`evidence:`に書き、認証情報そのものは書かない
- NFR-10 案件側のリポジトリには、設定（quality.yaml）、仕様（openspec/）、共通ルール（CLAUDE.md、AGENTS.md）、証跡（`.loomake/evidence/`）、レポート（`reports/quality/`）と、4ジョブを呼ぶ薄いワークフローを置く。Loomakeの実行ロジックとジョブ本体は複製せず、reusable workflowを呼ぶ
- NFR-11 状態の正本は情報の種類ごとに1つ（Git管理のファイルと長期保管先）。独立して編集する正本を増やさない。派生物は正本から再生成できるものに限る（7.9）。常駐プロセス、DB、キューは必要になるまで持たない
- NFR-12 テストは壊れると困る境界（誤合格、証跡不足、途中停止、重複実行）を重点的に確かめる

## 7. 仕様

### 7.1 quality.yaml

利用時品質目標（`objectives`）と製品品質要件（`product`）を分けて持ち、`linked_requirements`で関連づける。各項目は合格証拠（`evidence`）と参考指標（`indicators`）を分ける。案件ごとにリポジトリ直下に置き、Gitで版管理する。品質目標の正本はこのファイルで、DBを持つ場合は参照のみとする。実行中は基準版を固定し、基準の変更は版を分けて過去の結果を新しい基準の合格に流用しない。

```yaml
version: 2
model: iso-iec-25010-2011        # 品質モデルの識別子と版
defaults:
  window: 14d                    # 利用時の指標の比較期間
  min_samples: 100               # 判定に必要な最低サンプル数
report:
  status: weekly                 # 品質状況レポートの頻度（weekly / daily）
  publish: discussion            # 投稿先（discussion / issue / none）

objectives:                      # 利用時品質目標
  UQ-001:
    characteristic: efficiency
    context: CONTEXT-001         # 対象利用者、作業、端末、環境の定義への参照
    task: 月次締めを完了する
    evidence:                    # 合格に必要な証拠
      - metric: task_duration_p90_sec
        source: telemetry.task.monthly_close   # 本番計測。なければ observation.*
        target: "<= 1800"
        min_samples: 20
    indicators:                  # 参考指標（傾向を見る。これだけでPASSにしない）
      - metric: e2e_duration_sec
        source: e2e.monthly_close
    guardrails: [UQ-002]         # 悪化を防ぐ目標（例：タスク成功率）
    blocking: true
    linked_requirements: [PQ-012, PQ-020, REQ-003]

product:                         # 製品品質要件（副特性ごと、複数可）
  PQ-012:
    characteristic: usability
    subcharacteristic: operability
    objectives: [UQ-001]
    evidence:
      - metric: e2e_steps
        source: e2e.monthly_close
        target: "<= 12"
    indicators:
      - metric: task_abandon_rate
        source: telemetry.task.monthly_close
  PQ-031:
    characteristic: maintainability
    subcharacteristic: testability
    evidence:
      - metric: coverage_line
        source: ci.coverage
        target: ">= 80"
      - metric: tests_without_assertion
        source: ci.test_report
        target: "== 0"
    blocking: false
  PQ-040:
    characteristic: compatibility
    subcharacteristic: coexistence
    applicability: not_applicable
    reason: "単一テナントの専用環境で他システムと同居しない"
    confirmed_by: r

automation:                      # 自動実行条件（7.5）
  level: A1
  allowed_paths: ["src/**", "!src/auth/**", "!src/payment/**"]
  protected_paths: ["src/auth/**", "src/payment/**", "migrations/**", "tests/**"]
  max_diff_lines: 250
  require_rollback: true

evidence:                        # 証跡の保管方針（7.9）。最小スキーマは下の表、案件ごとの値はO16
  artifact_retention: 90d        # CI成果物の保持期間（開発中の本体）
  long_term_store: github-release   # リリースに採用した本体の長期保管先
  long_term_retention: 5y        # 長期保管の保持期間
  access: project-members        # 閲覧権限
  delete_policy: owner-approval  # 削除条件
```

- `source`はCI成果物、静的解析、依存監査、負荷テスト、E2E、時系列DB、利用者評価の取り込み（`observation.*`）のいずれか
- `blocking: true`の未達は他の達成で相殺せず、公開を阻止する
- 既定の雛形（31副特性の製品品質要件と、利用時品質目標の例）を`loomake init`が生成する。雛形の指標は参考指標から始め、合格証拠は案件ごとに決める

`evidence:`の最小スキーマ（coreのZodスキーマで定義し、既定値を補う。読み元はquality.yamlだけで、環境変数やAGENTS.mdから値を拾わない）

| キー | 型 | 既定値 | 用途 |
|---|---|---|---|
| `artifact_retention` | 期間（`90d`のような文字列） | `90d` | 開発中の本体に要求する保持期間。要約には実際の保存期限を書き、この値を満たすかを照合する |
| `long_term_store` | enum。初期は`github-release`と`manual` | `github-release` | リリースに採用した本体の保管先。`manual`は自動転送が未実装の間の手動運用 |
| `long_term_retention` | 期間 | `5y` | 長期保管の保持期間 |
| `access` | enum。初期は`project-members`と`owner` | `project-members` | 取得確認に使う閲覧者の権限 |
| `delete_policy` | enum。初期は`owner-approval`と`never` | `owner-approval` | 削除条件 |

- `evidence:`を省略すると既定値で動く。verify --spec-onlyはキーの不足で止めず、値が不正なときだけ止める
- 要約には設定のキー名ではなく、確認した実際の値（CI側で確認した実際の保存期限、保管先の場所）を書く。あとで設定が変わっても当時の要約の意味が変わらないようにする
- enumは、その保管先への転送と取得確認を実装したときに増やす。増やす手順はO16
- `artifact_retention`の既定はGitHub Actionsの成果物の既定の保持期間に合わせる。要約に書く保存期限はCI側の実際の期限で、quality.yamlの値は要求する保持期間として、実際の期限がそれを満たすかを照合する。設定値から期限を計算して書かない

| 列 | 内容 |
|---|---|
| 要件ID | REQ-xxx、PQ-xxx、UQ-xxx |
| 受け入れ条件 | 指標の形 |
| 副特性 | 該当する品質副特性 |

### 7.3 verify と判定の順序

| コマンド | 成功条件 | 終了コード |
|---|---|---|
| `verify --spec-only` | ブロッキング確認事項がゼロ | 0 / 1 |
| `verify --done` | FR-07の全条件、FR-08の適格性あり、FR-09の検知なし（検知時は基準の緩和として人へ） | 下の表 |
| `--json` | `scope`と実行状態の組で構造を分ける（判別可能な共用体）。(a) `scope: ci`、completed / partial：`{schemaVersion, change, run:{status, errors[]}, scope: "ci", checks:[{id, result, reason, evidence}], summary:{fail, insufficient, not_applicable, evaluated}, decision:{required, reasons:[{code, target, message}]}, verdict}`。(b) `scope: local`、completed / partial：同じ項目から`verdict`を除き、`summary`に`pending`（未完了のローカル項目数）を持つ。`decision`は品質判定とは別の軸で、人の判断が要るかを表す。`code`は`CRITERIA_RELAXATION`（FR-09の検知）、`PROTECTED_PATH`（保護パスへの変更）、`APPROVAL_REQUIRED`（7.5で人の承認が要る変更種別）、`LIMIT_EXCEEDED`（FR-13の上限超過）から始め、追加は`schemaVersion`の規則に従う。(c) aborted（scopeを問わない）：`{schemaVersion, change, run:{status: "aborted", errors[]}}`（checks・summary・verdictを持たない）。resultとverdictは4値。項目の全体は7.9の「判定の要約」 | 下の表 |

終了コード（表示形式に関係なく同じ。上の行が優先）
| 条件 | 終了コード |
|---|---|
| 実行状態がabortedで、原因が引数・change-idの誤り（`run.errors`の種別`usage`）または設定の内容の誤り（種別`config`） | 2 |
| 実行状態がabortedで、原因がそれ以外（権限、外部ツール、ネットワーク、実行時の失敗） | 3 |
| `decision.required`がtrue（FR-09の検知、人の承認が要る変更種別、上限超過）。`scope: ci`でverdictがFAILまたはINSUFFICIENT_EVIDENCE。`scope: local`で`summary.pending > 0`または`summary.fail > 0` | 1 |
| `scope: ci`でverdictがPASS。`scope: local`で`summary.pending = 0`かつ`summary.fail = 0`（最終合格ではない。下の集約の規則） | 0 |

要判断は終了コード1で返し、通常の不合格とはJSONの`decision.required`で区別する。要判断とFAILが同時にあれば、FAILの内容はJSONの`checks`と`summary`に残す。終了コード2と3は既存のCLI（REQ-041・REQ-192）と同じ意味に保ち、2を使い方の誤りとして扱う利用者のスクリプトを壊さない。`decision`は関数の戻り値にも含め、runnerは終了コードではなく`decision.required`を見て、修正を続けず判断待ちとして停止する（FR-13の「要確認」と同じ扱い）。人の判断が要る変更を、FAILの自動修正で進めてはいけないため。gateは0以外を合格にせず、判断待ちかどうかはJSONから表示する。`decision.reasons`には理由の種別、判断の対象、人向けの説明を入れる。

判定の順序（verify --done と評価ジョブで共通。入力から結果を返す純関数として実装し、ファイルの読み書き・ネットワーク・外部コマンドは呼び出し側に置く。1〜2は要約を再利用するgate・eval・trace reportも同じ関数で行う）
1. 品質要件と検証計画の版を確認する
2. 証跡の対象コミット、環境、手順、鮮度を照合する。要約を再利用する場合は、生成元をCIの実行ID・試行番号・対象SHAで照合し、改変の有無と、評価対象と基準の一致も確認する。検証器・必須チェック・許可ルールの定義は、信頼する基準ブランチか固定版から取る。エージェントが提出した要約だけではPASSにしない。固定済みの要約はリリース記録が持つハッシュと照合する
3. 期待する検証が実行され、必要な成果物が存在することを確認する。CIの集約ジョブがskipやneutralでも、必要なテストの実施を確認できなければ合格にしない
4. 目標・要件ごとに合格証拠の条件を判定する。参考指標は集計するだけ
5. 必須条件の未達、証跡不足、未解決の重大指摘を集約する
6. 自動実行条件と公開条件を照合する
7. 判定理由と根拠を保存する

集約の規則
- 合格証拠が未定義、または未実施の要件はINSUFFICIENT_EVIDENCE。証拠の配列が空のまま全件一致でPASSにしない
- 有効な証拠で必須条件の違反を確認できればFAIL
- NOT_APPLICABLEには理由と確認者を必須にする
- 全体の判定（verdict）は、FAILが1件でもあればFAIL、FAILがなく証跡不足があればINSUFFICIENT_EVIDENCE、PASSが1件以上あり残りがすべてPASSかNOT_APPLICABLEならPASS。評価対象がゼロ、または全要件がNOT_APPLICABLEのときはINSUFFICIENT_EVIDENCEとし、完了ゲートのPASSにしない。全体とは別に、FAIL・証跡不足・NOT_APPLICABLE・評価した件数を残す
- `scope: local`の結果はverdictを持たず、ローカル実施項目の完了状況だけを返す。ローカル項目の完了は、必要な証跡を確認してPASSになった場合、または理由と確認者を持つNOT_APPLICABLEの場合に限る。INSUFFICIENT_EVIDENCEは未完了として`pending`に数え、FAILは`fail`に数える。テストのプロセスが終了しても成果物を取得できなければ完了ではない。ローカル項目がすべて完了したとき（`pending = 0`かつ`fail = 0`）の終了コード0は「Draft PRを作ってよい」を意味し、最終合格ではない。gateはローカル要約だけでは合格にしない。最終合格はCI必須項目を含む全条件で判定する（FR-12）

実行状態と実行エラー（品質判定とは別の軸）
| 軸 | 値 |
|---|---|
| 実行状態（`run.status`） | completed、partial、aborted |
| 品質判定（`checks[].result`、`verdict`） | PASS、FAIL、INSUFFICIENT_EVIDENCE、NOT_APPLICABLE |

- 証跡の取得が権限不足などで一部できなかった場合はpartialとし、該当要件をINSUFFICIENT_EVIDENCEにして、原因の実行エラーを`run.errors`に入れる
- 設定を解析できず評価対象を確定できない場合はabortedとし、品質判定を生成しない。終了コードは、設定の内容の誤りなら2、読み取りの権限や外部ツールの失敗なら3
- `run.errors`の各要素は、種別（usage、config、permission、tool、network、runtime）、対象、メッセージ、次に取れる操作を持つ。usageは引数・change-idの誤り、runtimeはほかの種別に当たらない実行時の失敗
- 互換性：`0.x`の間はフィールドの追加は版を上げずに行い、削除・意味の変更・判定値の追加・終了コードの変更は`schemaVersion`を上げて移行方法を添える。読み手（gate・eval・trace report・外部ツール）は未知のフィールドを拒否せず無視する契約とし、Zodスキーマは未知のフィールドを通す設定で定義する。実行状態ごとの構造は判別可能な共用体として定義する

### 7.4 エージェント接続の契約

入力：changeのID、リポジトリのパス、対象コミット（base_sha）、仕様と品質目標の参照、触ってよいパス（allowed_paths）、検証計画、上限（回数・時間・費用）、出力スキーマの版
出力：status、changed_files、commit_sha、tests_reported、evidence_refs、unresolved_questions、session_ref、usage

- 出力はZodスキーマで検証する。tests_reportedは自己申告として扱い、合否はverifyがCIと成果物で決める
- Issue本文など外部の文章はデータとして渡し、実行権限を変える指示とは区別する
- エージェントは標準`spawn`を薄く包んだ共通関数で呼ぶ。ライブラリとしては取り込まない

| エージェント | 起動方法 |
|---|---|
| Claude Code | `claude -p`（headless）、または`anthropics/claude-code-action`。セッション継続やツール承認の制御が必要になればAgent SDK |
| Codex | `codex exec`、または`openai/codex-action` |

### 7.5 自動実行条件と変更種別

自動実行（人の承認なしの実装・マージ）は、副特性やパスのどれか1つではなく、次の条件の組み合わせで判定する。実装を始めてよい条件と、マージしてよい条件は分ける。実装前は予定（changeの範囲）で、マージ前は実差分で判定する。

実装前（実装を始めてよい条件）
| 条件 | 自動実行できる状態 |
|---|---|
| 変更する機能・ファイル・依存関係 | 予定が`allowed_paths`内のみ。`protected_paths`（認証、権限、決済、マイグレーション、公開API、`tests/`）に触れない。依存更新はメジャー更新でない |
| 基準 | 適用するquality.yamlと検証計画が承認済みの版である |
| 検証計画 | 影響先の要件に対して、実行できる検証（テスト、契約テスト、目的単位のE2E）が定義されている |
| 上限 | 修正回数・時間・費用・同時実行数の上限内（FR-13） |

マージ前（マージしてよい条件）
| 条件 | 自動実行できる状態 |
|---|---|
| 実差分 | 実差分が`allowed_paths`内のみで、`protected_paths`に触れていない。差分が`max_diff_lines`以内で、コードのrevertで戻せる（データ移行を含まない） |
| 外部に見える挙動の変更 | 公開APIの契約、画面の操作手順、データ形式を変えない（契約テストと目的単位のE2Eが通る） |
| 影響する品質要件 | 影響先の要件がすべて`blocking: false`、または修正後の合格証拠がそろっている |
| 検証の充足度 | 影響先の要件に修正後の合格証拠があり、INSUFFICIENT_EVIDENCEがない |
| 未解決の指摘 | AIレビューと人の指摘に未解決の重大指摘がない |
| 検証済みコミットとの対応 | 7.9の再利用条件を満たす |

どれか1つでも外れたら人へ戻す。自動実行条件を満たしていても、設定がA1ならマージしない。「保守性だから」「依存更新だから」という副特性や種類だけでは自動実行しない。

変更種別（自動実行条件とは別に判定する）
| 種別 | 扱い |
|---|---|
| 許可範囲の表示・ロジック修正 | 自動実行条件を満たせば実装と検証を自動実行 |
| 新機能、外部API連携 | 仕様と権限の確認後に実行 |
| 認証、権限、決済、破壊的データ変更 | 専用の確認条件。人が全行レビュー |
| 品質基準、評価手順、CIの緩和（FR-09で検知） | 通常の修正と分離した独立の変更として人が判断 |
| 証跡の追加（実差分が許可された証跡ファイルだけ） | アプリケーションの再検証を省略できる。要約のスキーマ、生成元、整合性、固定済み記録の改変、参照関係は検査する（FR-18） |
| 本番公開 | MVPは人の判断後に実行 |
| 目的や許容リスクの変更 | オーナーの判断が必要 |

人がレビューする深さの目安は、保護パスに触れる変更は全行、新規依存やスキーマ変更は該当モジュール、それ以外はテストと差分の流し読み。PRの目安は250行まで。超える場合は分割する。

### 7.7 利用時の品質の評価

利用時の品質は、証跡の出どころを3段で扱う。どの段でも、リリースの対象外とすることと、達成したと判断することは分ける。自社プロダクトは本番計測を最初から入れられるので、3段目を待たずに始める。OSSは利用者が開発者で計測を取りにくいので、2段目の出どころにIssue・Discussionを使う。OSSの出どころの扱いは次のとおり。

| 出どころ | 扱い |
|---|---|
| ダウンロード数、ドキュメントの参照数、Issue件数 | 原則として参考指標。Issueが少ないことを不具合が少ない証拠にしない |
| Issue・Discussion内の具体的な利用報告 | 対象版・利用状況・達成結果を確認できれば合格証拠の候補 |
| タスク観察、所要時間、利用者アンケート | 定義した条件（標本数、収集方法）を満たせば合格証拠 |

| 段 | 出どころ | 位置づけ |
|---|---|---|
| リリース前 | 目的単位のE2E（想定した利用者と状況） | 参考指標。「想定した利用者が、想定した状況で、目的を達成できるか」までを示す |
| 本番計測なし | 利用者によるタスク実施の観察、所要時間の測定、アンケート、業務記録（`loomake trace record --observation`で取り込む） | 合格証拠になりうる。標本数と収集方法を証跡に残し、少人数なら定性評価を併用して統計的な優劣を断定しない |
| 本番計測あり | OpenTelemetryなどの操作ログ、監視、インシデント記録 | 正とする。E2Eとの差を「E2Eでは見えない部分の大きさ」として追う |

| 特性 | 副特性 | リリース前（E2E） | 本番計測なし | 本番計測あり |
|---|---|---|---|---|
| 有効性 | なし | 想定手順で目的を最後まで達成できるか | 利用者のタスク成功率 | タスク完了率 |
| 効率性 | なし | 自動操作の手数と所要時間（人の操作時間の下限） | 観察した所要時間、手数 | 所要時間、手数 |
| 満足性 | 実用性、信用性、快感性、快適性 | 参考指標なし | アンケート、聞き取り | 評価、継続利用率（継続の理由も確かめる） |
| リスク回避性 | 経済、健康・安全、環境のリスク緩和性 | 誤操作・異常系で損失が出ないこと | 業務記録の差し戻し・損失件数 | インシデント記録 |
| 利用状況網羅性 | 利用状況完全性、柔軟性 | 状況の組み合わせでの完了 | 想定外の状況での観察 | 想定外の状況での完了率 |

有効性と効率性は特性そのものを評価単位にし、副特性を形式的に新設しない。成功者だけの所要時間が縮んでも、失敗者が増えれば改善と判断しない。初回公開時には実利用の証跡がないので、限定公開で観測を始められるが、その時点で利用時の品質を達成済みと表示しない。品質判定は未評価のまま保ち、限定公開の可否は公開条件（公開段階ごとに、未評価のまま進めてよい目標、観測期間、切り戻し条件）で別に判断する。公開条件は自動化レベルに関係なく定義し、A1・A2では人が条件を確認して公開し、A3では許可された範囲でその判断と実行を自動化する。本番にOpenTelemetryの計測点を入れることを、自社プロダクトでは要件段階で受け入れ条件に含める。対象プロダクトの計測項目・計測点・保存は初回公開までに用意し、Loomakeのevalへの自動取り込みは段階6で実装する。評価基盤が完成する前のデータも残し、計測を始めるためにA3を有効にする必要はない。

### 7.9 証跡の保管

リリース判断を後から確認できる状態を保ちながら、実行記録によるリポジトリの肥大化とレビュー負担を抑える。記録を「判定の要約」「実行記録の本体」「リリース記録」に分け、保存先と保持条件を決める。

```
                 verify / eval の実行
                        │
          ┌─────────────┼──────────────────────┐
          ▼             ▼                      ▼
   判定の要約      実行記録の本体          試行履歴・評価履歴
   .loomake/       CI成果物                attempts.jsonl（change ごと）
   evidence/       artifact_retention      history.jsonl（reports/quality/）
   <change>/       （既定 90d）で消えてよい      │
   Git管理          │                          │ 12か月 or 5MB、change の archive で
     │ 保存先・SHA-256・保存期限で参照          │ 月単位に切り出し（過去コミットは残る）
     │              │                          ▼
     │              │ リリースに採用した分だけ   gzip + 索引（期間・件数・スキーマ版・
     │              ▼                          │ 保存先・SHA-256）を Git にコミット
     │        long_term_store                  │ → 別コミットで Git 管理から外す
     │        （Release 添付など、               ▼
     │          long_term_retention）◀─────────┘
     │              │ 取得確認 + SHA-256 照合
     ▼              ▼
   リリース記録  .loomake/evidence/release/<リリースID>/   Git管理
   採用した要約の識別子・ハッシュ、承認者、判断日時、承認状態
   （承認状態を持つのはここだけ。参照された要約は固定）
          │
          ▼
   リリースレポート / 品質状況レポート（同じ JSON から生成）

   ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄
   派生物（Git 管理外、.loomake/quality/）
   SQLite / Parquet などの分析用。正本と保管済み履歴から再生成できる。
   なくても検証・リリース判断は成立する。要約の保存先には書かない
```

正本は上段の Git 管理のファイルと長期保管先で、点線の下は再生成できる派生物。矢印は参照の向きで、下から上へ戻ることはない。

| 種類 | 保存先 | 内容・扱い |
|---|---|---|
| 判定の要約・証跡の索引 | `.loomake/evidence/<change>/`、Git管理 | 評価対象、実行条件、結果、判定理由、本体の保存先・ハッシュ・保存期限 |
| 実行記録の本体 | CI成果物 | テストレポート、トレース、コマンド出力など。開発中の記録は`artifact_retention`で消えてよい |
| リリースの判断に採用した本体 | `long_term_store`（Release添付など） | 成功結果に加え、例外承認の根拠となった失敗結果も保存 |
| リリース記録 | `.loomake/evidence/release/<リリースID>/`、Git管理 | リリースするコードの版（タグと、タグが指すコミットSHAを併記）、採用した要約の識別子・ハッシュ、適用したquality.yamlの版、承認者、判断日時、対象範囲、承認状態、例外と理由。change単位の判断も同じ形式で、リリースIDにchange IDを使う |
| 試行履歴 | `.loomake/evidence/<change>/attempts.jsonl`、Git管理 | FR-47 |
| ローカルキャッシュ | `.loomake/quality/`、Git管理外 | 一時生成・取得用。共有の保存先やリリース判断の正本にはしない。要約の保存先に書かない |
| 固定fixture | テスト用ディレクトリ、Git管理 | テストに必要な最小限の入力と期待結果。実行出力とは分ける |

判定の要約に含める項目
- スキーマ版、実行ID、試行ID、評価器（Loomake）の版
- 対象コミット、仕様ハッシュ、品質基準ハッシュ
- 環境、検証方法・コマンド、ツールの版、実施日時
- checksごとの結果・理由、成功・失敗・スキップ件数
- 各証跡の保存先、SHA-256、保存期限
- 用途を示す`role`（development / release）と、実行元を示す`scope`（local / ci）
- 評価要求（要求ID、起動元、要求時刻）と、観測データ（観測期間、取得時刻、対象の公開版。本番計測や利用者評価を使う場合）
- 本体を確認した判定か、要約の整合性だけを確認した再利用か

要約内の対象コミットは、実際に検証したコードのコミットを指す。要約を追加したコミットへ置き換えない。承認状態はリリース記録だけが持ち、保存先のURLや`role: release`だけでは承認済みと判断しない。`role: release`の要約は、リリース記録から参照された時点で固定する。

再利用の条件（検証済みコミットと、マージ・リリースするコミットの対応）
- 検証済みコミットから対象コミットまでの差分が、許可された証跡ファイルだけなら、要約を再利用できる
- コード、仕様、品質基準、検証方法、実行環境のいずれかに触れる変更が混ざっていれば再検証する。mainへの追従も同じ
- gateはマージ直前にこの対応を再確認し、再利用した要約には再利用元の対象コミットと差分の範囲を記録する

リリース用要約の作り方（開発用の要約は書き換えない。順序を入れ替えない）
1. 開発用要約（`role: development`）を生成する
2. リリース版のコミットに対して、採用する各要約が再利用の条件を満たすかを照合する。満たさないものはリリース版で再検証して新しい要約を作る（FR-37。複数changeをまとめてリリースするときも同じ）
3. 採用する本体を長期保管先へ移し、取得とSHA-256を確認する
4. 元の要約を参照するリリース用要約（`role: release`。保存先と保存期限は長期保管先のもの）を追加する
5. リリース記録がリリース用要約を参照し、固定する。再検証前の結果を固定しない

長期保管の手順（リリースレポートを承認可能にする前に完了する。自動転送が未実装の間は手動で行い、結果は同じ項目でリリース記録に残す）
1. 採用する本体を`long_term_store`に保存する
2. `access`で定めた閲覧者の権限で取得できることを確認する
3. 取得した本体と要約のSHA-256を照合する
4. 保存先、保存期間、確認日時をリリース記録に書く

SHA-256は、取得できた本体と要約の同一性を照合するために使う。本体の復元や、実行の真正性を単独で証明するものではない。Release添付は自動では失効しない長期保管先の候補であり、永続保存の保証ではない。保存責任者・閲覧権限・保持期間・削除条件は`evidence:`に書く。

容量は、本体をGitに入れないことと要約を小さく保つことで抑える。最新索引の上書きは検索性のために行い、Git履歴の容量を減らす手段とは位置付けない。スクリーンショット、動画、トレース、圧縮ログなどのバイナリや大容量の成果物は本体側に置く。試行履歴の上限とローテーションはO14と合わせて決め、リリースに採用した記録とその判断を説明する履歴は削除対象から除く。

#### 履歴の切り出しと派生物

`history.jsonl`と`attempts.jsonl`にも、要約と同じ保存原則を適用する。各行には識別子、日時、評価対象、結果、理由、参照などの構造化した情報を記録し、大きなログや証跡の本体を複製しない。

履歴は容量または期間で区切り（既定値はO14。仮置きは直近12か月または5MB、`attempts.jsonl`はchangeのarchive時）、過去分をgzipで圧縮して`long_term_store`に保存する。保存物のSHA-256を必須とし、展開後の内容ハッシュは任意とする。保存先からの取得とハッシュの照合を確認し、対象期間・件数・スキーマ版・保存先・ハッシュを示す索引をGitにコミットしたあと、別のコミットで元の履歴をGit管理対象から外す。過去のコミットに履歴は残るので、この切り出しは既存のGit履歴の容量を減らす手段ではない。保持期間中の記録は、切り出したあとも取得できるようにする。

分析はJSONLの直接集計から始める。SQLiteやParquetなどの分析用の形式は、保管済みの履歴を含む正本から再生成できる派生物として、Git管理外（`.loomake/quality/`）に置く。通常の検証・リリース判断は、これらの派生物や外部の分析ツール（DuckDBなど）を必須としない。

履歴への同時追記は次のように扱う。
- `history.jsonl`を更新するevaluateは、手動起動と定期起動を含めて同じconcurrencyグループで直列化する。GitHub Actionsの既定の設定では待機中の実行は1件までで、新しい実行が来ると前の待機分は取り消される（`queue: max`を指定すると最大100件まで待機させられる）。evaluateは起動時に評価要求を受付済みとして記録し、次回の実行で前回の保存成功位置以降のActions実行一覧と照合して未記録の取消を取り込む（FR-48）。取り消された要求は次回の実行で再評価し、重複する行は書かない。再評価を元の時刻の結果として記録せず、再評価できない要求は回収不能として残す
- 同一changeのrunはFR-13の同時実行数の上限で1件に制限し、concurrencyグループをchange IDで分けてこれを強制する。`attempts.jsonl`への追記はコミット前に`git pull --rebase`し、競合したら最新状態と再照合して再試行する
- 直列化で対応できなくなった場合は、実行単位の独立した記録を正本とし、集約した履歴を再生成できる索引に改める方式を、O02と合わせて再検討する

## 8. 構成と技術選定

方針は「標準機能を優先し、自作が複雑になる部分だけライブラリに任せる」。詳細な表と理由はアーキテクチャ6章にあり、ここでは要点だけを置く。

| 領域 | 採用 |
|---|---|
| 言語・実行 | TypeScript strict、Node.js LTS |
| ビルド | `tsc`のみ、ESMのみ |
| パッケージ管理 | npm workspaces |
| CLI | 標準`parseArgs`と小さなコマンド表 |

| 自動実行 | GitHub Actionsのreusable workflow。独自の実行基盤は作らない |
| 借りるもの | OpenSpec、Claude Code／Codex／OpenHands、`anthropics/claude-code-action`、Biome・tsc・madge・jscpd・npm audit・gitleaks（静的指標）、Playwright（E2E）、OpenTelemetry → Grafana Cloud（本番計測、段階6）、DuckDB（任意の分析。検証・リリース判断では必須にしない） |

### 段階横断の受入シナリオ：プロダクトの作成と継続改善

目的と欲しいプロダクトから仕様を作成し、実装・検証・公開する。利用者は公開されたプロダクトから改善要望を送り、ツールがその要望をOpenSpec changeに変換して、再び実装・検証・公開する。元の要望から仕様変更、検証結果、公開版、利用者評価までを追跡できることを、段階5までの総合的な出口条件とする（A23）。このシナリオは段階ごとに接続して確認し、未実装の工程を含む全体の完了を、途中の段階の完了条件にはしない。

具体例は、「近所の行きたい店を管理したい」という目的から一覧・登録・編集ができるWebアプリを作って公開し、使ったあとに「定休日で絞り込みたい」と要望を送るものとする。生成するアプリのテンプレート・保存先・配置先は、このシナリオで使う構成として1種類に固定する（アーキテクチャ9章）。これはLoomake全体の対応範囲を限定するものではない。

既存の定義との対応
- 要望の入口：利用者はアプリ内のフォームから改善要望と不具合報告を送る。送信先はIssue（FR-01の入口）で、ツールが対象プロダクト、公開版（リリース記録のタグとコミットSHA）、画面のパスを付ける。稼働中のエラーの自動収集と、利用状況からの改善提案は段階6以降
- 要望の分類：要望に関連する現在の要件を探し、要件の追加、既存要件の変更、仕様どおり動かない不具合、確認が必要な相談のいずれかに分類する。比較対象は、報告対象のリリース記録が指す版の`openspec/specs`。版を特定できない場合は確認事項とする。分類後、現在の仕様と進行中のchangeにも照合し、対応済みまたは対応中の場合はその対応先を要望にひも付け、同じ内容のchangeを重複して作成しない
- 衝突の検出：要望と既存要件・受入条件を照合し、同時に満たせない可能性がある箇所を、該当する要件IDと理由付きで提示する。衝突の疑いはブロッキング確認事項として扱い、利用者の判断前に既存要件を上書きしない。完全な自動判定は約束しない。実装・検証の対象は段階6以降
- 仕様の確認：解釈が分かれる点はFR-03のブロッキング確認事項として保持し、利用者が回答するまで`verify --spec-only`（FR-06）で実装への進行を止める。changeの草案は回答前に生成してよい
- 実装後の判断：`decision.required`は`verify --done`の既存の意味（基準の緩和、保護パス、上限超過）に限り、マージは7.5に従う
- 要望の保存：元の要望を保存し、確定した仕様（archive後の`openspec/specs`）と区別する。評価からの変更は必ずOpenSpec changeを経由する
- 判定と評価：品質検証（既存機能を含む必要な検査）、要望の充足（今回の受入条件）、利用後の効果（利用者が「解消した」「未解消」を回答する）の3つを分けて表示し、対象外の目標は「未評価」と表示する（FR-38）。利用後の効果はFR-39の証跡の形で残し、利用者が1人のときは統計ではなく記録として扱う
- 復旧：データ移行を含まない変更を対象に、保存データを維持したまま以前のアプリ版を再公開する。切り戻しも`role: release`のリリース記録に残す
- 画面：このシナリオを操作する画面は、段階ごとに薄く作る。最初はIssueへの要望登録だけでも成立するが、それだけで仕様変更や改善が完了したとは扱わない
