## 0. 設計原則

Loomake は、少人数で保守でき、人・CI・AI エージェントから同じ判定処理を利用できる構造を優先する。重点的に避けるリスクは、依存の更新による挙動の変化、不要な常駐基盤、状態の二重管理の 3 つ。以下の原則は、このリスクを抑えながら機能を足すための判断基準とする。

原則は「必須ルール」と「現時点の方針」に分ける。必須ルールを変えるには本章の改訂が要る。現時点の方針は再検討条件を持ち、満たしたときに本章を更新して変えてよい。各原則の検証方法と実装作業は付録 A に置き、本章には原則と理由だけを書く。

### 0.1 標準機能を優先し、自作が複雑になる部分はライブラリに任せる

実行時依存を減らすことと、実装を簡潔に保つことが対立したら、保守負担が小さい方を選ぶ。Node.js の標準機能で明確に実装できる処理は標準機能を使い、独自実装に複雑な仕様対応や継続的な修正が必要な処理はライブラリを採用する。依存ゼロを目的に解析器や実行基盤を自作すると、かえってコードが増える。

実行時依存を足すときは、次の 3 点を確かめ、採用理由をこの文書に書く。

1. 標準機能では何が不足するか
2. 自作すると、どの保守負担が生じるか
3. 依存の更新・配布サイズ・対応環境への影響を許容できるか

現時点で認める直接の実行時依存は、外部ライブラリが core の `zod` と kit の `yaml` の 2 つ。内部パッケージへの依存は、依存する側 → 依存先で core ← kit ← trace ← runner ← cli の向きに限る（4 章の表）。runner は証拠の照合と記録に trace を使う。判定関数は kit の公開入口（`exports`）から提供し、runner と trace はそれを呼ぶ。内部ファイルへの直接参照はしない。予算は直接の実行時依存で数え、推移依存の扱いは付録 A に書く。

外部ツール（`gh`、`claude`、`codex`、Biome、Playwright）は標準 `spawn` を薄く包んだ共通関数で呼び、JSON 出力を読む。共通関数と証跡の収集は kit に置く。SDK を Loomake の Node パッケージの依存として取り込まない。Actions 経由で別プロセスとして動かす SDK（OpenHands の Python SDK、必要になった場合の Agent SDK）はこの禁止の対象外で、7.4 の接続の契約で扱う（要件定義 7.4）。ツール側の JSON 形式や終了コードも変わるので、ツール固有の変更は共通の呼び出し処理と変換処理に閉じ込める（必須）。

テンプレートエンジン、ロガー、CLI フレームワークは現時点では導入しない。テンプレート文字列、`console`、`parseArgs` で足りる（方針。必要が生じたら上の 3 点で再検討する）。

### 0.2 責務を分離し、パッケージ分割は具体的な利用要求で決める

読み込み・共通形式への変換・判定・実行・表示を分離する。判定処理を CLI や CI の都合に依存させない（必須）。

判定処理は必要なデータを引数で受け取り、結果を返す通常の関数を基本とする。ファイル操作、外部コマンド、通信、現在時刻の取得は呼び出し側で扱う。同じ入力なら同じ出力になり、誤合格の原因を入力から特定できる（必須）。import やグローバル参照の制限は補助であり、純粋性の保証とは区別する。

CLI は「入力 → 関数呼び出し → 出力」に絞る。runner も同じ関数を使い、判定を二重に持たない。データ構造は Zod スキーマから型を導出し、重複定義しない（必須）。

責務の分離はまずモジュール内で行う。判定関数を共有することと、パッケージを分けることは別の判断で、共有するだけなら kit のままで足りる。kit から quality を独立させる目安は、判定処理を初期化やテンプレート配布から独立して配布・更新したい要求が生じた時点とする（4 章）。クラス階層、DI コンテナ、汎用プラグイン基盤は、具体的な必要が生じるまで導入しない（方針。再検討条件は、同じ境界に複数の実装が並び、追加のたびに既存を広く触るようになったとき）。

### 0.3 状態の正本を情報の種類ごとに定め、常駐基盤は必要になるまで持たない

同じ情報を複数箇所で編集できる利便性より、整合性を保ちやすい構造を優先する（必須）。

仕様・設定は編集対象のファイルを正本とし、Git で履歴を管理する。派生レポートとキャッシュは正本から再生成する。過去の判定結果と実行証跡は記録として扱い、再実行しても当時の記録は復元できないので、保存先・保持期間・完全性の確認方法を別途定める（要件定義 NFR-07、NFR-09）。

```
   情報の種類            正本（編集・記録する場所）              派生物（正本から再生成）
   ─────────────────────────────────────────────────────────────────────────
   仕様・設定            openspec/、quality.yaml      Git    →  JSON Schema、雛形
   判定の要約・リリース記録  .loomake/evidence/       Git    →  リリースレポート、品質状況レポート
   評価・試行の履歴      history.jsonl、attempts.jsonl Git    →  レポートの推移
                          └ 古い分は gzip で長期保管先へ、索引を Git に残す
   実行記録の本体        CI 成果物 →（採用分）長期保管先       （Git や要約内に複製しない。要約が参照）
   分析用                （正本なし）                            .loomake/quality/ の SQLite・Parquet
                                                                   Git 管理外。消しても作り直せる
   ─────────────────────────────────────────────────────────────────────────
   矢印は左から右へだけ。派生物を直して正本に戻すことはしない（要件定義 7.9）
```

初期構成では Loomake 独自の常駐プロセス、DB、キューを導入しない。ロック・再試行・復旧は、Actions の再実行で復旧できる設計を優先する。ただし、重複した PR 作成や公開を防ぐ照合（FR-16）は Loomake 側に持つ（方針。再検討条件は、再開・長時間待機・並行実行に具体的な問題が生じ、既存の実行基盤とファイルでは解決が難しくなったとき。5 章、O02）。導入する場合は、状態の所有者、再実行時の動作、障害からの復旧方法を先に定義する。

### 0.4 公開する契約を絞り、互換性の範囲を明示する

内部を自由に変更できるよう、公開する入口と保証する挙動を必要最小限にする（必須）。

互換性を検討する対象は次のとおり。

- 関数 API の引数、戻り値、エラー
- CLI のコマンド、オプション、終了コード
- 設定（quality.yaml）のキー、既定値、パスの解釈
- verify と quality-report の JSON フィールドと判定値
- 外部から参照される生成ファイルの形式と保存先

verify の JSON と quality.yaml は形式の `version` を持つ。各形式では、フィールドの追加・削除・意味の変更、判定値の追加、既定値の変更をどう扱うかを定義する（要件定義 7.3）。形式のバージョンとパッケージのバージョンは区別する。内部モジュールへの直接参照は保証対象に含めない。非互換変更には、変更理由と移行方法を添える。

### 0.5 判定と実行エラーを区別し、次の操作まで説明する

結果は、利用者や runner が次の行動を決められる形で返す（必須）。

結果は二軸で返す。実行状態（completed、partial、aborted）と、品質判定（PASS、FAIL、INSUFFICIENT_EVIDENCE、NOT_APPLICABLE）。証跡の取得が権限不足などで一部できなかった場合は partial とし、該当要件を INSUFFICIENT_EVIDENCE にして原因の実行エラーも返す。設定を解析できず評価対象を確定できない場合は aborted とし、品質判定を生成せず実行エラーで終了する。必要な証跡を取得できない不足を合格として扱わない。評価対象がゼロのときも完了ゲートの PASS にしない。JSON は実行状態ごとに判別できる構造にし、aborted は品質判定の項目を持たない。人の判断が要るかは品質判定とは別の `decision`（有無・理由の種別・対象）で返し、runner は終了コードではなくこれを見て停止する。終了コードは表示形式に関係なく同じで、aborted のうち引数・設定の誤り（2）、それ以外の aborted（3）、`decision.required`・FAIL・証跡不足・ローカル未完了（1）、PASS またはローカル項目の全完了（0。最終合格ではない）の順に優先する。要判断と不合格は同じ 1 で、JSON の `decision` で区別する。読み手は未知のフィールドを無視する。構造と互換性の方針は要件定義 7.3 に置く。

`INSUFFICIENT_EVIDENCE` を含む判定結果には、該当する要件・基準、判定理由、不足している証跡、次に取れる操作を含める。再試行の上限に達した場合は、試したことと残る選択肢も示す（FR-13）。

関数 API は構造化した結果を返す。CLI はその結果を人向けの表示または機械向けの JSON に変換する。`--json` のときの stdout には JSON のみを出力し、診断ログや進捗は stderr へ出す（`console.error` など）。非対話環境では入力待ちにせず、不足している引数や設定を示して終了する。

### 0.6 原則を検証し、例外と見直しの理由を残す

機械で確認できる制約は CI で検査し、設計判断が必要なものはレビューで確認する。テストは、壊れると困る境界を重点的に書く。誤合格、証跡不足、途中停止、重複実行。

静的検査だけで純関数であることを保証できるとは扱わない。直接の import やグローバル参照は可能な範囲で制限するが、依存先の副作用、時刻・乱数への依存、引数の変更まではレビューとテストで確認する。

原則への例外が必要な場合は、理由、適用範囲、代替案、再検討条件を PR に書く。継続的な例外や重要な設計変更は ADR に残す。原則の変更は Issue または PR で提案し、メンテナーが決定する。変更履歴は Git で追跡する。`CONTRIBUTING.md` から本章へリンクし、脆弱性の報告方法は `SECURITY.md` に定める。

## 1. 一言でいうと

Loomake は**品質駆動開発のツール群**。構想や Issue から入り、完了ゲート（verify）を通るまで実装を回し、リリースの根拠を残し、評価の結果を次の仕様に戻す。対象は自社プロダクトと OSS（Loomake 自身を含む）で、受託で足す差分は要件定義の付録 B。品質を保つ仕組みはパッケージとして独立させず、kit の verify が担う（将来の分割は 4 章を参照）。

| 担当 | 役割 |
|---|---|
| OpenSpec（外部 OSS） | **何を作るか**：仕様の正 |
| `@loomake/kit` | **どう作らせ、どう確かめるか**：Issue・構想メモからの取り込み・共通ルール・完了ゲート（verify） |
| `@loomake/runner` | **作る**：仕様からレビュー可能な PR まで実装を回す（AI エンジンは選べる） |
| `@loomake/trace` | **作ったと証明し、測って戻す**：リリースの根拠（リリース記録・リリースレポート）、定期評価（eval）、品質状況レポート、改善提案（propose） |
| `@loomake/core` | 上の 3 つをつなぐ**契約**（trace.md・spec・quality.yaml・verify 結果・quality-report のスキーマと読み書き） |

仕様の書式は自作せず OpenSpec を使う。Loomake が担うのは、OpenSpec が持っていない「構想や要件からの入口」と「守らせる仕組み」と「リリースの根拠」と「使われた結果を仕様に戻す経路」。

## 2. 流れ

```
構想・Issue・ロードマップ（Markdown の要件メモを含む）
   │  kit: req-to-openspec Skill（目的・利用状況・受け入れ条件を自分で答えて quality.yaml にも反映）
   ▼
OpenSpec change（proposal / specs / tasks + trace.md）◀────────────────┐
   │  kit: verify --spec-only（ブロッキング確認事項があれば止まる）          │
   ▼                                                                     │
runner: tasks を実装 → ローカル verify（local 項目） → Draft PR → CI verify → 修正 │
   │  kit: verify --done --json（4 値判定・証跡の適格性。最終合格は ci 項目を含む全条件）│
   ▼                                                                     │
trace: 要件台帳 × 検証結果 → リリース記録・リリースレポート                 │
   ▼                                                                     │
公開条件を確認して公開（A1・A2 は人が判断、A3 で自動化）                     │
   │                                                                     │
   ▼                                                                     │
trace: eval（本番計測 + Issue / Discussion で定期評価）→ report --status（週次）│
   │  未達                                                               │
   ▼                                                                     │
trace: propose（証跡を添えた proposal の下書き PR）── 人がマージ ─────────┘
```

上の 5 段が「作って証明する」、下の 2 段が「測って戻す」。戻りは常に OpenSpec change を経由し、評価が直接コードを変えることはない。

## 3. 名前

ブランドは **Loomake ひとつ**に統一する（旧称：Loomkit → kit、Imploom → runner、Traspec → trace）。

| 種類 | 名前 |
|---|---|
| リポジトリ | `loomake/loomake`（モノレポ）、`loomake/site`（Docus） |
| npm | `@loomake/core` `@loomake/kit` `@loomake/trace` `@loomake/runner` `loomake` |
| CLI | `loomake init` / `loomake verify` / `loomake run` / `loomake trace <record|report|eval|propose>` |
| サイト | loomake.dev |

CLI は本体パッケージ `loomake` を 1 つ作り、各サブコマンドを束ねる（`npx loomake init` だけで始められる）。引数の解釈は標準 `parseArgs`、サブコマンドは小さなコマンド表（名前 → 関数）で振り分ける。

| サブコマンド | パッケージ | 役割 |
|---|---|---|
| `init` | kit | テンプレートと quality.yaml の雛形、案件側の薄いワークフローを導入 |
| `verify --spec-only / --done` | kit | 完了ゲート |
| `run <change>` | runner | エージェントに実装させ、ローカル verify → Draft PR → CI verify の結果で修正を回し、レビュー可能にする |
| `trace record` | trace | 証跡の記録。利用者評価の取り込み（`--observation <file>`）もここ |
| `trace report` | trace | リリースレポート（既定）。`--status` で品質状況レポート（週次） |
| `trace eval` | trace | 定期評価。quality.yaml の目標と証跡を照らして 4 値で判定し、history.jsonl に追記 |
| `trace propose` | trace | 未達から proposal の下書き PR |

`@loomake` スコープが npm で取れるか、商標と重ならないかは未確認（要件定義の未決事項 O13）。

## 4. パッケージと責務

| パッケージ | 場所 | 役割 | 実行時依存 |
|---|---|---|---|
| `@loomake/core` | `packages/core/` | 契約。trace.md・spec.md・tasks.md・quality.yaml（解析済み）・テストレポート・CI 成果物の Zod スキーマと型、共通形式への変換、verify 結果と quality-report のスキーマ。外部ツール向けに JSON Schema を `z.toJSONSchema()` で書き出す | `zod` |
| `@loomake/kit` | `packages/kit/` | verify と init の本体、判定関数の公開入口、外部コマンドの共通 `spawn` 関数と証跡の収集、配布するテンプレート（Skill・AGENTS.md・CLAUDE.md・devcontainer・quality.yaml の雛形・案件側ワークフロー）。純粋な判定モジュールと、実行・収集モジュールはディレクトリで分ける | `yaml`、core |
| `@loomake/trace` | `packages/trace/` | 証跡の記録（`record`）、リリースレポートと品質状況レポート（`report`）、定期評価（`eval`）、改善提案（`propose`）。判定は kit の関数を呼ぶ | core、kit |
| `@loomake/runner` | `packages/runner/` | tasks を AI のエンジンに実装させ、ローカル verify → Draft PR → CI verify の結果で修正を回し、レビュー可能にする（`run`）。エージェントと `gh` は kit の共通 `spawn` 関数で呼ぶ | core、kit、trace |
| `loomake` | `packages/cli/` | CLI 本体 | kit、runner、trace（直接使う場合のみ core） |

### 読み取りと判定の線

```
                      依存の向き（依存する側 → 依存先：cli → runner → trace → kit → core）

   ┌──────────────────────────── loomake（cli）────────────────────────────┐
   │  parseArgs → コマンド表 → 関数呼び出し → 表示 / --json（stdout は JSON のみ、診断は stderr）  │
   └───────────┬──────────────────────┬────────────────────────┬───────────┘
               ▼                      ▼                        ▼
      ┌──── kit ────┐        ┌────── runner ──────┐    ┌────── trace ──────┐
      │ init         │        │ run                │    │ record / report    │
      │ verify ──────┼───┐    │ 続行・修正・停止    │    │ eval / propose     │
      │ （完了ゲート）│   │    │ 判定しない          │    │                    │
      └──────┬───────┘   │    └────────┬───────────┘    └────────┬──────────┘
             │           │             │ 判定結果を受ける          │ 判定の順序を共有
             │           └─────────────┴──────────┬───────────────┘
             │                                    ▼
             │                    判定関数（kit の公開入口。通常の関数。I/O・外部コマンド・現在時刻は呼び出し側）
             │                    版の確認 → 証跡の適格性 → 実施確認 → 条件 → 集約 → 自動実行条件 → 根拠
             ▼                                    │
      ┌──────────────────────── core ────────────▼──────────────────────────┐
      │ Zod スキーマと型（trace.md・spec・tasks・quality.yaml・verify JSON・quality-report） │
      │ 読み取りと共通形式への変換（テストレポート・CI 成果物）。合否は決めない          │
      │ JSON Schema の書き出し                                                        │
      └──────────────────────────────────────────────────────────────────────┘

   外部ツール（gh / claude / codex / Biome / Playwright）は kit の共通 spawn 関数で呼び、
   kit の収集モジュールが取得した出力を core の変換処理に渡す。core は取得済みの入力を
   解析・変換するだけで、取得（HTTP・ファイル読み込み・コマンド実行）はしない。
   SDK を Node の依存として入れない
```

- **core** はスキーマと、取得済みの入力の解析・共通形式への変換だけを持つ。テストレポートや CI 成果物の形式を解析するのは core の責務で、取得はせず、合否も決めない
- **kit** が完了ゲートを判定する。必須テスト・閾値・証跡の鮮度（対象コミット・環境・実施日時の照合）などの完了条件は kit の verify に置く。外部コマンドの実行と証跡の収集も kit で、純粋な判定モジュールとは分ける
- **trace** が定期評価を判定する。判定の順序（版の確認 → 証跡の適格性 → 検証の実施確認 → 条件の判定 → 集約 → 自動実行条件の照合 → 根拠の保存）は verify と共通で、kit の判定関数を最初の eval 実装から使う
- **runner** は判定結果を受けて、続行・修正・停止を実行する。判定しない
- 評価が直接コードを変えることはない。改善は常に propose → change → runner の経路を通る

### 将来の分割（kit → kit + quality）

品質を保つ仕組みの置き場として `@loomake/quality` を検討したが、現時点では追加しない。verify を kit に残し、「品質駆動開発」は Loomake 全体の位置付けとして README とサイトで説明する。

分ける目安はコード量ではなく、**品質判定を、初期化やテンプレート配布から独立して配布・更新したい要求が生じたか**。runner や trace が判定関数を共有すること自体は kit のままで成立するので、共有を理由に分けない。

分けるときの形：

| パッケージ | 役割 |
|---|---|
| `@loomake/kit` | `init` とテンプレート（Skill・AGENTS.md・CLAUDE.md・devcontainer） |
| `@loomake/quality` | `verify`、`eval` の判定部分、完了ゲートと品質目標の定義、ブロッキング確認事項の判定 |

- 依存の向きは quality → core のみ。kit・runner・trace が quality に依存する（表の内部依存から kit を外し、quality に置き換える）
- Skill に「verify が通るまで直す」と書く指示は kit のテンプレートに残し、何を通すかの定義だけ quality に置く。テンプレートがゲートの中身を複製しない
- サブコマンドは `loomake verify` のまま。パッケージ名の quality は表に出さない

### 評価の入力と出力

`trace eval` の入力は、trace の証跡、verify の JSON、quality.yaml、CI 成果物、時系列 DB の読み取り結果、取り込んだ利用者評価に限定する。未測定・証跡不足は INSUFFICIENT_EVIDENCE（「未評価」）と出し、合格にしない。出力は quality-report.json、`reports/quality/history.jsonl` への追記、人が読むレポート。リリースレポートと品質状況レポートは同じ JSON から生成し、見せ方だけを変える。

## 5. リポジトリ構成

```
loomake/loomake            npm workspaces
├── .devcontainer/
├── .github/workflows/     run / gate / evaluate / propose を reusable workflow として公開
├── packages/
│   ├── core/              @loomake/core
│   ├── kit/               @loomake/kit
│   ├── trace/             @loomake/trace
│   ├── runner/            @loomake/runner
│   └── cli/               loomake
├── openspec/              Loomake 自身の仕様（kit で自分を作る）
├── quality.yaml           Loomake 自身の品質目標
└── reports/quality/       quality-report.json・history.jsonl・YYYY-WW.md
```

案件側には設定（`quality.yaml`）・仕様（`openspec/`）・共通ルール（CLAUDE.md・AGENTS.md）・証跡（`.loomake/evidence/`）・レポート（`reports/quality/`）と、4 ジョブを呼ぶ薄いワークフロー（`uses: loomake/loomake/.github/workflows/<job>.yml@v1`）を置く。Loomake の実行ロジックとジョブ本体は複製しない（要件定義 NFR-10）。

- **モノレポにする理由**：3 つのツールは契約（trace.md の書式・verify の JSON・quality.yaml）でつながっており、初期は契約が頻繁に変わる。1 つの PR でまとめて直せるようにする。1 人開発なので分けるメリットがまだない
- パッケージの版管理は changesets か `npm version` を段階 1 で決める
- **分けるタイミング**：外部コントリビューターが付いたとき、またはリリース周期が大きくずれたとき
- 既存の `traspec` は、契約と再利用範囲を確認したうえで（要件定義 O09）、`git subtree add` で `packages/trace` に取り込むことを候補にする
- Nuxtart は Loomake とは別枠なので別リポジトリ
- 実行基盤は GitHub Actions のみで始める。常駐ワーカー・DB・Inngest は、再開や長時間待機が問題になってから検証する

## 7. 作る順番

段階と出口（受入シナリオ）は要件定義 10 章を正本とし、この章は各段階で実装する内容だけを補足する。順の番号は要件定義の段階に対応し、順 0 は段階 1 の前半。要件定義 10 章の段階横断の受入シナリオ（A23）は、順 3 と順 5 で固定した構成（9 章）を使って確認する。

| 順 | 対象 | やること | 理由 |
|---|---|---|---|
| 0 | core | `verify.mjs` の解析処理を切り出し、Zod スキーマに `version` を付ける。quality.yaml のスキーマと JSON Schema の書き出し。verify JSON に対処情報のフィールドと、実行エラーを分ける構造を入れる（要件定義 7.3）。各パッケージの `package.json` に `exports` を置き、公開する入口を限定する。最初の契約テストは、要件定義 7.3 の JSON の各構造（ci の completed / partial、local の completed / partial、aborted）と終了コードの対応にする | 3 ツールすべてが依存するので最初に固める。契約テストが仕様をそのまま検証する |
| 1 | kit・trace | `npx loomake init` で導入可能にし、Loomake 自身の Issue と Markdown の要件メモを 1〜2 本流して直す。quality.yaml の雛形と案件側ワークフローを出す。eval を内部品質（静的指標）だけで動かし、週次の品質状況レポートが出る状態にする（eval は最初から kit の判定関数を使う）。CI に、`dependencies` の予算照合、`--json` 出力のスキーマ照合テスト、判定ディレクトリの import 制限を入れる。`SECURITY.md` と `CONTRIBUTING.md` を置く。リリースレポートの試作（trace.md と verify JSON から要件 ID ごとの表を出すだけ）を置いてよいが、リリース記録・長期保管・承認状態は段階 5 | ここが甘いと後ろが全部ぶれる。kit と合わせて「要件 → 実装 → 証拠 → 状況」が一周する |
| 2 | gate | verify と AI レビューを必須チェックにし、変更種別と自動実行条件（実装前・マージ前）を判定する。A2 の自動マージは実装するが初期設定は無効 | runner より先に、PR 側の判定を固める |
| 3 | runner | Claude Code の headless 実行だけに対応し、1 つの change をローカル verify → Draft PR → CI verify → 修正 → レビュー可能まで持っていく MVP。生成アプリの構成（9 章）の保存先と配置先は、この順の実装前までに選定する。A23 の確認は、この順では 1 つの change を実装・検証し、Draft PR 上の CI verify と必要な修正を経て、レビュー可能な状態にするところまでとする。マージ・公開・利用者評価・復旧を含む一往復は順 5 で確認する | 最も難しい。完了判定と証拠の出力先が先にあれば「CI の verify が通るまで回す」に絞れる |
| 4 | trace | propose を足し、保守性の未達からリファクタ提案を一周させる | 評価が仕様に戻る経路が閉じる |
| 5 | trace | リリース記録、リリース用要約、長期保管、リリースレポートの本実装。目的単位の E2E 生成と利用者評価（Issue・Discussion・観察）の取り込み。自社プロダクトの計測項目・計測点・保存はこの順を待たず初回公開までに用意し、eval への自動取り込みは順 6（要件定義の段階 6）で実装する。A23 の公開・復旧・利用者評価までの一周は、9 章の構成でこの順で確認する | 外側のループが閉じる |

判定関数の共有は順 1 の eval から始まるので、4 章の分割の目安（配布・更新の独立）に当たるかは、順 3 以降で kit の配布頻度と判定の変更頻度がずれ始めたときに見る。

## 8. 開発環境

devcontainer を標準にする（Node 24・npm・OpenSpec CLI・Claude Code・Codex・gh・Biome）。

- ログイン情報（`~/.claude`・`~/.codex`）は名前付きボリュームに置く
- runner の実行環境はこの devcontainer を土台にし、ネットワークは許可ドメインに絞る（要件定義 FR-15。権限確認の有無にかかわらず必須）。人が対話で使う devcontainer でも、権限確認なしで AI を動かすときは同じ制限をかける
- エージェント実行と、最終判定・マージ・リリース承認を担う処理の権限を分離する。エージェントには、判定を承認済みにできる資格情報を渡さない
- エージェントの実行環境に本番の資格情報を渡さない。計測は読み取り専用 API で取る

## 9. 受入シナリオで使う生成アプリの構成

要件定義 10 章の段階横断の受入シナリオ（A23）で、Loomake が生成して公開するアプリの構成を 1 種類に固定する。runner が生成するコード、検証方法、公開と復旧の手順がこの構成に依存するため、順 3 の実装前までに決める。これは受入シナリオで使う構成の固定であり、Loomake 全体の対応範囲を限定するものではない。

この章で決めるのは生成するアプリの構成で、Loomake を操作する管理画面の技術構成（6 章の Nuxt 4 ＋ Nuxt UI）とは別の項目とする。管理画面の提案を根拠に、生成アプリ側の構成を決定済みとは扱わない。受入シナリオを操作する画面は段階ごとに薄く作り、最初は Issue への要望登録だけでも成立する（要件定義 10 章）。

| 項目 | 制約 | 状態 |
|---|---|---|
| アプリ | Nuxt の単一テンプレートを使う。生成 AI にはこのテンプレートの範囲で画面・機能・テストを作らせる | 採用 |
| テンプレートの配置 | Loomake リポジトリ内の `templates/nuxt-supabase/` に置く。生成時に対象アプリのリポジトリへコピーして独立させ、使用したテンプレートのコミット SHA を記録する。テンプレートの更新を生成済みアプリへ自動で反映する仕組みは MVP では作らない。別パッケージとしての配布と版管理は増やさない | 採用 |
| 保存先 | Supabase の PostgreSQL。アプリの公開版から独立し、アプリの再配置と切り戻しでは DB を変更しない。実装・CI はローカル Supabase（CLI）とテストデータ、プレビューは本番と別の検証用プロジェクト、本番は専用プロジェクトに接続する。検証用環境は 1 つを直列に使い、PR ごとの分離環境（branching）は必要になってから広げる | 採用。契約は公開検証の開始時点（下の段落） |
| 配置先 | Vercel。Git 連携による自動デプロイは `git.deploymentEnabled: false` で無効にし、公開は Loomake の公開ジョブだけが行う。手順は「候補を作る → 確認する → 公開する」に統一する：`vercel deploy --prod --skip-domain` で本番ドメインに割り当てない候補を作り、対象デプロイの検証・公開条件（要件定義 7.7）の確認・必要な人の判断を経て、`vercel promote <deployment-id>` で本番ドメインに割り当て、公開結果（デプロイ ID と到達先）を確認してリリース記録に残す | 採用。契約は公開検証の開始時点（下の段落） |
| 生成範囲 | 画面・機能・テストは変更できる。実行基盤、保存方式、テンプレートそのものの変更は別途判断する。関連ファイルを `protected_paths` に指定し、対象パスはテンプレート作成時に実在するパスへ確定する（下の表）。保護パスの判定とマージは要件定義 7.5 に従う | 採用。対象パスはテンプレート作成時に確定 |
| 公開 | 検証対象のコミットと、実際に公開したデプロイ ID・到達先を対応付ける。公開条件は要件定義 7.7 に従う | 採用 |
| 復旧 | データ構造を変えない改善に限り、同じ保存先を使って以前のアプリ版を再公開する。データ移行の巻き戻しは対象外（要件定義 7.5 の「コードの revert で戻せる」と同じ範囲）。MVP では直前の正常な本番デプロイを復旧対象とし、その保持と利用可否、DB・設定との互換性を公開前に確認する。復旧は同じ公開ジョブの復旧処理から実行し、結果をリリース記録に残す。Vercel の切り戻しは当時のビルドに戻るだけで環境変数は戻らず、Hobby では直前の版に限られる。過去に promote 済みのデプロイは再 promote できず、保持期限で消えたデプロイは ID を記録していても使えないため、`promote` を任意の版への復旧手段とはみなさない | 採用。切り戻し先の範囲は契約プランに依存（Pro を前提） |
| 履歴 | 通常の公開と復旧をともに `role: release` のリリース記録に残し、稼働中の版を追跡する（要件定義 7.9）。Supabase の無料プロジェクトは 7 日間の低活動で自動停止するので、停止していた期間は利用なし・目標未達と混同せず、開始・終了・理由を観測不能の期間として証跡に記録する | 採用 |

資格情報は用途ごとに分け、runner に本番の資格情報を渡さない（要件定義 NFR-03、8 章）。

| 用途 | 方針 |
|---|---|
| Vercel への公開 | 公開ジョブだけが Vercel のトークンを使う |
| 通常のアプリ利用 | Supabase Auth と RLS、publishable key を基本とする。従来の `anon`・`service_role` を前提にせず、現行の publishable／secret key を基準にする |
| 高権限の処理 | secret key と service role は RLS を迂回するため通常の利用者操作には使わず、必要な場合だけ専用ジョブまたはサーバー実行環境に限定する。公開ジョブに高権限キーを置くことを必須にしない |
| runner | ローカル Supabase とテスト用の資格情報を使う |

契約プランは、公開検証（A23 の公開・復旧・継続評価の確認）を始める時点で Vercel Pro と Supabase Pro に移行する。段階 1 では契約せず、初期の動作確認は無料枠で進めてよい。本番は Supabase Pro の専用プロジェクト、検証用は同じ Pro 組織の別プロジェクトとし、実装・CI はローカル Supabase を使う。Vercel Pro にする理由は、保持されている過去の本番デプロイを切り戻し先に選べること（Hobby は直前のデプロイに限られる）と、商用利用への移行。Supabase Pro にする理由は、非活動による自動停止を避けて利用者評価を続けること。目安は Vercel Pro が月 20 ドル、Supabase Pro が月 25 ドルからで、追加プロジェクトは月 10 ドルから。1 人・Supabase の小規模プロジェクト 2 つなら月 55 ドル程度に税と従量料金が乗る。AI の実行費用と GitHub Actions の料金は別。

`protected_paths` の初期設定（生成アプリ側）。保護は変更の禁止ではなく、要件定義 7.5・FR-19 に従って人の判断・承認を求める意味。生成アプリにも 7.5 の既定（`tests/` を保護パスに含める）と FR-19（`tests/` と受け入れテストの変更は CODEOWNERS で人の承認を必須にする）をそのまま適用し、例外は置かない。runner はテストの生成・変更まで行い、必要な承認を経てマージする。承認負担の例外が要るかは、実際の承認負担を測ってから検討する。対象パスは、テンプレート作成時に実在するパスへ確定し、実在するものだけを登録する。

| 保護対象パス | 保護するもの |
|---|---|
| `tests/**` | 受入・回帰テスト。FR-19 に従って CODEOWNERS も設定する |
| `vitest.config.*`、`playwright.config.*` | テスト対象・除外・実行条件 |
| `quality.yaml`、Loomake の設定ファイル（パスは既存定義に合わせる） | 品質基準・判定・保護ルール |
| `supabase/migrations/**` | スキーマ・RLS・権限の変更 |
| `supabase/config.toml` | Supabase の構成 |
| `server/utils/db.ts`、`server/utils/auth.ts` | DB 接続・認証の共通処理 |
| `nuxt.config.ts`、`vercel.json` | 実行・配置・自動デプロイの設定 |
| `.github/workflows/**`、`.github/CODEOWNERS` | 検証・公開処理と承認ルール |
| `scripts/release/**` | 公開・復旧スクリプト |
| `package.json`、ロックファイル（pnpm なら `pnpm-lock.yaml`）、`.npmrc` | 依存関係・実行スクリプト・インストール設定 |

通常は保護対象にしない範囲は、`app/pages/**`・`app/components/**`・スタイル・画像、`server/api/**` の通常の業務処理、`tests/` に集約したテストで検証する通常のドメイン処理。認証や権限制御を通常の API ファイルに散らすとパス保護から漏れるので、テンプレートでは共通モジュール（`server/utils/auth.ts` など）に集約し、パス保護に加えて認証・権限の回帰テストで確認する。Loomake 本体側は別の設定で、`templates/nuxt-supabase/**` を丸ごと保護する（生成アプリへの影響範囲が広いため）。最初はこの構成で固定し、実際に承認が必要になった変更を記録してから保護範囲を調整する。

構成の検証は、段階 1 を進めたあと、順 3 で runner に接続する前に次の順で行う。(1) 最小テンプレートを作る（一覧・登録・編集・認証・DB 接続・テストが動く。定休日のデータ項目は初回から持たせ、絞り込み機能は入れない。A23 の改善で DB 移行が不要になり、合意した復旧範囲をそのまま検証できる）。(2) テンプレート内の実在するファイルと設定に対応させて保護対象パスを確定し、画面だけの変更は通常の検証に進み、テストの変更は FR-19 の承認対象になり、DB 移行・公開設定の変更は保護パスとして検出され、品質設定・保護ルール自体の変更は判断対象になることを、実際に変更して確かめる。(3) 公開・復旧を人の操作で一度通す。同じ DB を保持したまま改善版を公開して正常版へ戻し、復旧後も登録済みの店が残ること、稼働版とリリース記録が一致することまで確認する。ここが通れば、その手順を公開ジョブへ移す。(4) runner に接続し、固定した構成で 1 つの change が CI 検証・修正を経てレビュー可能になることを確認する。

通らない場合はテンプレートの範囲を見直す。代替として検討した Cloudflare Workers＋D1 は、loomake.dev と運用先をまとめられる利点があるが、D1 が SQLite であり、まず PostgreSQL で一往復を完成させる優先順位に合わないため今回は採らない。
