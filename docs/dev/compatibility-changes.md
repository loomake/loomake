# 互換性を変えるPRの準備

公開契約を変えるPRでは変更理由と利用側の移行方法を、実装と同じPRでレビューできるようにする。維持する契約と旧形式の対応範囲は[互換性と対応範囲](../guide/3.reference/1.compatibility.md)、契約の対象は[アーキテクチャ0.4](../architecture.md#04-公開する契約を絞り互換性の範囲を明示する)に従う。

## 変更前に確かめる

関数API、CLIのコマンド・オプション・終了コード、設定、公開JSON、外部から参照される生成ファイルへの影響を調べる。利用者のこれまでの使い方が動かなくなる場合は、対応するchangeに変更理由、変更前後の振る舞い、移行方法を記す。未決の製品仕様はtrace.mdに残す。

パッケージと形式のバージョンは別に判断する。[ADR 0002](../adr/0002-breaking-changes-in-0x.md)に従い、パッケージが0.xの間は破壊的変更をminor、それ以外をpatchとする。verify JSONの破壊的変更は、パッケージのバージョンとは別に、REQ-053に従ってschemaVersionのmajorを上げる。ほかの形式はその形式の仕様を確認する。

## PRに残す

[PRテンプレート](../../.github/PULL_REQUEST_TEMPLATE.md)の「公開契約と移行」に、次の内容を書く。該当しない項目にはその旨を書く。

1. 変更する理由と、影響する公開契約・利用側を示す。
2. パッケージと形式それぞれのバージョンの扱いを示す。利用者に影響する変更には[ADR 0001](../adr/0001-versioning-with-changesets.md)に従ってchangesetを付ける。文書や開発用の道具だけの変更には空のchangesetを付ける。
3. 利用側が変えるimport・設定・呼び出し方や、JSONの読み方を変更前後の例で示す。旧形式を読む範囲と、新しい処理や自動再利用に使える範囲を分けて説明する。
4. 維持する旧形式のfixtureは残し、新形式のfixtureを別に追加する。旧fixtureを新形式へ書き換えて互換性の検査を通さない。旧形式への対応を外す場合は、出典・差分仕様・移行手順・テストを同じ変更に含める。
5. 実行した契約テストと結果を示す。公開API・型・JSON・配布物に影響する場合は、該当する検証結果と未確認の範囲を記す。既存のスキーマ互換性検査がJSON Schema全体の互換性を判定できるとは扱わない。

現在の修正対象や検証済みの範囲、互換性検査の制約は、[互換性と対応範囲](../guide/3.reference/1.compatibility.md)を参照する。1.0以降の方針を決めるときは、ADR 0002の見直す条件と[W6-5（Issue #101）](https://github.com/loomake/loomake/issues/101)で別途扱う。
