# Issueを自律して進める手順

2026年11月16日の初回配布に向け、VS CodeのCodexから作業を継続するための手順。製品の仕様や完了条件は [AGENTS.md](../../AGENTS.md) と各changeに従う。

## 管理する場所と担当

作業・受入条件・依存は [マイルストーン](https://github.com/loomake/loomake/milestone/1) の既存Issue、段階の出口と日程の見直しは [進行管理Issue #121](https://github.com/loomake/loomake/issues/121) で管理する。ここには進捗表や残作業の一覧を複製しない。Projectsの設定を待つ必要はない。

管理役は1つのセッションに固定する。管理役が依存を確認して担当を割り当て、実装と独立レビューを分担する。同じIssue・changeへ複数のセッションが重複着手しない。同時に進めるchangeは、ほかのセッションの分も含めて3本まで。実装担当ごとにworktreeを分ける。

## 短い呼び出しで始める

このスキルを含むブランチの作業フォルダで、VS CodeのCodex入力欄に次を送る。ターミナルのシェルコマンドではない。

```text
$delivery
```

[deliveryスキル](../../.agents/skills/delivery/SKILL.md)が既存のGoalを確認し、Goal操作ツールが使える環境では未設定のGoalを登録して、次のIssueへ進む。既存の別のGoalは上書きしない。特定のIssueに絞る場合は `$delivery Issue #61` のように指定する。

新しいスキルが候補に出なければ、Codexの新しいチャットを開くか、VS Codeのウィンドウを再読み込みする。Goal操作ツールが使えない環境では、スキルが案内する短い `/goal` の入力が必要になる。

手順を読み込むことと、ターンをまたぐ自動継続を有効にすることは別である。下の長い起動文だけでGoal登録済みとは扱わず、Goalの登録結果を確認する。停止・再開は `/goal pause`・`/goal resume` を使う。このスキルを作成・インストールしただけでは開発を開始しない。

## VS Codeから始める

1. Loomakeの作業フォルダをVS Codeで開き、Codex拡張にサインインする。最新のmainを取得し、既存の変更があるフォルダではブランチを切り替えず、専用worktreeを用意する。
2. Codexからファイルの編集とテストを実行でき、接続済みGitHubツールでIssue・PRを読み書きできることを確認する。対応していない操作は、利用可能な認証済みの `gh` を使う。認証や権限の不足は記録し、利用者の認証設定を勝手に変更しない。
3. 下の起動文をCodexに送る。別の管理役が動いているときは、新しい管理役を立てず、担当Issueを1つ指定する。

```text
AGENTS.md と docs/dev/autonomous-delivery.md に従って、
https://github.com/loomake/loomake/milestone/1 の初回配布を
2026-11-16までに完了するための開発を進めてください。
進行管理は https://github.com/loomake/loomake/issues/121 に残してください。

最新main、Issueの依存・受入条件、既存PR、worktreeを最初に確認してください。
依存が解けた重要な作業を選び、担当とbranch・change・次の確認点をIssueに記録し、
仕様確認→実装→テスト→独立レビュー→PR→CI確認→受入の順に進めてください。
既存の承認範囲でpush・PR作成・マージ・Issue更新を行い、
1件の区切りで毎回「続けて」を求めず、着手可能な次のIssueへ進んでください。
部分実装のPRでは、Issue全体を完了扱いしないでください。

未決の仕様は推測せず、その作業の確認事項として残してください。
回答待ちの間も、独立して進められる別の作業を続けてください。
完成範囲の縮小、テスト・品質設定の緩和、公開・リリースなど、
AGENTS.mdで個別承認が必要な事項は、その承認に従ってください。

実行を中断するときは、変更したファイル、commitと未pushの有無、
検証結果、未決事項、次に実行する手順を記録してください。
再開時は記録とGitHubの最新状態を照合して続行してください。
```

この文書自体は実行サービスやスケジューラーではない。起動文を送っても、停止したセッションや利用上限で終了した実行が自動で再開するとは限らない。ローカル実行は開発マシンと実行プロセスを維持する。離席中の長い作業には、利用できる場合はIDEからクラウドへの委譲を検討する。現在の実行場所と起動したタスクを確認し、未設定の常駐実行を「稼働中」と報告しない。

## Issueを進める1回の手順

1. **着手を決める**：依存が完了したIssueから、段階の出口につながる作業を選ぶ。担当・branch・change・次の確認点をIssue本文の運用記録に追記し、受入条件など既存の本文を保持する。既に担当がいる場合は重複着手しない。依存の一部だけが解けた場合は、先行できる範囲と受入条件を合意してから切り出す。
2. **仕様を確かめる**：該当changeのspecs・trace・tasksを読む。製品の実装前に `pnpm -s verify --change <change-id> --spec-only` を通す。必要なchangeがなければ、対応するOpenSpecスキルで仕様と出典を準備する。未回答のブロッキング事項があれば、その実装を止める。`docs/dev/` に書く開発の仕組みだけの変更は、AGENTS.mdの例外に従いchangeを作らずに進める。
3. **小さく実装する**：tasksの順に実装し、タスクごとにコミットする。1日以内のマージを目安にPRを分割する。Requirementに対応するID付きテストを残し、公開APIやJSONを変えるときは利用側も同じ変更単位で追従させる。
4. **検証してレビューする**：`pnpm -s verify --change <change-id> --done`、tasksの完了、Requirementとテストの対応を確認する。未完了changeの一部を出すPRでは、その範囲の検証と残作業を明記し、change全体の完了を宣言しない。独立レビューはAGENTS.mdの上限内で行う。
5. **取り込んで受け入れる**：対応Issueを参照してPRを作る。マージ対象headの必須CIが成功し、重大な指摘が解消し、承認範囲内ならマージする。Issue全体の受入条件を満たしたときだけcloseする。一部の実装では `Refs #番号` とし、親Issueを自動closeさせない。完了changeの仕様反映とarchiveは、対応スキルの手順で行う。
6. **記録して次へ進む**：各Issueに成果・検証・未決事項・次の作業を反映する。作業記録は適用されるAGENTS.mdに従い、その作業のPRに含める。日程への影響と判断事項は #121 にまとめる。CI待ち・回答待ちの間は、担当上限内で別の着手可能な作業へ進む。すべて待ちなら理由と再開条件を残す。

承認や権限が不足する操作は、その操作だけを保留する。通常の実装・検証のたびに同じ承認を求め直さない。既存のテストや設定を緩めて期限に合わせない。

## 期限に間に合わせるための確認

#121の段階別目標を基準にする。11月2日に最初の実装単位の実績で残工数を再評価し、11月13日を機能追加の締切、14〜16日を導入確認と修正に使う暫定目標とする。日程の達成を保証するものではなく、遅延時は影響と対策を #121 に記録する。

毎日の確認では、受入できた成果、段階の出口までの残作業、依存・CI・判断の待ち時間、次の確認点を見る。Issue完了件数は補助指標とし、工数や機能完成度の割合に読み替えない。仕様上必要なCIの修理を優先しつつ、追加の高速化は初回配布の実装と比較して優先順位を決める。

初回配布の判定には段階1〜5、A23の一周、別リポジトリへの導入検証を含める。公開サービスなどの利用準備と、人が判断できる時間も早めに確認する。公開・リリースは適用される個別承認を経て実行する。
