# エージェントの分担と共通原則

この文書はLoomake自身を開発するエージェントの工程分担と、独立した調査・レビューの原則を定める。共通原則の版は4とする。[AGENTS.md](../../AGENTS.md)から参照し、Claude CodeとCodexに同じ原則を適用する。

規約の置き場所は次のとおりで、この文書には再掲しない。

- 仕様の正、工程の 3 段階（L1 文書・L2 試験・CI・開発基盤・L3 製品コード）、完了の定義、禁止事項、報告の形：[AGENTS.md](../../AGENTS.md)
- 承認の範囲、人の操作 4 項目、同時本数、レビューの回数とマージ条件：[ADR 0006](../adr/0006-standing-approval-for-autonomous-delivery.md)
- 管理役の手順（担当の割り当て、Opus への依頼、マージと証跡、週次集計、archive）：[delivery スキル](../../.agents/skills/delivery/SKILL.md)

## 1. 適用範囲

工程分担は `$delivery` 経由かどうかにかかわらず、Loomake自身のすべての開発作業に適用する。どの工程が要るかは、AGENTS.md 2 章の段階で決める。

ここで定めるのは開発時の運用であり、モデルを自動選択する製品機能ではない。CLI、公開スキーマ、配布するテンプレート、依存パッケージ、CIの判定処理は変更しない。利用者へ配る仕組みにするときは、OpenSpecのchangeを作り、仕様ゲートを通してから実装する。

## 2. 工程ごとの担当

既定の流れは **Opusが設計 → Codexが実装 → 別の新しいOpusセッションが独立レビュー** とする。難しい不具合ではCodexが先に調査するが、設計はOpusが担当する。モデルの評価は課題や版で変わるため、「GPTは論理、Claudeは発想」のような固定的な能力分類や、特定モデルには解決不能という断定を根拠にしない。

| 工程 | 通常の機能開発 | 難しいバグ・エッジケース |
|---|---|---|
| 先行調査 | Opusが設計と同じセッションで目的・範囲を調べる | Codexが再現条件・観測事実・原因仮説を整理する |
| 独立調査 | 既定では追加しない | OpusがCodexの仮説を見ずに調べ、見解を先に保存する |
| 設計 | Opusが受入条件・確認方法・変更対象を定める | 独立調査を担当したOpusが両者の見解を比較し、原因と修正方針を設計する |
| 実装・修正 | Codex | Codex |
| 独立レビュー | 設計・実装とは別の新しいOpusセッション（回数は ADR 0006） | 同左 |
| 品質判定 | 既存のverifyとCIによる証跡の確認 | 同左 |

実装前に、選んだ経路と理由をPRまたは作業記録に書く。再現が難しい不具合、境界値や実行順序に依存する不具合、修正後も同じ失敗を繰り返す場合は、難しいバグの経路を選ぶか切り替える。経路を変えても実施済みの調査・試行・レビューの履歴は保持する。

担当を指定するときは、実行ツールとモデルを分ける。Claude Codeは実行ツール、Opusはモデルの指定である。Opusの利用は実行結果に含まれる実際のモデル識別子で確認し、自己申告や設定値だけを根拠にしない。識別子が不明、別モデルへの切り替わり、認証・権限・利用上限による失敗があれば、その工程は未実施とし、理由を記録して、その工程を待つ作業だけを保留する。指定モデルが使えないとき、工程を省略・代替できるのは利用者が明示的に承認した範囲に限る。誤字修正など、振る舞いを変えず受入条件が明確な作業では、既存の設計成果物を再利用してよい。

### CodexからOpusへ依頼する

管理役のCodexは、利用者に追加のプロンプト入力を求めず、依頼ファイルを作って[deliveryの補助スクリプト](../../.agents/skills/delivery/scripts/ask-opus.mjs)を実行する。依頼の内容と上限は delivery スキルのテンプレートに従う。依頼ファイルと検証資料は専用worktreeの `.loomake/` 配下へ置き、作業ツリーの外へ解決されるパスやシンボリックリンクは起動前に拒否する。

```sh
node .agents/skills/delivery/scripts/ask-opus.mjs \
  --role design --request .loomake/design-request.md --head <40桁の対象SHA>
```

`$delivery` を使わずClaude Codeが本体として作業する場合も、実装・修正はCodexへ委譲する。Claude Codeが使えることと、指定したOpusの工程が成功したことを区別し、Codexのモデル設定を変えてOpusとして扱わない。同じモデルの別セッションによるレビューを、異なるモデルのレビューと報告しない。

`--role` は `design`、`second-opinion`、`review` のいずれか。難しいバグの独立調査には `second-opinion` を使い、先行担当の仮説や推奨修正を依頼に含めない。独立調査から設計を同じ担当が続ける既定は維持する。PR #152 の AUTO-152-02（独立調査の保存成果物を別の新規セッションへ渡す案）は、規則の変更が決まるまで適用しない。スクリプトは毎回新しいセッションIDを作り、`--resume` や `--continue` を使わない。既存のClaude認証をそのまま使い、APIキーの追加や認証設定の書き換えは行わない。

起動時は `--model opus`、読取ツールのRead/Glob/Grep、`Read(./**)` の範囲付き許可、`permissions.blockReadsOutsideWorkingDirectories:true`、hook無効、自動メモリ無効、MCPなしを固定する。[Claude公式の読取拒否設定](https://code.claude.com/docs/en/settings-reference#permissions-blockreadsoutsideworkingdirectories)は2.1.257以降が必要。Windowsのnpm版 `claude.cmd` は `shell:false` で起動できないため未対応とし、未実施を返す。時間上限は既定20分で、`--timeout-min` に1〜60の整数を指定できる。stdoutは8MiB、stderrは64KiBを上限とし、上限到達は未実施として停止する。

標準出力は1行のJSON要約とし、成果物はGitの除外対象である `.loomake/claude/<session-id>/` へ保存する（`request.md`、`events.jsonl`、`stderr.txt`、`result.md`、`manifest.json`）。生ログには入力やコードが含まれるため、そのまま公開しない。終了コード0かつ `ok:true` の結果だけを実施済みとして扱う。開始情報のモデルとすべてのassistantイベントの応答モデルがOpusであること、権限拒否0件、読取専用ツールとMCPなしを確認できなければ、終了コード1で未実施を返す。引数の誤りは終了コード2とする。管理役はセッションIDと結果（重大・軽微・情報の件数）を PR 本文の証跡ブロックへ転記する。

## 3. すべての担当が守る4つの原則

### 実装前に前提を確かめる

目的、対象範囲、対象外、前提、不明点、受入条件を整理する。複数の解釈で外部の振る舞いや許可範囲が変わる場合は、黙って選ばず確認事項にする。単純な案で条件を満たせるなら、その案を示す。仕様を変える必要がある場合は実装を止め、changeへ反映する提案を行う。

### 必要な実装を単純に保つ

要求されていない機能、将来のためだけの設定、不要な依存や抽象化を加えない。行数の少なさだけで評価せず、読みやすさ、責務、依存、保守負担を確認する。実際に起こり得る異常系の処理や、仕様上必要な安全策は残す。

### 原因解消に必要な箇所を変更する

無関係な整形、コメントの書き換え、リファクタリング、既存の未使用コードの削除を混ぜない。今回の変更で不要になったコードは削除する。修正に必要な関連箇所は変更し、その理由を説明する。各差分のまとまりを要件または不具合に対応付け、無関係な改善は別のIssueにする。

### 検証可能な目標で進める

作業と確認方法を対にして計画する。バグ修正では原則として、修正前に失敗し、修正後に成功する回帰テストを残す。再現できない場合は理由、調べた条件、代替証跡、残る不確実性を記録し、再現できたと報告しない。振る舞いを変えない文書修正には、リンクや記述の確認など変更に合った検証を選ぶ。

## 4. 独立した調査とレビュー

セカンドオピニオンの担当には、最初に仕様、対象コミット、コード、再現手順、入力、観測ログを渡す。先行担当の結論や推奨修正は渡さず、独立した見解を先に保存する。その後で仮説を比較し、合意点と相違点、相違を区別できる検証を記録する。

独立レビューは、設計・実装を担当したセッションから分ける。受入条件、最新の差分、対象コミットと検証結果を渡し、要件との一致、過剰設計、無関係な変更、境界条件、テストの弱体化を確認する。必要な背景説明は参照してよいが、実装担当の完了宣言を合格根拠にしない。レビューした head とマージ対象 head の対応は、PR 本文の証跡ブロックに残す。古い head のレビューを、新しい head のレビュー済みとは扱わない。回数やモデル間の意見の一致だけで合格にしない。

## 5. 分担の評価と製品への展開

利用者が指定した既定の分担は、同じ課題群に対する単一モデルの方式と比較して評価する。比較結果だけで既定を切り替えず、分担を変えるときは利用者の明示指示に従う。修正成功率、重大な見逃し、回帰、所要時間、採用された修正あたりの費用、人の作業時間を記録する。比較数が少ない段階でモデル全般の優劣を断定しない。

利用者向けに展開するときは、次の順序で別changeを作る。

1. 工程別の担当と2つの経路を明示設定できる実行契約、Claude CodeとCodexのアダプターを定義する。
2. 対象コミット、実際のモデル、適用原則の版、引き継ぎ成果物を証跡へ接続する。既存の再開・停止・予算管理を再利用する。
3. 計測結果をもとに切り替え条件を決め、自動切り替えと機械的な検証を追加する。

パッケージの責務は、coreが共通形式、runnerが実行と再開、traceが対応関係と証跡、kitが検証、CLIが操作と表示を受け持つ。新しいパッケージや常駐サービスの追加は前提にしない。この順序は実装計画であり、公開形式やコマンドの追加を確定するものではない。
