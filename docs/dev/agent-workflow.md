# エージェントの分担と共通原則

この文書はLoomake自身を開発するエージェントの作業手順を定める。共通原則の版は3とする。[AGENTS.md](../../AGENTS.md)から参照し、Claude CodeとCodexに同じ原則を適用する。CLAUDE.mdは既存どおりAGENTS.mdを参照し、本文を重複させない。

工程ごとに担当を分け、各担当が検証できる成果物を残す。モデルの評価は課題や版で変わるため、以下の分担は利用者が指定した既定の工程とし、評価結果は改善の材料として記録する。「GPTは論理、Claudeは発想」のような固定的な能力分類や、特定モデルには解決不能という断定を根拠にしない。

## 1. 適用範囲

工程分担は`$delivery` 経由かどうかにかかわらず、Loomake自身のすべての開発作業に適用する。誤字修正などの例外は2章に定める。

ここで定めるのは開発時の運用であり、モデルを自動選択する製品機能ではない。CLI、公開スキーマ、配布するテンプレート、依存パッケージ、CIの判定処理は変更しない。利用者へ配る仕組みにするときは、OpenSpecのchangeを作り、仕様ゲートを通してから実装する。

仕様ゲートと完了条件を維持し、Opus 最終レビューは指摘ゼロまで回数上限なしで繰り返す。承認範囲は [ADR 0006](../adr/0006-standing-approval-for-autonomous-delivery.md) に従う。確認事項はおすすめ案で回答し、仮定は管理役が理由を添えて承認して trace と PR へ記録する。既存仕様から判断できる技術的な選択は、調査・検証と独立レビューで解消し、同じ承認を聞き直さない。

## 2. 工程ごとの担当

既定の流れは **Opusが設計 → Codexが実装 → Opusが最終レビュー** とする。難しい不具合ではCodexが先に調査するが、設計はOpusが担当する。

| 工程 | 通常の機能開発 | 難しいバグ・エッジケース |
|---|---|---|
| 先行調査 | Opusが設計と同じセッションで目的・範囲を調べる | Codexが再現条件・観測事実・原因仮説を整理する |
| 独立調査 | 既定では追加しない | OpusがCodexの仮説を見ずに調べ、見解を先に保存する（独立調査として記録） |
| 設計 | Opusが受入条件・確認方法・変更対象を定める | 独立調査を担当したOpusが両者の見解を比較し、原因と修正方針を設計する |
| 実装・修正 | Codex | Codex |
| 最終レビュー | 設計・実装とは別の新しいOpusセッション（指摘ゼロまで繰り返す） | 設計・実装とは別の新しいOpusセッション（指摘ゼロまで繰り返す） |
| 品質判定 | 既存のverifyとCIによる証跡の確認 | 既存のverifyとCIによる証跡の確認 |

通常経路で実装前の設計レビューを追加する場合は、独立調査や最終レビューと分けて実施履歴に記録する。設計そのものの作成と、設計に対する追加の評価は区別する。

実装前に、選んだ経路と理由をPRまたは作業記録に書く。再現が難しい不具合、境界値や実行順序に依存する不具合、修正後も同じ失敗を繰り返す場合は、難しいバグの経路を選ぶか切り替える。切り替えるときは、失敗した試行と次に区別したい仮説を残す。経路を変えても実施済みの調査・試行・レビューの履歴は保持する。

担当を指定するときは、実行ツールとモデルを分ける。Claude Codeは実行ツール、Opusはモデルの指定である。Codexも、利用した実行ツールと実際のモデル識別子を記録する。識別子を取得できなかった場合は不明と書き、推測で補わない。

指定モデルが利用できない場合は、その工程を未実施として残す。Opusの設計がなければ実装へ進まず、Opusの最終レビューがなければマージしない。当該工程の代替を利用者が明示的に承認した場合だけ、代替理由と独立性の制約を記録して進める。その場合もOpusの工程を実施したとは報告しない。同じモデルの別セッションによるレビューを、異なるモデルのレビューと報告しない。異なるモデルによるレビューが個別の受入条件なら、代替では達成扱いにしない。

Opusの指定だけで実施済みとは扱わない。実行結果または実行ツールのセッション情報に含まれる、実際のモデル識別子でOpusの利用を確認する。セッションIDは工程の独立性を区別する記録とし、IDだけでモデルを判定しない。成果物・実際のモデル・セッション・対象コミットを記録し、モデルの自己申告や設定値だけを根拠にしない。Opusの識別子が不明、別モデルへの切り替わり、認証・権限・利用上限による失敗がある場合は、状態を未実施とし、その理由を記録し、その工程を待つ作業だけを保留して独立した作業へ進む。Codexのモデル識別子を取得できない場合も不明と記録し、推測で補わない。

工程の状態は「実施済み」「未実施」「再利用（元の成果物・対象）」「省略（適用する規定または人の承認元）」「代替（人の承認元）」で記録する。モデル未確認や実行失敗は未実施に含め、単に未確認とだけ書いて次へ進めない。

誤字修正など、振る舞いを変えず受入条件が明確な作業では、全工程を別モデルで実行する必要はない。既にOpusが設計し、受入条件が変わらない軽微な修正では、その設計成果物を参照して再利用できる。この例外以外の工程省略や担当の代替は、利用者が明示した範囲に限る。省略・再利用した工程、対象と理由をPRに残し、必要な検証と既存の承認条件は維持する。

### CodexからOpusへ依頼する

`$delivery` の管理役はCodexとし、設計と最終レビューをClaude CodeのOpusへ依頼する。

`$delivery` を使わずClaude Codeが本体として作業する場合も、実装・修正はCodexへ委譲する。Claude Codeの本体は設計成果物をCodexへ渡し、その差分と検証結果を設計とは別の新しいOpusセッションへ最終レビューとして渡す。Codexを利用できない場合は実装を未実施として止め、担当の代替には利用者の明示承認を得る。

Claude Codeが使えることと、指定したOpusの工程が成功したことを区別する。Codexのモデル設定を変えてOpusとして扱わない。

管理役のCodexは、利用者に追加のプロンプト入力を求めず、依頼ファイルを作って[deliveryの補助スクリプト](../../.agents/skills/delivery/scripts/ask-opus.mjs)を実行する。依頼には仕様・対象コミット・AGENTS.md・この文書と必要な資料への参照を含め、最初に規約を読むよう明記する。設定ソースを無効にした起動で、規約が自動で読み込まれるとは扱わない。作業の対象を専用worktreeでコミットし、依頼ファイルや検証資料はそのworktreeの `.loomake/` 配下へ用意する。依頼ファイルと `.loomake/` の実パスを確認し、作業ツリーの外へ解決されるパスやシンボリックリンクは起動前に拒否する。成果物の保存先も `.loomake/` 内であることとGitの除外対象であることを、ディレクトリ作成前に確認する。

```sh
node .agents/skills/delivery/scripts/ask-opus.mjs \
  --role design --request .loomake/design-request.md --head <40桁の対象SHA>
```

`--role` は `design`、`second-opinion`、`review` のいずれか。難しいバグの独立調査には `second-opinion` を使い、先行担当の仮説や推奨修正を依頼に含めない。最終レビューは `review` で別途起動する。工程をまたぐときは保存した成果物を次の依頼へ渡す。独立調査から設計を同じ担当が続ける既定は維持する。工程の分担を変更する案は規則の変更として #121 で `@rrr-xxx` に依頼する。PR #152 の AUTO-152-02（独立調査の保存成果物を別の新規セッションへ渡す案）は、規則の変更が決まるまで適用しない。スクリプトは毎回新しいセッションIDを作り、`--resume` や `--continue` を使わない。既存のClaude認証をそのまま使い、APIキーの追加や認証設定の書き換えは行わない。

起動時は `--model opus`、読取ツールのRead/Glob/Grep、`Read(./**)` の範囲付き許可、`permissions.blockReadsOutsideWorkingDirectories:true`、hook無効、自動メモリ無効、MCPなしを固定する。[Claude公式の読取拒否設定](https://code.claude.com/docs/en/settings-reference#permissions-blockreadsoutsideworkingdirectories)は2.1.257以降が必要で、本補助の実機確認はLinuxのClaude Code 2.1.308で行った。作業ツリー外へのRead/Grep/Globと、外向きシンボリックリンクの読取を拒否する。Claude自身が読み込む規約・スキル等まで遮断するOSの隔離ではない。Windowsのnpm版 `claude.cmd` は `shell:false` で起動できないため未対応とし、未実施を返す。自動メモリの無効化はこの子プロセスに限り、利用者の設定ファイルを書き換えない。シェルを介さず依頼を標準入力で渡し、時間と出力の上限で停止する。時間上限は既定20分で、`--timeout-min` に1〜60の整数を指定できる。この上限は各Claude呼び出しに適用し、Goal 全体の利用上限や最終レビューの反復条件を置き換えない。

stdoutはverboseのツール結果を含めて8MiB、stderrは64KiBを上限とする。子プロセスからの無制限な出力で管理役のメモリを使い切らないための保守的な上限で、大きな差分のレビューが収まる保証はない。上限到達は未実施として停止し、切り詰めた結果を合格にしない。

標準出力は1行のJSON要約とし、依頼や回答の本文を含めない。成果物はGitの除外対象である `.loomake/claude/<session-id>/` へ保存する。`request.md`、`events.jsonl`、`stderr.txt`、`result.md`、`manifest.json` を参照し、管理役が必要な根拠をPRへ転記する。生ログには入力やコードが含まれるため、そのまま公開しない。

終了コード0かつ `ok:true` の結果だけを実施済みとして扱う。実行前後のheadと未コミット変更、開始・終了のセッションID、実際のOpusモデル、結果の成功、権限拒否0件、読取専用ツールとMCPなしを確認できなければ、終了コード1で未実施を返す。引数の誤りは終了コード2とする。モデルの自己申告や終了コードだけで合格にせず、回答内容と受入条件も確認する。設定した `opus` の解決先は環境と版で変わるため、実際の識別子をPRへ記録する。開始情報のモデルと、すべてのassistantイベントの応答モデルがOpusであることを要求する。assistantの応答がない場合や、本体の応答に別モデルが含まれる場合は未実施とする。modelUsageにはOpusの実行記録が1つ以上必要で、補助処理の別モデルは許可し、名前と入力・出力トークン数をJSON要約とmanifestのhelperModelsへ記録する。本体の応答で確認できたモデルはresponseModelsへ記録する。

スクリプトは設計やレビューを実行する補助であり、承認や品質合格を自動で与えない。Opus 評価の実施履歴と、別枠の自動 Codex レビューの予定は管理役が起動前に確認する。ログインや利用枠が使えない場合は、その工程を未実施として #121 等の進行管理に残し、独立して進められる作業を続ける。

### 自律配布の承認範囲

[ADR 0006](../adr/0006-standing-approval-for-autonomous-delivery.md) により、マージ対象 head の必須 CI・自動 Codex レビュー・独立した Opus 最終レビューが揃い、Opus 最終レビューの指摘がゼロで自動 Codex の重大な未解決指摘もない PR は管理役がマージする。開発の仕組みの変更も管理役が行う。承認範囲、工程分担、ゲート、完了条件、禁止事項、レビューの反復条件を変える場合は、文書の配置先にかかわらず規則の変更として扱う。工程の代替や省略について、この文書が明示承認を求める場合も同様とする。確認事項へのおすすめ回答と仮定の承認は、根拠と決定者を trace と PR に記録する。確認事項の回答者は「利用者（ADR 0006 の包括承認）」と記録する。

テストの弱体化・skip・実装に合わせた期待値変更、品質設定の緩和、完成範囲の縮小は承認経路のない禁止とする。必要性が生じたら Issue に記録し、その変更は行わず独立した次の作業へ進む。費用の上限は設けない。Opus 最終レビューは指摘ゼロまで回数上限なしで繰り返す。

人の操作が必要なのは npm 公開・public 化・リリース・規則の変更の 4 つだけとし、対象と検証結果を具体化して #121 にコメントし、`@rrr-xxx` を呼ぶ。ChatGPT アプリへの通知設定を確認し、設定できなければ理由と代替を報告する。ADR 0006（2026-10-30）で指定された規約更新は承認済み。同時 change の上限は全セッション合計 4 本とし、配布 3 枠・品質計画 1 枠を基本に、既存の引き継ぎ対象は終了した枠からこの配分へ移す。

### ChatGPT アプリへの通知

人の操作を依頼するときは #121 のコメントで `@rrr-xxx` を呼び、対象と検証結果、必要な操作をまとめる。[OpenAI の通知設定](https://learn.chatgpt.com/docs/notifications)によると、ChatGPT の push はアカウントの Settings > Notifications とアプリ・OS の通知許可で管理する。Codex の [`notify`](https://learn.chatgpt.com/docs/config-file/config-advanced#notifications) は外部プログラムを起動する設定であり、ChatGPT アプリの push を直接有効にする設定としては使わない。

2026-10-30 の実行環境では、ChatGPT のアカウント側通知設定と端末の通知許可を変更するツールがないため、push は設定できていない。代替として #121 のメンションとこの会話への報告を残す。指定された `@rrr-xxx` は 2026-10-30 の GitHub API 照会で 404 となり、存在を確認できていない。指定表記は変更せず、GitHub の通知先・メンション先アカウントへの到達も、この環境で確認していない限り到達済みとは報告しない。Codex の端末通知だけを設定して ChatGPT への通知を設定済みとは扱わない。

## 3. すべての担当が守る4つの原則

### 実装前に前提を確かめる

目的、対象範囲、対象外、前提、不明点、受入条件を整理する。複数の解釈で外部の振る舞いや許可範囲が変わる場合は、黙って選ばず確認事項にする。単純な案で条件を満たせるなら、その案を示す。仕様を変える必要がある場合は実装を止め、changeへ反映する提案を行う。

### 必要な実装を単純に保つ

要求されていない機能、将来のためだけの設定、不要な依存や抽象化を加えない。行数の少なさだけで評価せず、読みやすさ、責務、依存、保守負担を確認する。実際に起こり得る異常系の処理や、仕様上必要な安全策は残す。

### 原因解消に必要な箇所を変更する

無関係な整形、コメントの書き換え、リファクタリング、既存の未使用コードの削除を混ぜない。今回の変更で不要になったコードは削除する。修正に必要な関連箇所は変更し、その理由を説明する。各差分のまとまりを要件または不具合に対応付け、無関係な改善は別のIssueにする。

### 検証可能な目標で進める

作業と確認方法を対にして計画する。バグ修正では原則として、修正前に失敗し、修正後に成功する回帰テストを残す。再現できない場合は理由、調べた条件、代替証跡、残る不確実性を記録し、再現できたと報告しない。振る舞いを変えない文書修正には、リンクや記述の確認など変更に合った検証を選ぶ。

## 4. 独立した調査とレビュー

セカンドオピニオンの担当には、最初に仕様、対象コミット、コード、再現手順、入力、観測ログを渡す。先行担当の結論や推奨修正は渡さず、独立した見解を先に保存する。その後で仮説を比較し、合意点と相違点、相違を区別できる検証を記録する。

最終レビューは、設計・実装を担当したセッションから分ける。受入条件、最新の差分、対象コミットと検証結果を渡し、要件との一致、過剰設計、無関係な変更、境界条件、テストの弱体化を確認する。必要な背景説明は参照してよいが、実装担当の完了宣言を合格根拠にしない。

最終レビューの対象コミットとマージ対象 head の対応を PR に記録する。Opus 最終レビューには回数の上限を設けず、指摘がゼロになるまで修正・検証・独立レビューを繰り返す。レビュー後に差分を変えた場合は、新しい head を新しいセッションで再レビューする。古い head のレビューを、新しい head のレビュー済みとは扱わない。

従来の Opus 評価合計による回数制限は撤廃する。設計、独立調査、設計レビュー、最終レビューの実施履歴は保持する。回数やモデル間の意見の一致だけで合格にしない。指摘がある head は、軽微なものも含めて指摘ゼロとは扱わない。

指摘ごとに、内容、対象箇所、対象 head、対応、同じ指摘の連続出現回数を PR に記録する。初回の指摘を 1 回目と数え、連続する最終レビューで 3 回目に同じ問題が出たら Issue に記録する。その問題が指摘されなかったレビューを挟んだら、連続回数は数え直す。Issue に記録した後も、修正・検証・レビューの往復を続ける。行番号や表現が変わっただけで別の指摘として回数をリセットしない。Issue への記録は未解決事項の追跡であり、指摘の解消やマージの許可にはしない。

GitHub の自動 Codex レビューは Opus と分けて、起動条件、実際の回数、対象 head、結果を記録する。重大な未解決指摘は修正・検証し、解消するまでマージしない。自動 Codex レビューで Opus の最終レビューを代替しない。自動レビューを含む開発の仕組みは、品質基準を維持して管理役が変更する。

マージは、対象 head の必須 CI・自動 Codex レビュー・指摘ゼロの独立した Opus 最終レビューが揃ったときに管理役が行う。認証・権限・利用上限でレビューを実行できない場合は、その PR を保留し、独立した次の作業へ進む。この回数上限の撤廃は、各呼び出しの時間・出力量の制限や Goal の利用上限を変更しない。

## 5. 引き継ぎと判定の記録

PRに次の情報をまとめる。既存のtraceやCI成果物にある内容はリンクで参照し、長いログを複製しない。traceの表には要点と参照先を置く。

| 記録 | 内容 |
|---|---|
| 対象 | change-idまたは文書変更の範囲、仕様の版、対象コミット |
| 担当 | 工程、実行ツール、モデル識別子、セッションの区別、共通原則の版 |
| 引き継ぎ | Opus設計の目的・範囲・対象外・前提・受入条件と確認方法・変更対象、設計元コミット、未決事項、成果物のリンク |
| 調査・判断 | 観測事実、前提、仮説、独立調査の結果、採用理由、未解決事項 |
| 検証 | 実行コマンドまたは手順、環境、結果、証跡へのリンク、対象コミット |
| 実行履歴 | 試行数、Opus 評価の回数・対象 head・指摘・同じ指摘の連続出現回数、自動 Codex の回数・head・結果、時間制限、停止理由。費用上限は設けない |

モデルの同意、原則を守ったという自己申告、テストの存在だけでは品質を保証しない。実行されていない検証や古いコミットの結果を、最新コミットの成功として扱わない。重大な未解決指摘がある場合は、必要な修正・検証と、規則変更の判断が必要かを管理役が明示する。

この手順の導入によって、既存のverifyに新しい自動判定が加わるわけではない。原則の適用状況はPRレビューで確かめ、機械的な品質判定は既存のゲートが扱う範囲で行う。証跡の適格性を自動で検査する機能が未接続の部分は、手動確認した内容と未確認の範囲を分けて記録する。

## 6. 分担の評価と製品への展開

利用者が指定した既定の分担は、同じ課題群に対する単一モデルの方式と比較して評価する。比較結果だけで既定を切り替えず、分担を変えるときは利用者の明示指示に従う。修正成功率、重大な見逃し、回帰、所要時間、採用された修正あたりの費用、人の作業時間を記録する。モデルの版、受入条件、実行環境、予算、試行回数をそろえ、同じ課題への繰り返しでは実行順の偏りを避ける。比較数が少ない段階でモデル全般の優劣を断定しない。

利用者向けに展開するときは、次の順序で別changeを作る。

1. 工程別の担当と2つの経路を明示設定できる実行契約、Claude CodeとCodexのアダプターを定義する。
2. 対象コミット、実際のモデル、適用原則の版、引き継ぎ成果物を証跡へ接続する。既存の再開・停止・予算管理を再利用する。
3. 計測結果をもとに切り替え条件を決め、自動切り替えと機械的な検証を追加する。

パッケージの責務は、coreが共通形式、runnerが実行と再開、traceが対応関係と証跡、kitが検証、CLIが操作と表示を受け持つ。新しいパッケージや常駐サービスの追加は前提にしない。この順序は実装計画であり、公開形式やコマンドの追加を確定するものではない。
