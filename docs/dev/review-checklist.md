# レビューのチェックリスト

レビュー（Opus・Codex）と CI、作業中の手戻りで見つかった問題のうち、試験では捕まえにくい種類を 1 行ずつ並べる。Opus に依頼する前の自己レビューでは、起草とは別のサブエージェントが Opus と同じ依頼文とこの一覧で確かめる（[delivery スキル](../../.agents/skills/delivery/SKILL.md)の「工程の担当と Opus への依頼」）。

Opus の指摘を直すときは、まず回帰試験で捕まえられるかを考える。試験に落とせない指摘はその修正 PR でこの一覧に 1 行足す。各行の末尾に出典の PR 番号を書く。

## 一覧

- 指摘を直したことで、別の検査を飛ばす抜け道ができていないか。例：tasks.md に完了したタスクがない change を `--spec-only` で検査する修正が、L2・L3 でも `--done` を避けられる道になっていた（#188）
- レビューや検証の担当が作った生成物が差分に混ざっていないか。例：`--help/audit.json` と `--help/audit.md` がコミットされていた（#188）
- 入力の読み取りで、上限を超えた入力が例外ではなく決められた誤りとして返るか。例：YAML のエイリアスの展開が上限を超えると例外を投げていた（#192、Codex 自動レビューの指摘）
- パスを比べる判定がシンボリックリンクで外れないか。例：macOS では `/var` が `/private/var` へのシンボリックリンクのため、一時ディレクトリから起動したスクリプトの直接実行の判定が外れ、出力なし・終了コード 0 で終わっていた（#190）
- REQ 番号がほかの Requirement と重複していないか。例：REQ-273 が 2 つの Requirement に付いていた（#188 の作業中に見つけた main の重複）
- 段階受入の規則は、利用者の明示承認・採用記録・関連規則の整合・main への反映が済むまで適用を禁じているか。各段を積み上げた最終 PR も、全累積差分と全要件を新しい独立レビューで確認できるか（#260）
