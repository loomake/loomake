# 0004 開発の技術スタックをいまのリポジトリのまま維持する

- 状態：採用
- 決めた日：2026-10-26
- 決めた人：利用者（PR #10 のコメント 6403295324 での回答。利用者の「Q-01〜03の回答して」という依頼に基づく方針選択）
- 出典：要件定義 v0.11.1 の 8 章、アーキテクチャ v2.5.3 の 6 章、WBS の W0-2、change `record-stack-and-versioning-decisions` の trace.md の Q-02（REQ-232）

## 決定

Loomake 自身の開発には、いまのリポジトリのとおり pnpm workspaces・Vitest・ESLint（typescript-eslint）・changesets を使い続ける。要件定義から順に、関連の文書をこれに合わせて直す。既存のテストと CI を別の道具に移すことより、C-001 の実装を優先する。

開発時の依存と、配布物の実行時依存は分けて扱う。この決定は開発時の道具だけを決め、配布物の実行時依存は [0003](0003-zod-as-core-runtime-dependency.md) と要件定義の NFR-01 で決める。

## 検討した選択肢

- **A：リポジトリに合わせる**：pnpm・Vitest・ESLint を使い続け、要件定義 8 章、アーキテクチャ 6 章・8 章、WBS の W0-2、`docs/overview.md` を直す。利点は、いまのテストと CI をそのまま使えること、既存の仕様（monorepo の「モノレポのパッケージ構成」は pnpm workspaces を、「changesets による公開準備」は changesets を定めている）と食い違わないこと。欠点は、テストの「依存ゼロ」（アーキテクチャ 6 章の理由欄）を手放すこと、正本の要件定義から直す手間がかかること
- **B：文書のとおりに移る**：npm workspaces・`node:test`・Biome に移る。利点は、開発時の依存が減り、要件定義とアーキテクチャを直さずに済むこと。欠点は、テストを書き直し、CI・lockfile・既存の仕様（monorepo）も変える必要があること。いま ESLint の型情報つきの規則（strictTypeChecked）で検査している内容を、Biome でどこまで保てるかも確かめる必要があること。利用者に見える変化はないこと

## 理由

- どちらを選んでも配布物の実行時依存は変わらず、NFR-01 の範囲には影響しない。変わるのは開発時の道具だけである
- B に移ると、テストと CI の書き直しに C-001 より前の時間を使うことになる
- Vitest は、Loomake が読むテストレポートの形式（`docs/compatibility.md` の「Vitest・Jest 形式の JSON」）でもあり、自分のリポジトリで使い続ける意味がある

## 適用範囲

- 対象は、Loomake 自身のリポジトリで使うパッケージ管理・テスト・lint と整形の道具
- アーキテクチャ 0.1・6 章の外部コマンドと静的指標に挙げた Biome は、案件側の静的指標を読むためのもので、Loomake 自身の lint とは別の話である。この ADR はそれを変えない
- 言語・ビルド・CLI・外部コマンドの呼び方（TypeScript strict、`tsc` のみ、ESM のみ、`parseArgs`、標準 `spawn`）は変えない

## 見直す条件

- Vitest・ESLint・pnpm のどれかの保守が止まったとき、または Node.js の対応版に追従しなくなったとき
- Node.js の標準機能（`node:test` など）で、いまのテストと検査の内容を保ったまま、開発時の依存を減らせると確かめられたとき
