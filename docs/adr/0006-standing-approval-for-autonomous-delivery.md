# 0006 自律配布の包括承認

- 状態：採用
- 決めた日：2026-10-30
- 決めた人：利用者
- 出典：2026-10-30 の本会話での `$delivery` 指示と、同日の後続指示（Opus 最終レビューの回数上限撤廃・指摘ゼロまでの反復を明示）。利用者が ADR 0006 自体への反映を指定したため、同日の決定を更新する。同日の利用者指定に従い、ファイル名と回答者表記を整合した。進行管理は [Issue #121](https://github.com/loomake/loomake/issues/121)

## 決定

Loomake の初回配布に向けた作業を、次の範囲で管理役へ包括承認する。今回指定された AGENTS.md、delivery スキル、agent-workflow.md の規約更新も承認済みとする。

- 確認事項はおすすめ案で回答し、選択肢・理由・決定・本 ADR を trace と PR に残す。回答者は「利用者（ADR 0006 の包括承認）」とする。
- 仮定は管理役が理由を添えて承認し、承認者を管理役と明記する。管理役の判断を利用者本人のレビューとして投稿しない。
- マージ対象 head の必須 CI・自動 Codex レビュー・設計と実装から独立した Opus 最終レビューが揃い、Opus 最終レビューの指摘がゼロで、自動 Codex レビューの重大な未解決指摘もない PR は、管理役がマージする。仕様ゲート・完了ゲート・要件対応テスト・tasks の完了は維持する。
- 開発の仕組みの変更は管理役が行う。ADR 0005 の範囲は change 不要とし、製品の仕様変更は引き続き change を通す。開発の仕組みの変更と、以下の規則の変更を区別する。
- テストを弱める・skip する・期待値を実装へ合わせること、品質設定を緩めること、完成範囲を縮めることは、承認経路のない禁止とする。必要性が生じたら Issue に記録し、その変更は行わず、独立した次の作業へ進む。秘密情報の記録も引き続き禁止する。
- 費用の上限を設けない。Opus 最終レビューにも回数の上限を設けず、新しい head に指摘ゼロが出るまで修正・検証・独立レビューを繰り返す。従来の Opus 評価合計による回数制限は撤廃する。同じ指摘が 3 回連続で再出現したら、その指摘を Issue に記録し、修正とレビューの往復は続ける。Issue への記録を解消やマージ許可とは扱わない。
- 人の操作が残るのは npm 公開・リポジトリの public 化・リリース・規則の変更の 4 つだけとする。必要な場合は、対象・検証結果・必要な操作を具体化して Issue #121 にコメントし、`@rrr-xxx` を呼ぶ。返答待ちには独立した作業を進める。
- 人への依頼時には ChatGPT アプリへ通知が届くよう Codex の設定を確認する。設定できない場合は理由と代替を報告し、通知を設定済み・到達済みとは扱わない。具体的な扱いは [agent-workflow](../dev/agent-workflow.md#chatgpt-アプリへの通知) に従う。
- 同時に進める change は全セッション合計 4 本までとし、配布に 3 枠、品質計画に 1 枠を配分する。品質枠は配布にも効く E3・E5・C2・C5 を優先し、同じファイルの実装を重複させない。既存の #157〜#159 は引き継ぎ対象として扱い、終了した枠からこの配分へ移す。

## 検討した選択肢

- A：上記の包括承認を記録し、管理役が判断と証拠を残して進める。判断待ちの時間を減らせる一方、管理役には承認範囲の確認と記録が必要となる。利用者は A を指定した。
- B：確認事項・仮定・マージごとに人の承認を待つ。判断を個別に確認できる一方、利用者の返信待ちで作業が止まる。

## 理由

利用者は初回配布を優先し、できるだけ早く自動で完成まで進めるよう指示した。品質基準と完成範囲を保ったまま判断を委任し、必要な人の操作を 4 種類に限定する。

## 適用範囲

Loomake 自身の初回配布に向けた開発、品質計画、PR と Issue の運用に適用する。AGENTS.md、delivery スキル、docs/dev/agent-workflow.md を本 ADR に合わせる。利用者に配るテンプレートや製品仕様は、この ADR だけでは変更しない。ツール・実行環境の権限制限を解除する決定でもない。

## 見直す条件

利用者が規則の変更を明示的に決定したときに、新しい ADR へ記録する。利用者が本 ADR 自体への反映を指定した場合は、本 ADR を更新し、出典に指示と日付を記録する。規則の変更が必要な場合は Issue #121 で `@rrr-xxx` に依頼する。包括承認の運用中にテストの弱体化・設定緩和・完成範囲の縮小を例外として認めない。
