# 0006 自律配布の包括承認

- 状態：採用
- 決めた日：2026-10-30（レビュー規則の改訂は 2026-10-31）
- 決めた人：利用者
- 出典：2026-10-30 の本会話での `$delivery` 指示と、同日の後続指示。利用者が ADR 0006 自体への反映を指定したため、同日の決定を更新する。同日の利用者指定に従い、ファイル名と回答者表記を整合した。2026-10-31 の改訂は実装ワークフローの組み替え計画（`.loomake/handoff/rebuild-plan-2026-10-31.md`、リポジトリ管理外）の 4 章で、利用者がおすすめ案をすべて承認したことによる。2026-10-31 に、利用者の指示（「実装して」）でメンションの宛先を正しいログイン名に直した。進行管理は [Issue #121](https://github.com/loomake/loomake/issues/121)

## 決定

Loomake の初回配布に向けた作業を、次の範囲で管理役へ包括承認する。今回指定された AGENTS.md、delivery スキル、agent-workflow.md の規約更新も承認済みとする。

- 確認事項はおすすめ案で回答し、選択肢・理由・決定・本 ADR を trace と PR に残す。回答者は「利用者（ADR 0006 の包括承認）」とする。
- 仮定は管理役が理由を添えて承認し、承認者を管理役と明記する。管理役の判断を利用者本人のレビューとして投稿しない。
- マージの条件は下の「レビュー規則（2026-10-31 改訂）」に従う。仕様ゲート・完了ゲート・要件対応テスト・tasks の完了は維持する。
- 開発の仕組みの変更は管理役が行う。ADR 0005 の範囲は change 不要とし、製品の仕様変更は引き続き change を通す。開発の仕組みの変更と、以下の規則の変更を区別する。
- テストを弱める・skip する・期待値を実装へ合わせること、品質設定を緩めること、完成範囲を縮めることは、承認経路のない禁止とする。必要性が生じたら Issue に記録し、その変更は行わず、独立した次の作業へ進む。秘密情報の記録も引き続き禁止する。
- 費用の上限を設けない。
- 人の操作が残るのは npm 公開・リポジトリの public 化・リリース・規則の変更の 4 つだけとする。必要な場合は、対象・検証結果・必要な操作を具体化して Issue #121 にコメントし、`@rrr-www` を呼ぶ。返答待ちには独立した作業を進める。AI のレビュー・CI の成功・マージ・返答がないことを、利用者の新しい承認とは扱わない。
- 人への依頼時には ChatGPT アプリへ通知が届くよう Codex の設定を確認する。設定できない場合は理由と代替を報告し、通知を設定済み・到達済みとは扱わない。2026-10-30 の実行環境では ChatGPT のアカウント側通知設定を変更するツールがなく、push は設定できていない。代替として #121 のメンションと会話への報告を残す。メンションの宛先は `@rrr-www` とする。2026-10-30 の GitHub API 照会が 404 になったのは、宛先のログイン名を `rrr-xxx` と誤っていたためで、2026-10-31 に直した。ただしエージェントは利用者のアカウントで投稿するので、どちらの宛先でも GitHub の通知は利用者に届かない。メンションは依頼の目印として残し、通知は開発機の Claude セッションが 1 時間ごとに未対応の依頼を確かめて、Remote Control の接続中に Claude モバイルアプリへ push で送る。到達を確認していない限り、到達済みとは報告しない。
- 同時に進める change は全セッション合計 4 本までとし、配布に 3 枠、品質計画に 1 枠を配分する。品質枠は配布にも効く E3・E5・C2・C5 を優先し、同じファイルの実装を重複させない。既存の #157〜#159 は引き継ぎ対象として扱い、終了した枠からこの配分へ移す。

### レビュー規則（2026-10-31 改訂）

2026-10-30 の決定にあった「Opus 最終レビューに回数の上限を設けず、指摘ゼロまで繰り返す」と「自動 Codex レビューの重大な未解決指摘がないこと」をマージ条件から外し、次に置き換える。

- 独立 Opus レビューの回数は工程の段階（AGENTS.md 2 章）で決める。L1 文書では行わない。L2 試験・CI・開発基盤では 1 回とし、指摘があれば修正後に 1 回だけ再レビューする。L3 製品コードでは最大 2 往復とする。
- 「往復」は指摘を修正して再レビューを受けるまでを 1 往復と数え、初回のレビューは数えない。回数を使い切ったあとに head が変わったときは、差分が指摘の修正だけなら再レビューは要らない。それ以外の変更が入れば往復を 1 つ消費する。
- マージ条件は段階ごとに次のとおり。軽微な指摘は Issue に記録すればマージしてよい。
  - L1：マージ対象 head の必須 CI の成功。
  - L2：必須 CI の成功と、独立 Opus レビュー 1 回（修正後の再レビュー 1 回まで）で重大な指摘がゼロ。レビューは同じ head のものか、最後のレビュー以降の差分が指摘の修正だけである head のものとする。
  - L3：必須 CI の成功、`verify --done` の成功、独立 Opus レビューで重大な指摘がゼロ（最大 2 往復）。レビューの head の扱いは L2 と同じ。
  - 「差分が指摘の修正だけ」の判定は管理役が行い、証跡ブロックに reviewed-head と head の両方を書く。
- レビューした head とセッション ID、モデル識別子、重大・軽微・情報の件数は PR 本文の証跡ブロックに残す。
- Codex 自動レビューはどの段階でもマージ条件に入れず、参考として扱う。結果は証跡ブロックに記録する。
- 回数を使い切っても重大な指摘が残るときは、L2・L3 とも PR を分割するか、Issue に記録して人がマージ可否を決める。

## 検討した選択肢

- A：上記の包括承認を記録し、管理役が判断と証拠を残して進める。判断待ちの時間を減らせる一方、管理役には承認範囲の確認と記録が必要となる。利用者は A を指定した。
- B：確認事項・仮定・マージごとに人の承認を待つ。判断を個別に確認できる一方、利用者の返信待ちで作業が止まる。

レビュー規則の改訂では次を比べた。

- A：L2 は 1 回、L3 は 2 往復を上限にし、残った軽微な指摘は Issue 化でマージ可とする。利用者は A を選んだ。
- B：上限なしを維持する。PR #179 のように 9 時間を超えても終わらないレビューが続く。

## 理由

利用者は初回配布を優先し、できるだけ早く自動で完成まで進めるよう指示した。品質基準と完成範囲を保ったまま判断を委任し、必要な人の操作を 4 種類に限定する。

レビュー規則を改訂したのは、独立 Opus レビューは実際に指摘を出している一方で、「指摘ゼロまで無制限」の規則が 18 行の文書 PR にも 5 時間以上かかる工程を生んでいたためである。Codex 自動レビューは 2026-10-29 以降の 8 本の PR で指摘がなく、マージ条件に数える根拠がない。

## 適用範囲

Loomake 自身の初回配布に向けた開発、品質計画、PR と Issue の運用に適用する。AGENTS.md、delivery スキル、docs/dev/agent-workflow.md を本 ADR に合わせる。利用者に配るテンプレートや製品仕様は、この ADR だけでは変更しない。ツール・実行環境の権限制限を解除する決定でもない。

## 見直す条件

利用者が規則の変更を明示的に決定したときに、新しい ADR へ記録する。利用者が本 ADR 自体への反映を指定した場合は、本 ADR を更新し、出典に指示と日付を記録する。規則の変更が必要な場合は Issue #121 で `@rrr-www` に依頼する。包括承認の運用中にテストの弱体化・設定緩和・完成範囲の縮小を例外として認めない。Codex 自動レビューは、2 週間で指摘が 1 件も出なければ依頼自体をやめる。
