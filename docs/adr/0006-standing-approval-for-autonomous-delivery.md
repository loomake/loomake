## 決定

Loomake の初回配布に向けた作業を、次の範囲で管理役へ包括承認する。今回指定された AGENTS.md、delivery スキル、agent-workflow.md の規約更新も承認済みとする。

- 確認事項はおすすめ案で回答し、選択肢・理由・決定・本 ADR を trace と PR に残す。回答者は「利用者（ADR 0006 の包括承認）」とする。
- 仮定は管理役が理由を添えて承認し、承認者を管理役と明記する。管理役の判断を利用者本人のレビューとして投稿しない。
- マージの条件は下の「レビュー規則（2026-10-31 改訂）」に従う。仕様ゲート・完了ゲート・要件対応テスト・tasks の完了は維持する（仕様適合の修正は、change がないので、完了ゲートと tasks の代わりに「完成を早めるための規則変更」A の完了条件を使う）。
- 開発の仕組みの変更は管理役が行う。ADR 0005 の範囲は change 不要とし、製品の仕様変更は引き続き change を通す。開発の仕組みの変更と、以下の規則の変更を区別する。
- テストを弱める・skip する・期待値を実装へ合わせること、品質設定を緩めること、完成範囲を縮めることは、承認経路のない禁止とする（完成範囲については、2026-11-05 の利用者決定 B の範囲だけを除く）。必要性が生じたら Issue に記録し、その変更は行わず、独立した次の作業へ進む。秘密情報の記録も引き続き禁止する。
- 費用の上限を設けない。
- 人の操作が残るのは npm 公開・リポジトリの public 化・リリース・規則の変更の 4 つだけとする。必要な場合は、対象・検証結果・必要な操作を具体化して Issue #121 にコメントし、`@rrr-www` を呼ぶ。返答待ちには独立した作業を進める。AI のレビュー・CI の成功・マージ・返答がないことを、利用者の新しい承認とは扱わない。
- 人への依頼時には ChatGPT アプリへ通知が届くよう Codex の設定を確認する。設定できない場合は理由と代替を報告し、通知を設定済み・到達済みとは扱わない。2026-10-30 の実行環境では ChatGPT のアカウント側通知設定を変更するツールがなく、push は設定できていない。代替として、#121 への依頼コメント（メンションを目印として付ける）と会話への報告を残す。
- メンションの宛先は `@rrr-www` とする。2026-10-30 の GitHub API 照会が 404 になったのは、宛先のログイン名を `rrr-xxx` と誤っていたためで、2026-10-31 に直した。ただしエージェントは利用者のアカウントで投稿するので、どちらの宛先でも GitHub の通知は利用者に届かない。通知は、開発機の Claude セッションが 1 時間ごとに未対応の依頼を確かめ、Claude モバイルアプリへ push で送る。この経路が動くのは、開発機の Claude セッションが起動していて Remote Control に接続している間だけで、セッションを閉じると止まり、1 時間ごとの確認は 7 日で期限が切れる。到達を確認していない限り、到達済みとは報告しない。
- 同時に進める change は全セッション合計 5 本までとし、配布に 4 枠、品質計画に 1 枠を配分する（2026-11-05 に 4 本から 5 本へ変更。経緯は下の「完成を早めるための規則変更」）。品質枠は配布にも効く E3・E5・C2・C5 を優先し、同じファイルの実装を重複させない。既存の #157〜#159 は引き継ぎ対象として扱い、終了した枠からこの配分へ移す。

### レビュー規則（2026-10-31 改訂）

2026-10-30 の決定にあった「Opus 最終レビューに回数の上限を設けず、指摘ゼロまで繰り返す」と「自動 Codex レビューの重大な未解決指摘がないこと」をマージ条件から外し、次に置き換える。

- 独立 Opus レビューの回数は工程の段階（AGENTS.md 2 章）で決める。L1 文書では行わない。L2 試験・CI・開発基盤では 1 回とし、指摘があれば修正後に 1 回だけ再レビューする。L3 製品コードでは最大 2 往復とする。
- 「往復」は指摘を修正して再レビューを受けるまでを 1 往復と数え、初回のレビューは数えない。回数を使い切ったあとに head が変わったときは、差分が指摘の修正だけなら再レビューは要らない。それ以外の変更が入れば往復を 1 つ消費する。
- マージ条件は段階ごとに次のとおり。軽微な指摘は Issue に記録すればマージしてよい。
  - L1：マージ対象 head の必須 CI の成功と、自己レビューで重大な指摘がゼロ（2026-11-02 利用者決定）。
  - L2：必須 CI の成功と、独立 Opus レビュー 1 回（修正後の再レビュー 1 回まで）で重大な指摘がゼロ。レビューは同じ head のものか、最後のレビュー以降の差分が指摘の修正だけである head のものとする。
  - L3：必須 CI の成功、`verify --done` の成功、独立 Opus レビューで重大な指摘がゼロ（最大 2 往復）。ただし「仕様適合の修正」（下の「完成を早めるための規則変更」A）は change がなく、`verify --done` の代わりに同節の完了条件を満たし、独立 Opus レビューは 1 回（修正後の再レビュー 1 回まで）とする。レビューの head の扱いは L2 と同じ。
  - 「差分が指摘の修正だけ」の判定は管理役が行い、証跡ブロックに reviewed-head と head の両方を書く。
- 独立 Opus へのレビュー依頼文は「変更差分 ＋ 変更した Requirement の ID 一覧 ＋ レビュアーが読むべきファイルの一覧（パス）」とする。Requirement の全文や呼び出し側の抜粋は依頼文に貼らない。レビュアーは Read・Glob・Grep で worktree 内のファイルを読める。200KiB の上限は差分にだけ掛け、差分が 200KiB を超えるときは PR を分ける（2026-10-31 利用者決定、quality-speed-plan の Q1）。
- レビューした head とセッション ID、モデル識別子、重大・軽微・情報の件数は PR 本文の証跡ブロックに残す。
- Codex 自動レビューはどの段階でもマージ条件に入れず、参考として扱う。結果は証跡ブロックに記録する。
- 回数を使い切っても重大な指摘が残るときは、L2・L3 とも PR を分割するか、Issue に記録して人がマージ可否を決める。

#### 段階 PR の受入

例外の対象は、利用者が名前を挙げて承認した main 以外の統合専用ブランチへ向けた、同じ change の段階 PR だけとする。接頭辞から対象を推測しない。段階受入について、その統合先以外のすべてのブランチには従来の条件を適用する。管理役は次の全条件を対象 head で確認する。

1. 実行前の分割計画に、その段で受け入れるタスク・要件・検証と、後段へ残すタスク ID・要件 ID・実観測・最終受入を記す。許容する非 PASS の検査 ID（`tasks.md`、`要件ごとのテスト`、該当する `quality:*`）ごとに、対象の REQ ID・残タスク ID・不足理由を宣言する。Requirement・Scenario・tasks の本文や必要な検証を削らず、未実装のタスクに完了印を付けない。
2. 仕様ゲートと対象段の試験・検証が成功し、AGENTS.md の段階分類、gate 以外の必須 CI、必要な 3 OS 試験を満たす。各段 PR の base から最新 head までの全差分を 200KiB 以内に収め、最新 head の独立レビューで重大な指摘ゼロを確認する。既存のレビュー回数の上限も維持し、上限内で確認できなければ保留する。既存の品質設定、試験、期待値、skip、timeout、カバレッジ閾値は維持する。
3. CI の gate と `verify --done` を省略・置換せず実行する。管理役は gate ジョブ全体の標準出力・標準エラー・終了状態を確認する。許容候補は、対象 change の完了ゲートに対して `ciGateProblem` が返す「verdict が PASS ではありません」または「不合格か証拠不足の検査があります」という理由に限る。build、REQ ID 重複、段階判定の誤り、change の特定失敗、別 change のゲート失敗など、ほかの失敗はすべて保留する。
4. 対象の JSON が現行 Verify スキーマに適合し、`change` が対象と一致し、`scope` が `ci`、`run.status` が `completed`、`run.errors` が空配列、`decision.required` が `false` であることを確認する。結果が読めない、型が不正、実行未完了、要判断の場合は保留する。`ciGateProblem` は最初の理由だけを返すため、後続の条件が出力されなくても管理役が実際の JSON で確認する。`checks` が 1 件以上あり全件 `NOT_APPLICABLE` ではなく、`tasks.md`・`要件ごとのテスト`・ID が `command: ` で始まる検査がそろい、`command: ` の検査がすべて `PASS` であることを求める。`verdict` は `FAIL` または `INSUFFICIENT_EVIDENCE` で、実際の verify の終了コードが現行の `verifyExitCode` に対応する `1` であることも確認する。 gate のログに verify 自体の終了コードが出ない場合は、同じ head のビルド済み CLI を `node packages/cli/dist/cli.js verify --change <change-id> --done --json --scope ci` で直接実行し、標準出力・標準エラーと実際の終了コードを別の証跡として保存して確認する。gate 全出力の確認は省かず、直接実行の JSON にも本項の全条件と実行前宣言との完全一致を求める。JSON の内容から実際の終了コードを推論して代用しない。これらが欠落・不一致なら保留する。全検査を読み、実際の非 PASS（`FAIL`・`INSUFFICIENT_EVIDENCE`）の検査 ID・REQ ID・残タスク ID の集合と不足理由が、実行前の宣言と完全に一致する場合だけ許容する。理由は未完了タスク、後段で実装する要件の対応試験不足、宣言済みの同じ不足から直接生じた品質証拠不足だけに限る。宣言外の不足を推論で補わず、品質コマンドの失敗、入力不正、実行エラー、partial・aborted、既存の回帰、無関係な不足があれば受け入れない。
5. PR 本文末尾の一つの証跡ブロックに、対象 head、統合先、承認元、段階の検証・レビュー、期待した非 PASS と実際の非 PASS、gate の実結果と残作業を記録する。gate の失敗は失敗として残し、段階受入を change 全体や親の完了とは呼ばない。

`ci-gate`、required checks、ruleset、品質コマンドや試験設定は変更しない。GitHub の保護規則を迂回せず、保護規則がマージを拒む場合は保留する。上のいずれかを満たさない段階 PR も保留する。

#### main への最終 PR のレビュー

最終 PR は、全タスク完了、全 Requirement の対応試験、`verify --done`、全必須 CI、必要な 3 OS 試験、実観測・導入検証を満たす。ここには段階受入の gate 失敗の例外を適用しない。テストの弱体化、設定緩和、完成範囲の縮小を認める承認経路は作らない。

管理役は各段のレビュー済み範囲と最終 head の累積差分の対応を記録する。段階レビューを最終レビューの代わりに数えず、設計・実装・各段レビューとは別の新しい Opus セッションが、最終 head の全累積差分、全 Requirement と相互作用を独立にレビューする。重大な指摘や読めない範囲があれば未受入として修正・確認する。軽微な指摘の Issue 記録とレビュー回数の上限は、上のレビュー規則に従う。上限を超えて自動で受け入れない。最終 PR は各段の積み上げをまとめるため、通常の 1 日・commit 10 個以内という分割の目安の対象外とする。各段 PR は引き続きこの目安に従う。

累積差分が 200KiB 以下なら、従来どおり全差分を依頼文へ貼る。200KiB を超える累積最終 PR に限り、上記の承認対象では、全差分の原文を改変・欠落なく専用 worktree 内の差分ファイル群へ保存する。最終依頼には比較元・最終 head、全ファイルのパス、原文の順序と担当範囲を示す索引、各段レビュー済み範囲との対応を載せ、レビュアーに全ファイルを全件 Read させる。分割保存した原文を順に連結すると `git diff <base> <head>` の全出力と一致することを管理役が確認する。要約や段階レビューだけで代用せず、読取漏れは未受入とする。

これは差分を依頼へ貼る通常規則に対する、承認された累積最終 PR だけの特例である。通常 PR、段階 PR、規則変更 PR #260 には適用しない。ask-opus.mjs の依頼全体 1MiB・差分欄 200KiB を含むツール設定や上限は変えず、依頼にも上限内の索引と明示的な外部ファイル形式の表示を載せる。上限内に収まらない依頼や、全原文を読めない実行は受け入れない。

選択肢は A＝段階受入と上の累積最終レビュー方式の両方を、対象ブランチ・分割計画とともに明示承認する、B＝例外を認めず、それぞれで DoD を満たせる独立した子 change へ仕様・設計を分ける、である。A を推奨した。分割済みの作業と親の全受入を保ち、各段の検証に加えて最終 head の全体を別の Opus が確認できるためである。A は累積原文の保存・全件読取・範囲対応の記録が増える。B は現行規則を保てるが、要件の所有と依存を子 change ごとに設計し直す必要がある。どちらも未収集の実観測や親の完成条件を省かない。利用者は 2026-11-01 に A を選んだ（出典・対象・適用開始は本節の冒頭を参照）。

### 完成を早めるための規則変更（利用者決定・2026-11-05）

利用者は 2026-11-05 の Claude Code の会話で、完成を早める施策 A〜D の提示に「早く完成させたいので、全てやる」と答え、すべてを承認した。本節はその決定を文書に反映したものである。適用は、規則変更 PR のマージ後に、B・C・D はすぐ、A は下記の CI 対応のあとに始まる。

**A. 仕様適合の修正の経路（新設）。** 仕様どおりに直すだけのバグ修正は、change を作らずに L3 を通せる。次の 5 つをすべて満たすときだけ使い、1 つでも外れたら通常の L3（change 必須）にする。

1. 直す振る舞いが `openspec/specs/` の既存 Requirement に書かれている。コードを仕様に合わせるだけである。
2. 対象の既存 REQ ID を名前に入れたテストを足すか直し、そのテストは修正前に失敗し、修正後に通る。
3. `openspec/` を変えない。
4. 公開契約（CLI のフラグ・終了コード・JSON の形式・設定キー）を変えない。
5. PR 本文に `loomake-change: none`、`loomake-route: spec-fix`、`loomake-req: REQ-xxx`（複数可）を書く。

手続きは通常の L3 から次の点だけを変える。品質コマンドと 3 OS の CI は通常どおり通す。Opus 設計は省く。change がないので `verify --done` は対象外で、完了は、品質コマンド（lint・typecheck・test）と 3 OS の CI の成功、対象の REQ ID を名前に入れたテストが修正前に失敗し修正後に通った証拠（PR 本文）、独立 Opus レビューで重大な指摘がゼロ、の 3 つがそろったときとする。独立 Opus レビューは L2 と同じく 1 回とし、重大な指摘があれば修正後に 1 回だけ再レビューする。changeset は通常どおり付ける。仕様が曖昧なときや、仕様にない振る舞いを決める必要があるときは、この経路を使わない。AGENTS.md 1 章の「仕様に書かれていない振る舞いは実装しない」と DoD は変えない。

CI がこの経路を受け付けるのは、[Issue #427](https://github.com/loomake/loomake/issues/427)（`openspec/specs/monorepo/spec.md` の REQ-343「段階ごとの完了ゲートの動作」を MODIFIED する change。L3 として Codex が対応）がマージされてからである。それまでは文書上の決定だけが先に入り、`loomake-route: spec-fix` を宣言しても ci-gate は通常の L3 として扱い、`loomake-change: none` を失敗にする。この経路はそれまで使えない。

**B. W1 の範囲の絞り込み。** 「完成範囲を縮めること」の禁止（決定の 5 項目め）に対する承認として、次を記録する。

- W1-11（trace eval・report --status）：内部品質の指標は、既存の品質コマンドがすでに出す値（テストの成否と数、カバレッジ、lint・型のエラー数）だけにする。週次の自動実行はせず、手動で実行して出す。未測定を「未評価」と表示する完了条件は維持する。 A20 の W1 受入範囲は、下の「W1 の起票制限の一時除外と A20 の扱い」に定める。
- W1-9（開発効率の計測）：人力工数の自動推定（FR-49）は段階 1 から外し、`record --effort` による実績の記録と、手書きの記録（C-001〜003）を取り込んだ表だけにする。外した部分は W7 の候補として残す。
- WBS の固定版（`docs/wbs/baseline-v1.4.md`）は書き換えない。決定は本 ADR に置き、各 Issue（#68・#70）にコメントで記録する。

**C. 同時に進める change の増枠。** 全セッション合計 4 本を 5 本に増やし、配布 4・品質 1 に配分する。増えた 1 枠は W1 に充てる。

**D. 時間切れのテストの隔離。** 今回の変更と関係なく Windows で時間切れになるテストは、既存の隔離の仕組み（`tests/quarantine.json`）に載せてよい。対象は `tests/delivery-opus-prior.test.ts` の「first-error: 第一段階で失敗したら仮説を送らない」（PR #425 の CI で 5007ms の時間切れ）で、載せる作業は [Issue #428](https://github.com/loomake/loomake/issues/428) で扱う。隔離の仕組みは試験ファイル単位で外すので、載せるとこのファイルの試験が Windows の quality ジョブからすべて外れる。1 件だけ外す方法（試験の分割など）にするか、ファイル単位で外すかは #428 で決め、分割するときもテストの削除や期待値の変更にしない。隔離には期限と Issue を必ず付け、テストの削除と期待値の変更はしない。


#### W1 の起票制限の一時除外と A20 の扱い（利用者決定・2026-11-05）

利用者は 2026-11-05（日本時間）の本会話で、[選択式の確認への直接回答の記録](https://github.com/loomake/loomake/issues/121#issuecomment-6653027069)のとおり「指定W1案件の起票制限だけ一時的に外す」と、W1 は手動の同時要求を実装して定期起動を後段へ残す案を直接選んだ。本節は今回の直接選択を承認元とし、その指示を受けた時点から適用する。

- **新しい L3 PR の起票。** delivery スキルが定める「作成から 24 時間以上たち、マージ条件を満たしていない PR が 2 本以上あるときは新しい L3 PR を起こさない」という制限を、今回指定された W1 案件に限り、今回の指示から W1 の出口確認まで一時的に外す。対象は #427・#70・#61・#66・#71・#65・#69・#68・#73・#46 と、先に指定された #425（#416）・#426（#419）・#428 の仕上げである。
- **維持する条件。** 必須 CI・仕様ゲート・完了ゲート・要件対応テスト・独立レビューとその回数、既存の禁止事項は維持する。同時に進める change は全セッション合計 5 本まで（配布 4・品質 1）のままとする。一時除外の対象外の案件と、W1 の出口確認後には、起票制限を通常どおり適用する。
- **A20 の W1 受入。** #70 が、手動の同時要求・待機・すべての要求の追跡を追加実装する。実行中 1 件に加えて待機 2 件以上を発生させ、各要求を評価済み・再評価待ち・取消・回収不能のいずれかとして追跡できること、`history.jsonl` に重複行がないこと、再評価の結果を元の時刻の結果として記録しないことを検証する。定期起動と手動起動の重なりは後段に残し、W1 の手動範囲の受入と元の A20 全体の達成を区別して記録する。

A20 の実装と対応する仕様・試験は #70 が所有する。WBS 固定版（`docs/wbs/baseline-v1.4.md`）は書き換えず、この決定と受入記録で今回の範囲を示す。

## 検討した選択肢

- A：上記の包括承認を記録し、管理役が判断と証拠を残して進める。判断待ちの時間を減らせる一方、管理役には承認範囲の確認と記録が必要となる。利用者は A を指定した。
- B：確認事項・仮定・マージごとに人の承認を待つ。判断を個別に確認できる一方、利用者の返信待ちで作業が止まる。

レビュー規則の改訂では次を比べた。

- A：L2 は 1 回、L3 は 2 往復を上限にし、残った軽微な指摘は Issue 化でマージ可とする。利用者は A を選んだ。
- B：上限なしを維持する。PR #179 のように 9 時間を超えても終わらないレビューが続く。

## 理由

利用者は初回配布を優先し、できるだけ早く自動で完成まで進めるよう指示した。品質基準と完成範囲を保ったまま判断を委任し、必要な人の操作を 4 種類に限定する。

レビュー規則を改訂したのは、独立 Opus レビューは実際に指摘を出している一方で、「指摘ゼロまで無制限」の規則が 18 行の文書 PR にも 5 時間以上かかる工程を生んでいたためである。Codex 自動レビューは 2026-10-29 以降の 8 本の PR で指摘がなく、マージ条件に数える根拠がない。

## 適用範囲

Loomake 自身の初回配布に向けた開発、品質計画、PR と Issue の運用に適用する。AGENTS.md、delivery スキル、docs/dev/agent-workflow.md を本 ADR に合わせる。利用者に配るテンプレートや製品仕様は、この ADR だけでは変更しない。ツール・実行環境の権限制限を解除する決定でもない。

## 見直す条件

利用者が規則の変更を明示的に決定したときに、新しい ADR へ記録する。利用者が本 ADR 自体への反映を指定した場合は、本 ADR を更新し、出典に指示と日付を記録する。規則の変更が必要な場合は Issue #121 で `@rrr-www` に依頼する。包括承認の運用中にテストの弱体化・設定緩和・完成範囲の縮小を例外として認めない。Codex 自動レビューは、2 週間で指摘が 1 件も出なければ依頼自体をやめる。
