# 0002 `0.x` の間は破壊的変更を minor で出す

- 状態：採用
- 決めた日：2026-10-26
- 決めた人：利用者（PR #10 のコメント 6403295324 での回答。利用者の「Q-01〜03の回答して」という依頼に基づく方針選択）
- 出典：WBS の W0-6、change `record-stack-and-versioning-decisions` の trace.md の Q-03（REQ-227・REQ-233）

## 決定

パッケージの版が `0.x` の間は、破壊的変更を minor の版で、それ以外の変更を patch の版で公開する。破壊的変更には移行の方法を添える。

パッケージの版と形式の版は独立させる。verify の JSON に破壊的変更を入れるときは、パッケージの版とは別に、仕様 REQ-053 に従って `schemaVersion` の major を上げる。

## 検討した選択肢

- **A：破壊的変更を minor で許す**：`0.x` の間は、破壊的変更を minor、それ以外を patch で出す。利点は、`docs/compatibility.md` の「変更を公開する判断」に書いたいまの運用と、changesets の使い方を変えずに済むこと。npm の `^0.y.z` は minor の更新を取り込まないので、`^` で入れた利用者は破壊的変更を自動では受け取らないこと。欠点は、minor の版ごとに移行の手間が生じうること
- **B：破壊的変更を許さない**：`0.x` の間も破壊的変更を避け、必要になったら 1.0 に上げる。利点は、`0.x` の中の更新が利用者にとって安全になること。欠点は、契約が頻繁に変わる初期（アーキテクチャ 5 章）に変更しにくくなり、1.0 を早く出すことになること

## 理由

- `docs/compatibility.md` がすでにこの運用を書いており、changesets の設定もそれに沿っている
- npm のキャレットの範囲で、利用者は意図しない破壊的変更から守られる
- アーキテクチャ 5 章は「初期は契約が頻繁に変わる」としている。B は初期の開発に合わない
- アーキテクチャ 0.4 は「形式のバージョンとパッケージのバージョンは区別する」としている。パッケージが `0.x` でも、verify の JSON を読む外部の道具は `schemaVersion` で互換性を判断できる

## 適用範囲

- 対象は、npm に公開する 5 つのパッケージの版（[0001](0001-versioning-with-changesets.md) の changesets で上げる）。changeset で `minor` を選ぶか `patch` を選ぶかを、この ADR で決める
- 破壊的変更に当たるものは、アーキテクチャ 0.4 の互換性を検討する対象（関数 API、CLI のコマンド・オプション・終了コード、quality.yaml、verify と quality-report の JSON、外部から参照される生成ファイル）を変えて、これまでの使い方が動かなくなる変更とする
- 形式の版：verify の JSON は REQ-053 に従う。quality.yaml などのほかの形式に `version` を付ける作業（WBS の W1-1）と、互換性の方針の運用（W6-5）は、この ADR の範囲に入らない
- 1.0 以降の版の上げ方は決めない

## 見直す条件

- 1.0 を出すと決めたとき（WBS の W6-5 の完了条件「1.0 を出す時点で互換性の範囲が文書化されている」）
- 利用者から、minor の版ごとの移行の手間が大きいという報告が続いたとき
