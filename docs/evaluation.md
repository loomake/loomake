# Loomake の評価

評価日：2026-10-23（ブランチ fix-review-findings-2、コミット 1629e6f）

## 総評

狙いがはっきりしていて、作りも小さくまとまっています。「確認事項が残る間は実装させない」「全要件に成功したテストがあることを確かめる」の 2 つの約束を、OpenSpec の書式に乗せて機械的に検査する、という切り出し方がよくできています。lint・typecheck は合格し、テストは 252 件すべて成功しました。

弱いのは 3 点です。要件ごとのテストの判定が名前だけで決まること、導入に手作業が残ること、対象がまだ狭いこと（Vitest・Jest の JSON、Claude Code、日本語のみ、npm 未公開）です。

## 使いやすさ

よい点

- 終了コードが 0（合格）・1（不合格）・2（使い方の誤り）に分かれ、`--json` もあるので、CI やエージェントから扱いやすい
- 不合格の理由に次の手順が書いてある（「.gitignore に足してコミットしてから、もう一度実行してください」など）
- `run --dry-run` で、エンジンに渡すタスクと指示を先に確かめられる

気になる点

- 導入後に手で設定することが 3 つある（テストランナーの JSON の出力先、`.loomake/` の .gitignore、AGENTS.md の書き換え）。init が .gitignore に足さないので、そのまま `run` を実行すると、始める前に止まる
- trace.md の表（回答者・回答日・承認者・承認日）を人が Markdown で書く。列名が日本語で決まっているので、書き間違えると解析エラーになる。顧客とのやりとりが多い案件では、ここの手間が大きい
- メッセージとドキュメントは日本語だけ。いまの利用者には合っているが、OpenSpec の利用者に広げるなら障壁になる

## 構成

- 依存の向きを core → kit → trace → runner → cli の一方向に決め、core の実行時依存をゼロにしている点はよい。仕様（REQ-046 など）とテストで守っているので崩れにくい
- 一方で、テストを含めて約 4,900 行の規模に対して 5 パッケージは多め。利用者が入れるのは `loomake` だけなので、公開する単位はもっと減らせる
- [run.ts](../packages/runner/src/run.ts) の `runRun` は 220 行ほどの 1 つの関数で、事前の確認、タスクの実行、完了ゲートの直し、PR 作成を順に書いている。段階ごとに関数を分けると、再開の扱いを足すときに読みやすくなる

## 技術面

よい点

- 完了ゲートは、品質コマンドを実行する前に前回のテストのレポートを消すので、古い結果で合格しない
- 時間の上限で止めるときは、子のプロセスまで止める。Windows では taskkill でプロセスの木ごと止める
- エンジンの変更をコミットする前に、テストの削除、skip の追加、設定ファイルと仕様の書き換えを差分から探す（[guards.ts](../packages/runner/src/guards.ts)）

気になる点（重い順）

1. 要件ごとのテストは、成功したテストの名前に `[REQ-xxx]` があるかだけで判定する（[test-report.ts:535](../packages/core/src/test-report.ts#L535)）。中身が空の `it('[REQ-012] …', () => {})` でも合格する。MODIFIED の要件も、前の change で書いたテストがあれば合格する。名前で判定するのは設計どおりだが、「全要件にテストがある」と検収レポートに書くなら、この限界をレポートか docs に明記したほうがよい
2. ガードは HEAD との差分しか見ない（[guards.ts:380](../packages/runner/src/guards.ts#L380)）。`--skip-permissions` のときにエンジンが自分で `git commit` すると、そのコミットの中身はガードを通らない。エンジンを呼ぶ前の HEAD を覚えておき、そこからの差分で調べる必要がある。コードを読んで見つけた点で、再現はしていない
3. git の失敗を `UsageError` で投げる（[git.ts:7](../packages/runner/src/git.ts#L7)）ので、証拠のコミットなどに失敗すると、終了コード 2（使い方の誤り）になり、使い方の案内も表示される。push と PR 作成の失敗だけは捕まえて、終了コード 1 で止まる。CI からは、設定の誤りと実行時の失敗を終了コードで区別できない
4. 完了ゲートを通すタスクかどうかを、タスクの文に「verify」と「--done」があるかで決めている（[run.ts:56](../packages/runner/src/run.ts#L56)）。tasks.md の書き方が少し変わると、エンジンにゲートのタスクを渡してしまう

## 開発の進め方とドキュメント

- Loomake 自身を Loomake の流れで作り、17 の change を archive まで進めている。要件の出典から実装までたどれる点は、このツールの主張をそのまま示している
- 一方で、コードのコメントが「fix-review-findings-2 の仮定 A-02」のような change ごとの番号を多く参照している。archive のあとは、その番号を探しに archive の trace.md まで行く必要がある。理由そのものを 1 行で書いておけば、番号を追わずに読める
- ドキュメントは quickstart・usage・positioning・for-agents でかなり重なっている。読む人ごとに分けた意図は分かるが、同じ手順を複数の文書で直す手間が増えている

## 先に手を付けるなら

1. ガードがエンジン自身のコミットを見逃す点を直す（上の技術面の 2）
2. init で `.loomake/` を .gitignore に足し、テストランナーの設定例を出す
3. 要件ごとのテストの判定が名前によることを、検収レポートと docs に書く


## 2026-10-24 の追加評価

**Loomake は、要件の取りこぼしや確認漏れを減らしたい AI 開発に向いた、設計の筋がよいツールです。ただし、初回導入の手軽さと、検収の証拠としての厳密さには改善の余地があります。** 現時点では、小規模な案件で人がレビューしながら使うのが適切だと評価します。

現在の作業ツリーのコード・仕様・文書を確認し、`fix-review-findings-2` の完了ゲートを実行しました。ビルド・lint・型検査・テストは成功し、**252 件すべてのテストが成功**しました。実際の Claude Code と GitHub を使った一連の実行は未検証です。

| 使いやすさ | 改善余地あり | コマンドの役割は明確。ただし導入時に OpenSpec・テスト出力・Git 除外・エージェントの設定が必要 |

| 自動化の信頼性 | 条件つき | 停止・質問・検証失敗を扱う一方、テストの弱体化など検出できない変更がある |
| 保守・拡張性 | 良好だが注意 | 小さな実装で把握しやすい。Markdown の書式や外部 CLI の仕様への依存は増えやすい |

**特に良いのは、「何を作ったか」を後から説明できる構成です。**

出典・未回答の質問・仮定・テスト結果を同じ流れで扱える点に価値があります。仕様の確認だけ、実装だけ、テストだけで終わらず、顧客に説明する材料まで残せます。受託開発や、要件の合意が重要な社内開発では役立つ設計です。

また、テスト名をソースから拾うだけでなく、テストランナーが出した**成功したテストの結果**を使う点も適切です。古いレポートを消してから検査する処理や、JSON 出力と進捗表示を分ける処理にも配慮があります。[要件とテストの照合](../packages/kit/src/verify/run.ts#L257)

**改善の優先度が高いのは、次の点です。**

1. **検収レポートを、検証した時点の仕様に結び付ける。** 現在は、保存したテスト結果と作業ツリーにある最新の要件・仕様を組み合わせています。一時リポジトリで、証拠の記録後に要件の要約を変更すると、変更後の要約にも古い結果で「合格」が表示されました。証拠にあるコミットの文書を読むか、文書のハッシュを保存して不一致を示す必要があります。検収用途では最優先です。[レポート生成](../packages/trace/src/report.ts#L96)

2. **「テストがある」と「要件を満たす」の違いを明確にする。** 現在の照合は REQ ID と成功結果の対応を確認します。テスト内容の妥当性までは確かめません。また、期待値を `expect(true).toBe(true)` に置き換える変更は、runner の違反検査で検出されませんでした。既存テストの変更を人のレビュー対象として明示するなど、運用と検査を組み合わせる必要があります。[変更の検査](../packages/runner/src/guards.ts#L42)

3. **CI の完了ゲートをブランチ名だけに依存させない。** 現状は、ブランチ名と change-id が一致しないと、要件・タスクを確認する完了ゲートが実行されません。規約どおりの名前なら機能しますが、チーム運用では名前の付け間違いで検査が抜けます。変更ファイルや明示した change-id から対象を決める方式が望ましいです。[CI の対象判定](../scripts/ci-gate.mjs#L13)

4. **初回導入と CLI 内の案内を充実させる。** `--help`・`--version` が未対応で、`verify --help` は「知らないオプション」になります。まずこの案内と、導入状態を調べる `doctor` 相当の機能があると、文書を往復する負担を減らせます。`init` 後に残る設定も一覧で確認できると使いやすくなります。[CLI の引数処理](../packages/cli/src/main.ts#L23)

5. **runner を実案件で評価し、時間と費用を測る。** 自動テストでは偽の Claude・gh コマンドで制御を確認しています。これは回帰テストとして有効ですが、実エージェントの権限・質問・出力の揺れは別途確認が必要です。また、完了ゲートの後に証拠記録でも品質コマンドを再実行するため、テストが重い案件では待ち時間が増えます。実案件で完了率、手動介入回数、所要時間、利用料金を記録すると、次の改善を判断できます。[runner の検証用環境](../packages/runner/test/helpers.ts#L1)

**構成は維持し、まず検収レポートの整合性と導入体験を改善するのがよいと思います。** 機能を増やす前に、この 2 点を整えると、Loomake の提供価値を利用者が確認しやすくなります。要件が頻繁に変わる短い試作では文書管理の負担が大きくなりやすく、合意・検収の記録が必要な案件ほど導入効果を期待できます。
