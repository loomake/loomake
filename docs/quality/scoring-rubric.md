# 品質の採点の規準

このリポジトリの品質を、15 の観点で 100 点満点に採点するときの規準です。点数の台帳は [scorecard.json](scorecard.json)、各回の記録は [reviews/](reviews/README.md) にあります。規準は 2026-10-24 の初回の採点（git 履歴の [cc5df0f](https://github.com/loomake/loomake/blob/cc5df0f85a29158512f45d5ff5517ff38a0b0aa7/docs/review.md) にあった docs/review.md の「100点満点での評価」と「追加した観点の点数」）から起こしたものです。回をまたいで点数を比べられるように、規準は変えずに使います。変えるときは、この文書を直し、変えた回の記録にその旨を書きます。

## 点数の意味

点数はその回に確認できた実装・仕様・テスト・履歴に基づくレビュー上の判断です。テストの成功率や外部認証の値ではありません。

| 点数 | 状態の目安 |
|---:|---|
| 90 以上 | 主要な異常系と配布・運用まで確認できる |
| 80 台 | 構成と検証が充実している |
| 70 台 | 基盤があり、重要な不足が残る |
| 60 台 | 重要な保証の検証や実装に不足がある |
| 60 未満 | その観点の手順や検証の根拠を十分に確認できない |

未検証の項目は不具合として数えません。評価の確かさを制限する要因として扱い、各観点の「根拠と残る確認」に書きます。カバレッジ率、クラス数、テスト件数だけを 90 点の根拠にはしません。実行環境と運用を含む観点は、その環境での確認結果が必要です。

## 15 の観点

| 観点 | 何を見るか |
|---|---|
| 設計 | 要件の出典から仕様・テスト・コミット・証拠までのつながりが明確か。実行の開始から証拠と PR までの状態・停止・失敗・再実行が仕様で定義され、各境界の失敗シナリオが実装と一致するか |
| 実装 | 型検査、純粋な解析、機能ごとの分割が保たれているか。Git のパス処理、子プロセスの停止、JSON の検証のような外部との境界で、不正な入力を定義したエラーへ変換するか。再現済みの指摘を未対応で残していないか |
| テスト | 要件 ID とテストの対応、失敗系、一時 Git リポジトリによる試験があるか。Requirement だけでなく Scenario とテストの対応を確認し、安全上重要な判定に正常・異常・境界の試験と mutation の検出があるか |
| 動作の信頼性 | 完了ゲート、配布物の起動、テンプレートの展開が実際に動くか。実際のエンジンと GitHub を使う一連の動作、別 OS・別 Node での実行、時間切れと中断の扱いを確認できているか |
| TDD | 不具合の修正と機能の変更で、変更前の Red、実装後の Green、整理後の成功を記録しているか。単発の例ではなく複数の change で続け、テストの弱体化をレビューしているか。確認できる手順と記録の評価であり、ローカルの作業順を断定しない |
| アーキテクチャ | core の実行時依存ゼロと一方向のパッケージ依存が保たれているか。プロセス・Git・時刻を必要な箇所で差し替えられ、ルールの試験が外部ツールを必要としないか |
| OSSとしての整備 | ライセンス、changesets、複数 OS の CI、導入ガイドがあるか。公開予定の SHA に対して品質と配布物の検査が成功し、貢献・脆弱性報告・サポート・互換性の方針と現行の文書がそろっているか |
| ドメイン駆動設計 | 要件・確認事項・仮定・検証・証拠という用語が仕様とコードで対応しているか。責務の境界とモデルの整合性条件を定義し、主要なルールを I/O から分離して直接検査できるか |
| セキュリティ | 脅威と信頼境界を定義し、パス・権限・資格情報・ログ・停止を検証しているか。エンジンへの許可一覧、秘密情報の置換、シンボリックリンクの扱いなど、再現した指摘を解消または理由付きで受容しているか |
| 供給網と公開 | lockfile、公開の手順、公開対象と検査対象の SHA の一致、配布物からの検査があるか。CI と公開の権限、Actions の不変参照、認証、公開元の検証、依存更新の方針が整っているか |
| 互換性 | 対応 OS と Node の範囲を決め、配布物から主要コマンドを実行しているか。JSON の版と過去スキーマの fixture、公開 API の型、旧形式の証拠の読み取りで、破壊的変更を検出できるか |
| 保守性 | 小さな純粋関数と機能ごとの分割、named export が保たれているか。設定・Git・プロセスの規則を変更する場所が明確で、設計文書が同期し、変更がどの仕様と試験に影響するか追えるか |
| 使いやすさ | help・doctor・上書き前の差分と確認・クイックスタートがあるか。導入、普段の操作、失敗からの復旧で利用者の判断負担が少なく、help・doctor と実際の挙動が一致するか。AI による操作試験と人による試験は区別する |
| 性能と資源制限 | 対象規模ごとの時間・メモリ・出力・ディスクの予算を定義し、測定しているか。過大な入力や出力で予算を超えたときも、理由を示して止まり、作業状態を確認できるか |
| 障害対応と復旧 | 同時実行、中断、強制終了、証拠保存の失敗、push の失敗、PR 作成の失敗からの再実行を検証しているか。完了済みの変更や証拠を重複・上書きせず、復旧手順が実際に通るか |

## 採点の手順

1. 対象は `origin/main` の head とします。採点した時点の SHA を記録に書きます。
2. 採点者（モデル名か人）を記録に書きます。
3. 各観点に、点数と「根拠と残る確認」を 1〜2 文で書きます。根拠はその回に実行して確かめたこと（コマンド、件数、再現した結果）に限ります。残る確認は未検証の項目を列挙します。
4. 前回と同じ規準で付けます。前回から変えた観点は何を確かめて何点から何点にしたかを書きます。据え置いた観点はその旨を書きます。
5. 点数の根拠が読めない回は、台帳に入れません。
