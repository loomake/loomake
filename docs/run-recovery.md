# runを中断したときの再開

`loomake run --change <change-id>`を再実行すると、既存のchangeブランチと未完了のタスクを使う。最初に`git status`と直前の`.loomake/runs/<run-id>/summary.json`を確認する。タスクとコミットの内容を読み、未コミットの変更を残すか、必要な部分を直すかを判断する。ログのために作業内容を削除する必要はない。

## 二重起動の防止

同じGit作業ツリーでrunを同時に起動すると、後の実行は終了コード1で止まる。dry-runも対象になる。通常終了、SIGINTによる中断、例外では、自分のロックを解放する。

ロックは`git rev-parse --absolute-git-dir`で確認できるディレクトリの`loomake-run.lock`に置く。PID、ホスト名、所有トークンを記録する。Git worktreeごとにロックを分ける。

同じホストで所有プロセスが終了済みと確認できれば、次のrunがロックを回復する。PIDが再利用されて生存中のプロセスを指している場合は回復しない。プロセスを調べる権限がない場合も、終了したとは判断しない。

## 自動回復できない場合

所有者の情報が壊れている場合、別ホストが所有する場合、回復用の`loomake-run.lock.recovery`が存在する場合は、自動で削除しない。

1. エラーに表示されたロックの場所と、そのPID・ホストを確認する。
2. 所有ホストで対応するrunとエンジンが終了していることを確認する。作業ツリーを共有している場合は、その利用状況も確認する。
3. 終了を確認できた場合だけ、表示された専用ロックファイルを取り除く。Gitの`index.lock`など、別のロックは削除しない。
4. 作業内容と直前の実行記録を確認し、同じchangeを再実行する。

ホスト名が同じ別PID名前空間から、同じ作業ツリーを共有する構成は対象外とする。別ホストのプロセスを確認できない状態では、ロックを手動削除しない。

## 記録と外部操作

同じchangeを同じ秒に再実行しても、記録のディレクトリは別に作る。最初は従来の日時形式を使い、名前が衝突したら連番を付ける。

ロックは同時実行を防ぐための仕組みであり、エンジンが残した変更を取り消す仕組みではない。外部操作が失敗した場合は、summary.jsonの理由を読み、GitHubとローカルの状態も確認する。

## pushやPR作成が失敗した場合

認証、通信、originの設定など、停止理由にある問題を直してから、同じchangeのrunを再実行する。再実行でも完了ゲートを通す。過去の合格が今回の不合格を代用することはない。

直前のコミットが対象changeの合格証拠だけを追加したもので、証拠のSHAがその親を指し、現在のtrace.mdと差分仕様のスナップショットが一致する場合は、同じ証拠とコミットで外部操作を再試行する。以前の証拠やコミットを削除する必要はない。

| 止まった段階 | 再実行で確認することと動作 |
|---|---|
| push失敗 | originと認証・通信を確認する。証拠が再利用できれば、そのコミットを再度pushする |
| PR作成前の失敗 | push後に同じbase/headの既存PRを確認し、存在しなければ作成する |
| 作成の応答が失われた | 既存PRが一意に存在すれば、作成を繰り返さずURLを表示して完了する |
| PR検索の失敗・不正な結果・複数の候補 | 新規作成せず止まる。検索条件とGitHubの状態を確認する |
| 証拠の不整合 | 自動で上書きや削除をしない。表示された証拠、親コミット、仕様と合格結果を確認する |
| 検証中のHEAD・ブランチ・作業ファイルの変更 | 変更を取り消さず止まる。品質コマンドとGitの状態を確認する |

証拠の後に実装や文書の変更をコミットした場合は、変更後の状態に対する新しい証拠を記録する。文書を含まない旧形式の証拠はレポートで読めるが、自動再利用の候補としては扱わない。

既存PRとして自動で使うのは、同じリポジトリで同じbase/headを持つopen PRだけである。別リポジトリのPR、違う枝、複数の結果は自動選択しない。既存PRを使った場合はsummary.jsonへそのURLを含む理由を残す。

この復旧経路はローカルのGitと代替ghで回帰試験を行っている。実際のGitHubでの認証・通信・権限・障害からの復旧が成功したという検証結果ではない。

## 証拠の保存が失敗した場合

証拠は、保存前に形式と完成JSONの64MiB上限を検証する。同じ保存先の専用一時ファイルへ完全に書き、同期して閉じてから、最終名へ上書きせず公開する。保存先にはハードリンクを作れるファイルシステムが必要である。対応しない場合は直接書き込みへ切り替えず止まる。

書き込み・同期・公開前の失敗では、不完全な最終JSONを残さず、自分の一時ファイルを片付ける。保存先の容量・権限・機能を直した後は、同じchangeを再実行する。完了済みの実装コミットを保ち、再検証と証拠記録から進める。

最終JSONを公開した後、一時ファイルの片付けだけが失敗する場合もある。エラーに対象を表示して停止するので、次の順で確認する。

1. `git status`、直前のsummary.json、表示された保存先を確認する。
2. 最終JSONがあれば、`loomake trace report --change <id>`と内容を確認する。検証したSHAが、証拠を追加する前の実装コミットを指すことも確認する。
3. 作成元の実行環境とプロセスの終了を確認した後、表示された自分の専用一時ファイルだけを取り除く。名前は`.loomake-evidence-<PID>-<識別子>.tmp`である。所有者を判断できないファイルは消さない。
4. 完全な最終JSONが未コミットで、合格結果と実装・文書の対応を確認できた場合は、そのファイルだけを`git add -- "<証拠のパス>"`で追加してコミットする。
5. 同じchangeを再実行する。再検証に成功し、直前の証拠だけのコミットが再利用条件に合えば、証拠を増やさずPRの公開へ進む。

SIGKILLなど、片付けの処理が動かない強制終了でも一時ファイルが残ることがある。最終JSONがなければ、終了を確認した専用一時ファイルを片付けてから再実行する。一時ファイルは検収用の証拠として読み取らない。最終JSONがあれば、上の確認とコミットの手順を使う。

この保存方法は、完全な内容だけを最終名で見せるためのもので、電源断や保存装置全体の永続性、同じ利用者による後からの編集を保証する仕組みではない。

## 実行記録の容量が不足した場合

容量と項目数の上限は[resources.md](resources.md)を参照する。開始前の履歴確認で止まった場合は、表示された履歴のサイズ・項目数・リンクを確認する。必要な記録を別の場所へ保管してから、不要と判断した履歴を手動で整理するか、用途に合わせて設定値を見直す。Loomakeは履歴を自動削除しない。

開始後に記録の予算を超えた場合も、完了済みのコミットと作業中の変更は保つ。通常はsummary.jsonに停止理由を残す。summary自体が64KiBの予約に収まらない場合は、別形式のstop.jsonを保存する。

stop.jsonはschemaVersionが1、kindがrun-stopである。change、operationStatus、短いreasonとrecordingError、doneTaskCount、remainingTaskCount、lastVerifyを持つ。operationStatusは記録保存を試みた時点の処理結果であり、保存失敗による終了コード1と区別する。タスク一覧を空に置き換えたsummaryではない。個々のタスクはtasks.mdと保存済みの記録、Gitの状態から確認する。

実際の容量不足や権限エラーでは、停止情報も保存できないことがある。その場合はコンソールに保存不可と確認先を表示する。保存済みだとは表示しない。コンソール、git status、tasks.mdを確認してから保存先を直す。途中の変更を取り消さず、同じchangeの実行を再開する。公開済みのPRがある場合は、上の再試行条件も確認する。

記録storeは、保存中にI/Oが失敗した後、同じ実行の別ファイルへ書き続けない。自分が作成した部分ファイルの削除にも失敗した場合は、その理由を表示する。強制終了や電源断で常に停止情報が残ることを保証するものではない。

## Git・ghなどの操作が時間切れになった場合

Git・gh・エンジンの存在確認・OpenSpec検証は1操作30秒まで、runでは全体の残り時間の方が短ければその時間で停止する。開始前は使い方の誤り、記録開始後は停止理由を残して終了コード1になる。時間切れ・出力超過・中断は、実行ファイルがない場合や通常の非ゼロ終了と表示を分ける。

pushやPR作成の途中で止まった場合、遠隔側の操作はすでに完了していることもある。停止を遠隔側の失敗だと決めつけず、GitとGitHubの状態を確認する。保存先や認証・通信などを直した後、同じchangeを再実行する。上の証拠の再利用と既存PR検索の条件を満たせば、証拠やPRを増やさずに進む。中断した操作を自動で取り消さない。

品質コマンドの検査中だけ付けるタスクの完了印は、期限後もGitを使わず元へ戻す。検証中にtasks.mdが自分の一時的な変更と違う内容へ変わった場合は、上書きせず止まる。表示された差分を確認し、どのタスクが完了したか判断してから再実行する。

この経路はLinuxの実プロセス・ローカルGit・代替ghで試験している。実際のGitHub接続やWindows・macOSで同じ停止結果を確認したという記録ではない。
