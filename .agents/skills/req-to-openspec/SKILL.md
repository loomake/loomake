# 要件書 → OpenSpec change

要件書を **抜け・推測なしに** OpenSpec の change へ落とし込む。目的は「要件書のどの一文が、どの Requirement・どのテストで確かめられたか」を後から機械的に追えるようにすること。

最重要ルール：**曖昧な点を推測で埋めない。** 埋めずに「確認事項」として残し、必要なら止まる。

## 手順

### 0. 前提を確認する

- 入力ファイルと、その版・日付を把握する（ファイル名や表紙・改版履歴から）
- `openspec/specs/` を読み、既存仕様を把握する（既存プロジェクトの改修なら必須）
- `openspec/` が無ければ `openspec init` を案内して止まる

### 1. 要件書を読む

読める要件書は **Markdown（.md）だけ** である。

- .md の要件書はそのまま読む。章番号・表・行番号を出典に使うので、構造を崩さずに読む
- .docx・.xlsx・.pdf など Markdown 以外の要件書を渡されたら、**読まずに止まる**。利用者に「Markdown に変換してから渡してください」と求める。変換は利用者が行い、この Skill は変換しない

要件書の中の画像（画面イメージ・業務フロー図）は内容を言葉で書き起こし、出典に「図 X」と記す。

### 2. 要件台帳を作る

要件書の「〜すること」「〜できる」「〜しない」「〜以内」など、**要求を述べている文を 1 つずつ** 拾い、採番して台帳に載せる。

- 1 行に複数の要求があれば分ける
- 出典は「文書名・章と行」まで書く（例：`要件定義書 v1.2 §3.4 2 行目`、`要件定義書 v1.2 §5 表 2 の 3 行目`）
- 種別を付ける：`機能` / `非機能` / `制約` / `前提` / `範囲外`
- 書式は [templates/trace.md](templates/trace.md) に従う
- REQ の番号は、リポジトリにある trace.md（`openspec/changes/` の進行中と archive）に出てくる最大の REQ 番号の次から振る。trace.md が 1 つもなければ `REQ-001` から振る。テスト名の `[REQ-xxx]` はリポジトリ全体で探すので、別の要件書の要件と番号を重ねない
- Q・A の番号は、要件書 1 冊の中で通し番号にする
- 複数の change に分けても、REQ・Q・A を change ごとに振り直さず、同じ番号を使う
- 後のフェーズで作る要件（要件書が、今回ではなく後のフェーズで作ると決めている要件）は、種別と状態を `範囲外` にし、要約の末尾に「（フェーズ：〇〇）」と書く

ここでは解釈しない。原文に忠実に要約するだけ。

### 3. 曖昧さを洗い出す

[references/ambiguity-checklist.md](references/ambiguity-checklist.md) の全項目を、台帳の全 REQ にあてる。一部の REQ だけで済ませない。

見つけたものは次のどちらかで記録する。

- **確認事項（Q-xx）**：要件を出した人に聞かないと決められないもの。実装に影響するなら `ブロッキング = yes`
- **仮定（A-xx）**：一般的な既定値で進めてよさそうなもの。仮定の内容を明記し、`承認` 欄は空のまま（人が埋める）

次の 6 つに関わる曖昧さは、**仮定にしてはいけない**。必ずブロッキングな確認事項（`ブロッキング = yes`）にする。

1. お金
2. 個人情報
3. 権限
4. データ削除
5. 外部連携
6. 受け入れの数値（性能・件数・期限など、受け入れ条件に直結する数値）

既存仕様と矛盾する要求も確認事項にする。

要件書に未決事項の章や表があるときは、その項目をすべて確認事項にし、質問に要件書側の ID（例：`要件書 Q-03`）を書く。仮定にはしない。ブロッキングかどうかはここまでの決まりで決める。ただし、関係する要件がすべて後のフェーズなら、ブロッキングにしない。

### 4. change に分割する

- 1 change = **一緒にリリースされる単位**。要件書 1 冊を 1 change にしない
- change-id は動詞始まりの kebab-case（例：`add-order-export`、`change-login-lockout`）
- 書き出す前に、分割案（change-id・含める REQ・分けた理由）を人に示し、合意を取る。合意が取れるまで次へ進まない
- 複数の change にかかわる要件（非機能要件など）と確認事項は、かかわる change それぞれの trace.md に、同じ番号・同じ内容の行で載せる。同じ確認事項を載せるときは、質問の末尾に「（<change-id> の Q-01 と同じ質問）」と書く

### 5. change を書き出す

`openspec/changes/<change-id>/` に次を作る。書式は [references/openspec-format.md](references/openspec-format.md) を参照。

| ファイル | 中身 |
|---|---|
| `proposal.md` | なぜ（背景）・何を変えるか・範囲外（Non-goals）・影響範囲 |
| `specs/<capability>/spec.md` | `## ADDED / MODIFIED / REMOVED Requirements` の差分仕様 |
| `design.md` | 技術判断が要るときだけ。選択肢と決定理由 |
| `tasks.md` | 実装チェックリスト。最後に「テスト」「verify」のタスクを必ず入れ、verify のタスクの行末に `<!-- loomake:gate=done -->` を付ける。このタスクは `--done --scope local` のローカルの完了で、最終の合格（`--scope ci` と必須 CI）は書式の注記に従う |
| `trace.md` | 要件台帳・確認事項・仮定（[templates/trace.md](templates/trace.md)） |

各 Requirement には次の 3 つを必ず入れる。1 つでも欠けた Requirement は書かない。

1. `SHALL` または `MUST` を使った規範文
2. 本文の直後に `Source: REQ-012` 行（複数なら `Source: REQ-012, REQ-013`）
3. 1 つ以上の `#### Scenario:`（正常系）。エラー・権限・境界値の要求があれば、それぞれを Scenario にする

非機能要件も「測れる形」の Requirement にする（例：「一覧 API は 1,000 件で 95 パーセンタイル 500ms 以内に応答 SHALL」）。測れる形にできない場合は確認事項にする。

範囲外（種別 = `範囲外`）の要件は Requirement にせず、proposal.md の Non-goals に書く。後のフェーズの要件は、Non-goals の中で、それ以外の範囲外の要件と分けて書く。

### 6. 検証する

```sh
openspec validate <change-id> --strict
pnpm -s verify --change <change-id> --spec-only
```

両方通るまで直す。ただし **ブロッキング確認事項が残っていて verify が落ちるのは正常**。その場合は直さずに報告へ進む。

### 7. 報告する

作業の最後に、次の形で人に報告する。

1. change 一覧（change-id と一行説明）
2. 台帳の集計：REQ 総数 / 反映済 / 確認待ち / 範囲外 / 既存仕様で充足
3. **ブロッキング確認事項**の一覧（要件を出した人にそのまま送れる文面で）
4. 未承認の仮定の一覧（`承認` 欄が空のもの）
5. 次の一手：ブロッキング確認事項が無ければ「実装に進めます」、あれば「回答待ち」

ブロッキング確認事項は要件を出した人にそのまま送れる文面で出す。

- 丁寧語で書き、1 件ごとに番号を振る
- REQ ID や Q 番号だけに頼らず、要件書のどの記述についての質問かを、章と原文の引用で示す
- 決まらないと何が進められないかを 1 文で添える
- 選択肢とおすすめがあれば、おすすめの理由とともに書く
- 社内の用語や OpenSpec の用語（change・Requirement・Scenario など）は使わない

## やってはいけないこと

- 台帳に載せずに Requirement を作る（出典の無い要件は存在しない）
- 原文に無い機能を「あったほうが良い」で足す。提案したいなら確認事項に書く
- 確認事項を仮定に格下げして先へ進む
- `openspec/specs/` を直接書き換える
