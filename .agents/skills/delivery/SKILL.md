# Loomake Delivery

既定の対象は `loomake/loomake` の [マイルストーン1](https://github.com/loomake/loomake/milestone/1)、進行管理は [Issue #121](https://github.com/loomake/loomake/issues/121)。目標日は2026年11月16日。利用者が今回の呼び出しでIssueや段階を指定した場合は、その範囲に絞る。

規約は [AGENTS.md](../../../AGENTS.md)（仕様の正・工程の 3 段階・DoD・禁止事項・報告の形）と [ADR 0006](../../../docs/adr/0006-standing-approval-for-autonomous-delivery.md)（承認の範囲・人の操作 4 項目・同時本数・レビュー規則）に置く。このスキルは管理役の手順だけを書き、規約を再掲しない。

## 呼び出し方

VS CodeのCodex入力欄で `$delivery` と送る。特定のIssueに絞る場合は `$delivery Issue #61` のように指定する。`/delivery` は登録していない。スキルの候補に出なければ、新しいチャットを開くかVS Codeのウィンドウを再読み込みする。停止・再開には `/goal pause`・`/goal resume` を使う。

Codex拡張へのサインインとファイル編集・テストの実行、GitHubの読み書きができる環境で利用する。スキルを作成・インストールしただけではGoalを開始しない。通常の起動文を読むことと、Goalによる自動継続を有効にすることを区別し、登録結果を確認する。

## 開始時

リポジトリを確認し、適用される `AGENTS.md` を読む。別リポジトリの作業を始めない。接続済みGitHubツールで対象Issueの最新状態・依存・受入条件を確認し、必要なら認証済みの `gh` を使う。作業状況をスキル内の固定リストから判断しない。

利用者による `$delivery` の明示的な呼び出しは、以下の範囲のGoalを設定して作業を進める依頼として扱う。説明やスキルの作成・編集だけを求められたときはGoalを開始しない。暗黙のスキル選択だけを根拠にGoalを新規作成しない。

## Goalを確認する

利用可能なGoal操作ツールで、現在のGoalを取得する。

- 同じ対象のGoalが有効なら再作成せず、検証結果と最新Issueを照合して続行する。
- 未完了の別のGoalがある場合は上書きせず、対象を確認して終了する。実装やGitHubへの書き込みは始めない。
- 一時停止中、または上限で停止したGoalは勝手に状態変更しない。利用者側の再開操作が必要なら短いコマンドやUI操作を示して終了する。実装やGitHubへの書き込みは始めない。
- Goalがない、または前のGoalが完了しており、利用者がこのスキルを明示的に呼んだ場合は、指定範囲のGoalを作る。利用者が指定していないトークン予算は追加しない。

既定のGoalには次の内容を含める。Issueを指定された場合は、そのIssueの受入条件を完了条件にする。

> Loomakeの2026-11-16初回配布に向け、マイルストーン1とIssue #121で定めた範囲を実装・検証し、各段階の出口、A23の一周、別リポジトリへの導入、必要な配布の受入を証拠で確認する。AGENTS.mdと本スキルに従い、依存順に作業し、既存担当と重複しない。仕様ゲート・完了ゲート・要件対応テスト・独立レビュー・必須CIを維持する。確認できる承認範囲でPR・マージ・Issue更新を進め、部分実装で親Issueを完了扱いしない。判断待ちは独立した作業を進め、進められる作業がなければ未決事項と再開条件を報告する。個別承認が必要な公開・リリース等は承認前に実行しない。未実施の受入や公開が残る間は初回配布完了と報告しない。

Goal操作ツールが使えない、またはGoal作成が失敗した場合は、自動継続が有効になったと報告しない。対応するCodexの入力欄で、次の短い指示を送る方法を案内して終了する。この分岐では実装やGitHubへの書き込みは始めない。

```text
/goal .agents/skills/delivery/SKILL.mdに従い、初回配布の完了条件を満たす。
```

## 作業を進める

同じ対象のGoalが有効と確認できた場合、または新規作成に成功した場合に限り、同じ実行で次の着手可能な作業へ進む。

### 担当の割り当て

作業・受入条件・依存は既存のWBS Issue、段階の出口と日程の見直しは #121 を正本とする。進捗表や残作業の一覧をスキルやローカル文書へ複製しない。Projectsの設定を待たずに進める。

管理役は1セッションに固定し、依存を確認して実装・独立レビューを分担する。担当の重複や未コミット作業は `git worktree list`・既存PR・Issueの記録と照合する。実装担当ごとにworktreeを分け、同じIssue・changeへ重複着手しない。同時に進める本数と配分は ADR 0006 に従い、ほかのセッションも数に含める。既存の変更があるフォルダでブランチを切り替えない。既存の PR ブランチは worktree で扱い、新しい作業は `git fetch` したあとの origin/main から専用 worktree を作る。ルートの作業ツリーが main と一致するまで、ルートの規約は読まず、自分の worktree の規約を読む。マージされた PR の worktree は当日中に消す。削除は `scripts/clean-merged-worktrees.sh --dry-run` で一覧を確かめてから引数なしで実行する。各 worktree の `.loomake/` は `.loomake/archive/worktree-loomake-<日付>/` に退避される。

実装の受け取りは GitHub Issue で行う。ラベル `post-merge-review` の Issue を最優先で、次にラベル `implementation-queue` の Issue を古い順に拾う。`post-merge-review` は、マージ代行があったと記録された PR の承認元と実際のマージ結果を照合するための事後レビューで、Issue に書かれたマージ commit と reviewed-head の差分を `docs/dev/review-checklist.md` で見て、結果を Issue にコメントする。重大があれば修正 PR を立てて Issue から参照し、なければ「重大 0」と書いて閉じる。`implementation-queue` は設計済みの実装依頼で、Issue に書かれた change-id・設計ファイル・対象 SHA・受け入れ条件に従って実装する。マージ代行の可否は、適用される規約と利用者の明示的な承認に従う。事後レビューでは、代行の承認元と実際のマージ結果を照合し、マージ前に必要な独立 Opus レビューと必須 CI の条件も確認する。

サブエージェントの下書きや一時ファイルは、scratchpad の担当別フォルダ（`scratchpad/<担当>/`。例：`scratchpad/w5/`）に置く。scratchpad 直下の同じ名前のファイルを担当どうしで共用しない。

リポジトリ全体で開いている PR のうち、作成から 24 時間以上たち、まだマージ条件を満たしていないもの（Draft か Ready かを問わない）が 2 本以上あるときは、新しい L3 PR を起こさない。先にそのどれかを受け入れる（マージかクローズ）か、分割する。

担当を変えるときは、前の担当の作業を止めたことを確かめ、引き継ぎ（どこまで済んだか、未 push の作業があるか）を `trace.md` か作業記録に書いてから始める。

### 小さな項目をまとめる

S は [plan90 の出典](https://github.com/loomake/loomake/issues/121#issuecomment-6516886398) で示す小項目の区分で、同じ領域は同じ機能や保守対象を扱う範囲を指す。

同じ領域の S 項目は要件・受入条件・必要な試験・tasks をすべて残して 1 change にまとめる。plan90 の C2 と C5、D4 と D5 はそれぞれまとめる。A6 は共通ヘルパーの集約・`LoomakeConfig` への `run` 追加・設定ファイルの読み取りを 1 回にする作業を含め、項目全体を 1 つの単位として扱う。

change が必要な部分を含む束は、開発の仕組みの部分も同じ change の tasks に含める。specs には製品の約束だけを置き、開発の仕組みは docs/dev と PR・作業記録に残す。change がある作業は、計画の項目 ID と、対応する Requirement・tasks・要件 ID 付きテストの関係を trace と PR に記録する。開発の仕組みだけの変更は ADR 0005 と AGENTS.md に従って change 不要の範囲を判断し、change がない作業の項目・受入条件・検証結果は PR と作業記録に残す。

まとめることを理由に、完成範囲や段階ごとの必須の検査・レビューを省略しない。別の change の担当と同じファイルの実装を重複させない。

### 工程の担当と Opus への依頼

工程の分担（Opus が設計、Codex が実装、別の Opus セッションが独立レビュー）と、独立した見解を先に保存する原則は [agent-workflow.md](../../../docs/dev/agent-workflow.md) に従う。どの段階でどの工程が要るかは AGENTS.md 2 章の表で決める。

Opusへの設計・独立調査・レビューは、管理役が依頼ファイルを用意し、[ask-opus.mjs](scripts/ask-opus.mjs)を自動で実行する。利用者にClaudeの起動やプロンプトの入力を求めない。`ok:true` の成果物と実行情報を確認して引き継ぎ、`ok:false` は未実施として理由を記録する。補助からGitHubへの投稿、push、マージ、Goalの変更は行わない。

設計には [design-request.md](templates/design-request.md) を使い、依頼の内容と上限はテンプレートに従う。レビューには [review-request.md](templates/review-request.md) を使い、依頼文の形と上限は ADR 0006 のレビュー規則に従う。レビュー依頼は 1 PR に 1 依頼とし、工程ごとに分けた並列依頼（G1a/G1b… のような分け方）はしない。分けたくなるなら PR を分ける。

独立 Opus へレビューを依頼する前に、起草した担当（PR の差分を書いた実装担当）とは別のサブエージェントが、Opus に渡すのと同じ依頼文と [review-checklist.md](../../../docs/dev/review-checklist.md) で自己レビューする。重大な指摘をゼロにしてから Opus に依頼する。重大な指摘が消えないときは Opus に依頼せず、修正するか PR を分ける。自己レビューは Opus のレビュー回数に数えない。結果は証跡ブロックの `process:` 行に `self-review=<実施者・重大件数>` の形で書く。

Opusの設計がまだなければ自動で依頼する。Codexから起動できない場合は設計待ちとして #121 に記録し、その実装は進めない。レビュー待ちの間も独立した別作業を進めるが、段階に必要なレビューを未実施のままマージしない。工程の省略や担当の代替は、利用者が明示的に承認した範囲に限り、その承認元を証跡ブロックに記録する。指定した担当が使えないことを、Goalの完了や別モデルでの実施済みに読み替えない。

### 工程を重ねて進める

管理役は、ある項目を Codex が実装している間に、次の独立した項目の Opus 設計を先に依頼する。同時本数と既存担当の範囲を確認し、設計の対象・元コミット・依存を記録する。設計成果物を確認し、その項目に必要な仕様ゲートが成功してから実装へ引き継ぐ。

完了ゲートが必要な作業は、対象 head でローカルの完了（`--done --scope local`）と、gate ジョブの完了ゲート（scope ci）の成功を確認する。独立レビューは必須 CI の完了を待たずに始めてよい。CI が失敗したら原因を修正して再検証し、変更後の head を段階の回数の範囲で再レビューする。差分を変えずに再実行する場合も、原因と再検証の結果を記録する。変更範囲外の原因は Issue に記録し、必須 CI の成功を確認するまで対象 PR を保留する。

### Issueの処理

1. 依存が完了したIssueから、段階の出口につながる作業を選ぶ。担当・branch・change・次の確認点をIssue本文の運用記録に追記し、既存の受入条件や移行時の記録を保持する。依存の一部だけが解けた場合は、先行範囲と受入条件を合意してから切り出す。
2. changeのspecs・trace・tasksを読み、製品の実装前に仕様ゲートを通す。必要なchangeがなければ、Opusへ仕様・設計・出典の整理を依頼し、その成果物を対応するOpenSpecスキルの形式で記録する。Codexが未決の設計を代わりに埋めない。確認事項と仮定の回答は ADR 0006 に従い、決定を trace と PR に記録してから実装する。
3. Opusの設計成果物・対象範囲・未決事項と仕様ゲートの結果を確認してから、Codexがtasksの順に実装してタスクごとにコミットし、1日以内のマージを目安にPRを分割する。Requirementに対応するID付きテストを残す。公開APIやJSONを変えるときは、利用側も同じ変更単位で追従させる。
4. ローカルの完了ゲート（`--done --scope local`）、tasksの完了、Requirementとテストの対応を確認し、段階に応じた独立レビューを依頼する。changeの一部を出すPRでは、その範囲の検証と残作業を明記し、change全体の完了を宣言しない。
5. 対応 Issue を参照して PR を作る。PR 本文の先頭に `loomake-change:` と `loomake-tier:` を書き、末尾に証跡ブロックを置く（下の「マージと証跡」）。マージ条件は ADR 0006 に従う。Issue 全体の受入条件を満たしたときだけ close し、部分 PR は `Refs #番号` とする。
6. 各Issueに成果・検証・未決事項・次の作業を反映する。作業記録はAGENTS.mdの形で、その作業のPRに含める。1件ごとに「続けて」を求めず、CI待ち・回答待ちには担当上限内で独立した作業へ進む。待ちがある場合は「承認待ちでも継続する」に従う。

認証や権限の不足は記録し、利用者の認証設定を勝手に変更しない。承認不足の操作はその操作だけを保留し、通常の実装・検証で同じ承認を求め直さない。人の操作が必要な 4 項目と禁止事項は ADR 0006 と AGENTS.md に従う。

### マージと証跡

証跡の正本は GitHub とする。PR 本文の末尾に `## 証跡` 節を 1 つ置き、次の共通欄を 1 ブロックだけ書く。節は次の `## ` 見出しの直前までとし、管理役はこのブロックと同じ head の CI の状態を見てマージする。L1 は工程行の検査の対象外で、7 つの工程行を書かなくてよい。L2・L3 は以下の文法を使う。

[ADR 0006 の段階受入・最終レビュー](../../../docs/adr/0006-standing-approval-for-autonomous-delivery.md#統合専用ブランチへの段階受入と最終レビュー採用2026-11-01)は 2026-11-01 に利用者が規則案 A を承認し、採用した。承認の出典・対象ブランチ・分割計画は同節に記録する。規則変更 PR #260 が必須 CI・独立レビューを満たして main へマージされるまで、以下の追加欄を例外受入の根拠にしない。通常 PR の証跡は上記の条件と次の共通欄を維持する。

```text
head: <マージ対象の 40 桁 SHA>
tier: <gate の出力行。例 loomake-tier: L2（scripts/ci-gate.mjs）>
route: <normal|hard-bug>（経路を選んだ理由）
survey: 実施済み by=opus session=<36字UUID> model=<実際のモデル識別子>
second-opinion: 対象外
design: 実施済み by=opus session=<36字UUID> model=<実際のモデル識別子>
implement: 実施済み by=codex
review: 実施済み round=1 by=opus session=<36字UUID> model=<実際のモデル識別子> head=<40桁SHA> critical=0 minor=0 info=0
reviewed-head: <Opus が最後にレビューした head の SHA。L1 なら「対象外（L1）」、まだなら「未実施」>
quality: 実施済み verify=<pass|fail|対象外> ci=<必須CIのrun-URL>（verifyが対象外なら理由）
codex-review: <Codex 自動レビューが受領した head の SHA（参考。マージ条件ではない）。なければ「未実施」>
process: self-review=<実施者・重大件数>（ほかの欄にない補足）
```

規則変更 PR #260 の main マージ後、承認された段階 PR だけは同じ証跡ブロックに次を加える。期待する非 PASS の検査 ID・REQ ID・残タスク ID・不足理由は承認済み分割計画の範囲内で実行前に宣言し、実結果との集合・理由の完全一致を記す。計画の範囲・配分の変更や統合先の追加は、ADR 0006 の採用節にある再承認・更新 PR の手順に従い、main 反映前は適用しない。新しい計画が固定されるまで対象の例外は保留する。最新 head の全差分 200KiB 以内・独立レビューを確認し、gate は失敗のまま記録する。承認された統合先以外ではこの扱いを使わず、ほかの CI 失敗や保護規則による拒否は保留する。

```text
integration-target: <明示承認された統合先ブランチ名>
stage-approval: <採用済み ADR・利用者の承認元・日付・対象分割計画>
expected-nonpass: <実行前に宣言した検査 ID・REQ ID・残タスク ID・不足理由>
actual-nonpass: <gate 全出力の証跡と実際の同じ集合・理由。対象 change の ciGateProblem 由来だけか確認。verify の実終了コードの証跡元。gate に出ない場合は ADR の同じ head・scope ci の直接実行の stdout/stderr・JSON・実終了コードと全条件照合>
remaining: <残タスク・要件・実観測・最終受入。親/change は未完了>
```

規則変更 PR #260 の main マージ後、承認された累積最終 PR だけは、共通欄と同じブロックに次を加える。全タスク・全要件・完了ゲート・必須 CI の成功を満たし、各段のレビューを最終レビューの代用にしない。累積差分が 200KiB を超える場合だけ、明示承認されたファイル形式を使い、全原文の保存と全件 Read を確認する。通常 PR は全差分を依頼へ貼る。

```text
final-approval: <採用済み ADR・累積最終レビュー方式の明示承認元・対象計画>
review-coverage: <各段レビュー済み範囲と最終 head の全累積差分との対応>
cumulative-diff: <base/head・全差分の提供形式。承認されたファイル形式なら全パスと順序・範囲の索引>
final-independent-review: <別の新しい Opus による最終 head の全累積差分・全 Requirement・相互作用の確認。ファイル形式なら全件 Read の証跡と読取漏れなし>
```

以上の追加欄は別ブロックにせず、該当する PR の共通欄に続けて一つにまとめる。最新 head の結果が未実施・不明・不一致なら受入を保留する。

#### 工程行の文法

この節を工程行の文法の正本とする。固定の行名を使い、1 工程 1 行で書く。`review:` だけはレビューの回ごとに 1 行ずつ追加し、ほかの行は 1 行ずつにする。

```text
<行名>: <状態> [<key>=<値> ...]（自由記述）
```

値には空白と全角の開き括弧「（」を含めない。自由記述は行末の全角括弧に 1 つだけ書き、必須とした場合以外は省いてよい。改行は LF・CRLF の両方を受け付ける。知らない key、key の重複、空の値、雛形の `<…>` を残した値は使えない。

| 状態語 | 必須の key と書き方 |
|---|---|
| `実施済み` | 工程ごとの表に従う |
| `未実施` | key は付けない。理由は行末の全角括弧に書いてよい |
| `対象外` | key は付けない |
| `再利用` | `source=<UUID か URL>` |
| `省略` | `approval=<規定のパス#見出し か URL>` |
| `代替` | `by=<担当> approval=<URL>` |

| 行名 | 工程・行数 | `実施済み` のときの key |
|---|---|---|
| `route:` | 経路、1 行 | 状態語を使わず `normal` または `hard-bug` と書き、理由の全角括弧を必ず付ける。切り替えたら `from=<元の経路>` を理由の前に書く |
| `survey:` | 先行調査、1 行 | `by=`。`by=opus` なら `session=` と `model=`、それ以外なら `session=` か `record=` |
| `second-opinion:` | 独立調査、1 行 | `by=opus session= model= independent-view=あり\|なし`。normal の経路では `対象外` と書く |
| `design:` | 設計、1 行 | `by=opus session= model=` |
| `implement:` | 実装・修正、1 行 | `by=`。担当の代替は `代替 by=… approval=…` と書く |
| `review:` | 独立レビュー、1 行以上 | `round=<1からの整数> by=opus session= model= head= critical=<件数> minor=<件数> info=<件数>` |
| `quality:` | 品質判定、1 行 | `verify=pass\|fail\|対象外 ci=<run URL>`。`verify=対象外` なら理由の全角括弧を必ず付ける |

表の値の選択肢を区切る `|` は実際の行では選んだ値 1 つに置き換える。`session=` は小文字の 36 字 UUID をそのまま書き、コメントの URL で代えない。`head=` は小文字 40 桁の 16 進数、`by=` は `opus`・`codex`・`claude`・`human` のいずれか、`round=` は 1 以上の整数、件数は 0 以上の整数とする。`model=` は実行結果のモデル識別子、`record=` は先行調査の記録の場所を書く。`ci=` は `https://github.com/<owner>/<repo>/actions/runs/<数字>` の形にする。

レビュー前は `review: 未実施`、CI の結果がそろう前は `quality: 未実施` と書く。この形で工程行の検査に通っても、その工程の完了やマージ条件の達成を意味しない。品質判定が終わったら、同じ head の verify の結果と必須 CI の run URL を `quality:` に写す。change のない L2 では change 指定の完了ゲートが対象外である理由を添えて `verify=対象外` と書くが、通常の lint・typecheck・test と必須 CI は省略しない。Opus のモデル識別子を確認できない工程は `未実施` とし、「不明」で実施済みに読み替えない。

工程ごとの表の `by=opus` は既存の担当分担に従う記入例で、形の検査で許す `by=` の値は各行とも `opus`・`codex`・`claude`・`human` である。担当やモデルが工程表と一致するかは形の検査では判定しない。

通常の経路では先行調査と設計を同じ Opus セッションで行い、難しいバグの経路では独立調査と設計を同じ Opus セッションで行う。各レビューは設計・実装とは別の新しい Opus セッションにする。工程を `省略`・`代替` と記録するのは、既存の規定または利用者の明示承認がその省略・代替を認めている場合に限る。`approval=` の形式が通ることは新しい許可にならない。

`survey:`・`design:` を `省略 approval=AGENTS.md#2-工程の-3-段階` と書けるのも既存の段階規則により設計を要しない L2 の場合に限る。今回の Issue #256 は Opus の設計が指定されており、その省略に当たらない。

`reviewed-head:` は最後の `review:` の `head=` と同じ値を書く。レビュー後の修正については ADR 0006 の head の扱いを維持する。残る共通欄の空欄は「対象外（L1）」か「未実施」とし、工程行の状態語とは分ける。`process:` は `self-review=<実施者・重大件数>` と、ほかの欄にない補足だけにし、工程の状態を混ぜない。

旧形式の `ci:`・`opus-review:`・`opus-model:` は削除する。CI の run URL は `quality:` の `ci=`、Opus のセッション ID と指摘件数は各 `design:`・`review:`、モデルは各 Opus 工程の `model=` にまとめ、同じ情報を二重に記録しない。

L2・L3 の gate は PR 番号があるときだけ `## 証跡` 節の工程行の形を検査し、節や必須行の欠落、重複、不正な状態・値、旧形式の 3 行を失敗にする。担当の違い、セッションの一致・独立性、実行記録との照合はこの検査では判定しない。工程表からの逸脱はダッシュボードと分析コメントで扱い、その記録だけを理由に #121 で利用者を呼ばない。実行記録の照合は毎日の routine の担当とし、#273 の保留中は Opus の工程を「申告のみ」と表示する。

本文の編集だけでは CI が起動しないので、L2・L3 の管理役は最後に本文を更新したあと、マージ前に次を実行して終了コード 0 を確認する。これは最後の本文の形の確認であり、必須 CI や独立レビューの代わりにはしない。

```sh
gh pr view <PR番号> --json body -q .body | node scripts/process-evidence.mjs
```

判定の起点はこの規則のマージ時刻とする。それより前にマージ済みの PR は書き直さない。開いている L2・L3 の PR は新しい検査コードを使う次の CI から対象とし、管理役が本文を新しい形にそろえる。

acceptance.json、CI 成果物のハッシュ照合、検査 merge の tree 照合、handoff 文書ごとの yomiyasu ログは作らない。GitHub の status が同じ head を保証している。

段階ごとのマージ条件と「往復」の数え方は ADR 0006 のレビュー規則に従う。条件を満たした PR は管理役がマージする。差分を変えたら新しい head で証跡ブロックを書き直す。回数を使い切っても重大な指摘が残るときは、ADR 0006 に従って PR を分割するか、Issue に記録して人の判断を仰ぐ。

試験（`tests/`・`packages/*/test/`）・ルートの `scripts/`・`.github/workflows/` を変える L2 の PR には `ci:all-os` ラベルを付け、Windows・macOS の CI も成功してからマージする。必須チェックの試験は ubuntu でしか流れないため、改行コードなどの OS 差はこのラベルがないと確かめられない。

`@codex review` の依頼文には、変更した Requirement の ID と Scenario、見てほしい観点（境界値・エラー経路・OS 差）を書く。

### マージ後に仕様を反映して archive する

管理役は実装 PR のマージ時に、対応する change の全タスク・CI の完了ゲート（scope ci）・要件対応テスト・レビューの完了と、実装が main に入ったことを確認し、[仕様同期](../openspec-sync-specs/SKILL.md)と [archive](../openspec-archive-change/SKILL.md) の手順へ続けて進む。一部だけを受け入れた change は、残りを完了扱いにしない。

両スキルに従って delta と現在の主仕様を比べ、必要な差分を同期する。同期を完了し、主仕様へ全差分が反映されたことを確かめてから、その change を archive する。同じ capability の同期は順に進め、反映済みのほかの要件や Scenario を保持する。`openspec/specs/` の変更はこの change 経由の同期で行い、直接編集の例外は AGENTS.md にある archive 直後の Purpose 修正だけとする。

仕様同期と archive の差分も PR にし、段階に応じた検査とレビューを経て同じ管理役がマージする。archive を後続へ残すときは対応 PR と次の手順を Issue に記録し、その PR の取り込みまで追う。未完のタスクやゲート、レビューを省いて後始末を完了扱いにしない。

### 承認待ちでも継続する

一部の承認待ちを理由にGoal全体をblockedにしない。承認を待つ実装・マージ・公開だけを保留し、次の候補をGitHubの依存・担当・worktreeと照合する。

- 依存が解けた別の対象Issue。
- 未承認の仕様を仮定せず先行できる再現、検証、設計の準備。
- 初回配布に必要な既存の不具合修正や文書の修理。

CI待ちは正常な待機として扱い、実行中の処理の結果を確認しながら独立した作業を進める。対象範囲外の仕事や意味のない検証を作って継続したことにしない。新しい情報や変更がなければ、同じ検査やレビューを繰り返さない。

すべての候補が人の判断や外部状態を待ち、有用な進捗が不可能な場合に限り、待ち項目・照合した候補・再開条件を #121 へ記録する。最初の回答待ちだけでblockedへ変更せず、同じ障害が3回連続のGoalターンで続いたか等、利用可能なGoalツールの条件に従う。ユーザーの停止指示と利用上限は優先する。別セッションやblockedのGoalを勝手に再開せず、常駐監視や無期限のポーリングが有効になったと報告しない。

### Issue #121 への投稿

管理役の投稿は 1 日 1 回の進捗と、人の判断が必要なときの依頼（ADR 0006 の 4 項目と、L3 で重大な指摘が残った PR のマージ可否）だけにする。進捗には受入できた成果、段階の出口までの残作業、依存・CI・判断の待ち、次の確認点を書く。PR ごとの経緯はここに書かず、PR 本文と作業記録から参照する。

### 作業記録と計測、週次集計

作業記録は L2・L3 の PR で、AGENTS.md 5 章の形（1 PR 4 項目、各 1〜2 文）で書く。L1 は PR 本文の 1 行だけにする。run ID・session ID・ハッシュは書かない。

L3 の PR には作業記録に次の計測表を添える。L1・L2 には付けない。

| PR | 設計待ち | 実装 | CI 待ち | レビュー往復回数 | マージまで |
|---|---|---|---|---|---|
| PR のリンク | 時間または状態 | 時間または状態 | 時間または状態 | 回数または状態 | 時間または状態 |

設計待ちは、Opus への設計依頼から、成果物を確認して実装への引き継ぎが可能になるまでの経過時間とする。実装は、最初の着手から、その PR のマージ対象 head の完了ゲート成功までの経過時間とする。CI 待ちは、対象 head に必要な CI の最初の起動から、必要な検査の結果がそろうまでの経過時間とする。マージまでは、PR 作成からマージまでの経過時間とする。レビュー往復回数は、独立 Opus レビューの指摘を受け、修正後の再レビュー結果を受け取るまでを 1 往復とし、初回のレビューは往復に含めない。工程どうしは重なるため、各欄を足して全所要時間にしない。測定できなかった値は「未測定」、続いているものは「進行中」、まだ始めていないものは「未実施」、適用しない欄は理由付きで「対象外」とし、欠測を推定で埋めない。

マージ後に確定した値は次の作業ブランチの作業記録へ対象 PR へのリンクを添えて追記する。

管理役は週 1 回、前回と重複しない日本時間の対象期間と対象 PR の一覧を示して [Issue #121](https://github.com/loomake/loomake/issues/121) に集計を書く。期間は開始を含み終了を含まない形で示し、期間中に作業・CI・レビュー・マージのあった PR を対象とする。計測済み・未測定・進行中・未実施・対象外を区別し、各時間とレビュー往復回数、主な待ちの原因を元の作業記録へリンクして示す。期間をまたぐ区間は期間内の部分だけを集計し、過去の欠測は推定で埋めない。常駐実行や定期投稿を実際に設定していない限り、設定済みとは報告しない。

### 日程と中断時の記録

#121の段階別目標を基準にする。11月2日に最初の実装単位の実績で残工数を再評価し、11月13日を機能追加の締切、14〜16日を導入確認と修正に使う暫定目標とする。遅延の影響と対策は #121 に記録する。

毎日の確認では、受入できた成果、段階の出口までの残作業、依存・CI・判断の待ち時間、次の確認点を見る。Issue完了件数を工数や機能完成度の割合に読み替えない。必要なCIの修理を優先しつつ、追加の高速化は初回配布の実装と比較して優先順位を決める。

初回配布の判定には段階1〜5、A23の一周、別リポジトリへの導入検証を含める。公開サービス等の準備と、人が判断できる時間も確認する。中断時は変更ファイル、commit・未pushの有無、検証結果、未決事項、次の手順を記録し、再開時にGitHubの最新状態と照合する。

Goalの達成はIssueのclose件数や説明だけで判断せず、対象の受入条件と実行結果を確認する。完了前の停止・未実行の検査・承認待ちは明示する。期限や利用上限を超える無期限実行、PC停止後の自動再開は保証しない。ローカル実行は開発マシンと実行プロセスを維持する。離席中の長い作業には、利用できる場合はIDEからクラウドへの委譲を検討する。実行場所と起動したタスクを確認し、未設定の常駐実行を稼働中と報告しない。
