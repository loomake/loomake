# Loomake Delivery

既定の対象は `loomake/loomake` の [マイルストーン1](https://github.com/loomake/loomake/milestone/1)、進行管理は [Issue #121](https://github.com/loomake/loomake/issues/121)。目標日は2026年11月16日。利用者が今回の呼び出しでIssueや段階を指定した場合は、その範囲に絞る。

## 呼び出し方

VS CodeのCodex入力欄で `$delivery` と送る。特定のIssueに絞る場合は `$delivery Issue #61` のように指定する。`/delivery` は登録していない。スキルの候補に出なければ、新しいチャットを開くかVS Codeのウィンドウを再読み込みする。停止・再開には `/goal pause`・`/goal resume` を使う。

Codex拡張へのサインインとファイル編集・テストの実行、GitHubの読み書きができる環境で利用する。スキルを作成・インストールしただけではGoalを開始しない。通常の起動文を読むことと、Goalによる自動継続を有効にすることを区別し、登録結果を確認する。

## 開始時

リポジトリを確認し、適用される `AGENTS.md` と[エージェントの分担と共通原則](../../../docs/dev/agent-workflow.md)を読む。別リポジトリの作業を始めない。接続済みGitHubツールで対象Issueの最新状態・依存・受入条件を確認し、必要なら認証済みの `gh` を使う。作業状況をスキル内の固定リストから判断しない。

利用者による `$delivery` の明示的な呼び出しは、以下の範囲のGoalを設定して作業を進める依頼として扱う。説明やスキルの作成・編集だけを求められたときはGoalを開始しない。暗黙のスキル選択だけを根拠にGoalを新規作成しない。

## Goalを確認する

利用可能なGoal操作ツールで、現在のGoalを取得する。

- 同じ対象のGoalが有効なら再作成せず、検証結果と最新Issueを照合して続行する。
- 未完了の別のGoalがある場合は上書きせず、対象を確認して終了する。実装やGitHubへの書き込みは始めない。
- 一時停止中、または上限で停止したGoalは勝手に状態変更しない。利用者側の再開操作が必要なら短いコマンドやUI操作を示して終了する。実装やGitHubへの書き込みは始めない。
- Goalがない、または前のGoalが完了しており、利用者がこのスキルを明示的に呼んだ場合は、指定範囲のGoalを作る。利用者が指定していないトークン予算は追加しない。

既定のGoalには次の内容を含める。Issueを指定された場合は、そのIssueの受入条件を完了条件にする。

> Loomakeの2026-11-16初回配布に向け、マイルストーン1とIssue #121で定めた範囲を実装・検証し、各段階の出口、A23の一周、別リポジトリへの導入、必要な配布の受入を証拠で確認する。AGENTS.mdと本スキルに従い、依存順に作業し、既存担当と重複しない。仕様ゲート・完了ゲート・要件対応テスト・独立レビュー・必須CIを維持する。確認できる承認範囲でPR・マージ・Issue更新を進め、部分実装で親Issueを完了扱いしない。判断待ちは独立した作業を進め、進められる作業がなければ未決事項と再開条件を報告する。個別承認が必要な公開・リリース等は承認前に実行しない。未実施の受入や公開が残る間は初回配布完了と報告しない。

Goal操作ツールが使えない、またはGoal作成が失敗した場合は、自動継続が有効になったと報告しない。対応するCodexの入力欄で、次の短い指示を送る方法を案内して終了する。この分岐では実装やGitHubへの書き込みは始めない。

```text
/goal .agents/skills/delivery/SKILL.mdに従い、初回配布の完了条件を満たす。
```

## 作業を進める

同じ対象のGoalが有効と確認できた場合、または新規作成に成功した場合に限り、同じ実行で次の着手可能な作業へ進む。

### 管理と並行作業

作業・受入条件・依存は既存のWBS Issue、段階の出口と日程の見直しは #121 を正本とする。進捗表や残作業の一覧をスキルやローカル文書へ複製しない。Projectsの設定を待たずに進める。

管理役は1セッションに固定し、依存を確認して実装・独立レビューを分担する。担当の重複や未コミット作業は `git worktree list`・既存PR・Issueの記録と照合する。実装担当ごとにworktreeを分け、同じIssue・changeへ重複着手しない。同時4changeの上限（配布3枠・品質計画1枠。既存の引き継ぎ対象は終了した枠からこの配分へ移す）にはほかのセッションも含める。既存の変更があるフォルダでブランチを切り替えず、最新mainから専用worktreeを用意する。

### 小さな項目をまとめる

S は [plan90 の出典](https://github.com/loomake/loomake/issues/121#issuecomment-6516886398) で示す小項目の区分で、同じ領域は同じ機能や保守対象を扱う範囲を指す。

同じ領域の S 項目は要件・受入条件・必要な試験・tasks をすべて残して 1 change にまとめる。plan90 の C2 と C5、D4 と D5 はそれぞれまとめる。A6 は共通ヘルパーの集約・`LoomakeConfig` への `run` 追加・設定ファイルの読み取りを 1 回にする作業を含め、項目全体を 1 つの単位として扱う。

change が必要な部分を含む束は、開発の仕組みの部分も同じ change の tasks に含める。specs には製品の約束だけを置き、開発の仕組みは docs/dev と PR・作業記録に残す。change がある作業は、計画の項目 ID と、対応する Requirement・tasks・要件 ID 付きテストの関係を trace と PR に記録する。開発の仕組みだけの変更は ADR 0005 と AGENTS.md に従って change 不要の範囲を判断し、change がない作業の項目・受入条件・検証結果は PR と作業記録に残す。

まとめることを理由に、完成範囲や必要な仕様ゲート・完了ゲート・要件対応テスト・独立レビュー・必須 CI を省略しない。同時 4 change の上限と配布 3 枠・品質計画 1 枠、既存の担当とマージ条件を維持し、別の change の担当と同じファイルの実装を重複させない。

### 工程の担当

管理役のCodexがOpusの設計成果物を確認し、実装担当のCodexへ引き継ぐ。完了ゲートの後は、新しいOpusセッションへ最終レビューを依頼する。担当と引き継ぎの正本は[エージェントの分担と共通原則](../../../docs/dev/agent-workflow.md)とし、Claude Codeの呼び出し例、モデル確認、独立性と最終レビューの反復条件は同文書に従う。

Opusへの設計・独立調査・最終レビューは、管理役が依頼ファイルを用意し、[ask-opus.mjs](scripts/ask-opus.mjs)を自動で実行する。利用者にClaudeの起動やプロンプトの入力を求めない。呼び出し方と結果の扱いは[正本の実行手順](../../../docs/dev/agent-workflow.md#codexからopusへ依頼する)に従う。`ok:true` の成果物と実行情報を確認して引き継ぎ、`ok:false` は未実施として理由を記録する。補助からGitHubへの投稿、push、マージ、Goalの変更は行わない。

設計には [design-request.md](templates/design-request.md)、最終レビューには [review-request.md](templates/review-request.md) を使う。管理役がプレースホルダーを実値へ置き換え、対象コミットの行番号付き抜粋、関連 Requirement の全文、受入条件を埋める。レビュー時は base と head の全差分と検証証跡も渡す。必要な資料を専用 worktree 内にそろえ、記入済みの依頼を `.loomake/` 内へ保存してから、正本の手順に従って `ask-opus.mjs` の `--request` に渡す。テンプレートの展開と記入は管理役が行う。

Opus 最終レビューに回数上限を設けない。新しい head の指摘がゼロになるまで、修正・検証と新規セッションでの独立レビューを繰り返す。従来の Opus 評価合計による回数制限は撤廃し、設計・独立調査・設計レビュー・最終レビューの実施履歴は保持する。同じ指摘が 3 回連続で再出現したら Issue に記録し、往復を続ける。GitHub の自動 Codex レビューは別枠で、起動条件・回数・head・結果を記録する。費用の上限は設けない。

Opusの設計がまだなければ自動で依頼する。Codexから起動できない場合は設計待ちとして #121 に記録し、その実装は進めない。レビュー待ちの間も独立した別作業を進めるが、Opusの最終レビューを未実施のままマージしない。正本に従う工程省略・担当代替は、利用者が明示的に承認した範囲に限り、その承認元を記録する。指定した担当が使えないことを、Goalの完了や別モデルでの実施済みに読み替えない。

### 工程を重ねて進める

管理役は、ある項目を Codex が実装している間に、次の独立した項目の Opus 設計を先に依頼する。同時 4 change と既存担当の範囲を確認し、設計の対象・元コミット・依存を記録する。設計成果物を確認し、その項目に必要な仕様ゲートが成功してから実装へ引き継ぐ。

完了ゲートが必要な作業は、対象 head での成功を確認する。最終レビューは必須 CI の完了を待たずに、設計・実装とは別の新しい Opus セッションで始める。CI が失敗したら原因を修正して再検証し、変更後の新しい head を新しいセッションで再レビューする。マージ時には同じ対象 head の必須 CI・自動 Codex レビュー・指摘ゼロの Opus 最終レビューをそろえる。

差分を変えずに再実行する場合も、原因と再検証の結果を記録する。変更範囲外の原因は Issue に記録し、必須 CI の成功を確認するまで対象 PR を保留する。

### Issueの処理

1. 依存が完了したIssueから、段階の出口につながる作業を選ぶ。担当・branch・change・次の確認点をIssue本文の運用記録に追記し、既存の受入条件や移行時の記録を保持する。依存の一部だけが解けた場合は、先行範囲と受入条件を合意してから切り出す。
2. changeのspecs・trace・tasksを読み、製品の実装前に `pnpm -s verify --change <change-id> --spec-only` を通す。必要なchangeがなければ、Opusへ仕様・設計・出典の整理を依頼し、その成果物を対応するOpenSpecスキルの形式で記録する。Codexが未決の設計を代わりに埋めない。確認事項は ADR 0006 に基づきおすすめ案で回答し、仮定は管理役が理由を添えて承認する。決定を trace と PR に記録して仕様ゲートを再実行し、成功後に実装する。開発の仕組みだけの変更は、AGENTS.mdで認められた範囲ではchangeを作らずに進める。
3. Opusの設計成果物・対象範囲・未決事項と仕様ゲートの結果を確認してから、Codexがtasksの順に実装してタスクごとにコミットし、1日以内のマージを目安にPRを分割する。Requirementに対応するID付きテストを残す。公開APIやJSONを変えるときは、利用側も同じ変更単位で追従させる。
4. `pnpm -s verify --change <change-id> --done`、tasksの完了、Requirementとテストの対応を確認し、AGENTS.mdの反復条件に従い、設計・実装とは別の新しいOpusセッションによる最終レビューを行う。changeの一部を出すPRでは、その範囲の検証と残作業を明記し、change全体の完了を宣言しない。
5. 対応 Issue を参照して PR を作る。マージ対象 head の必須 CI と自動 Codex レビューが揃い、同 head の独立した Opus 最終レビューで指摘ゼロとなり、重大な未解決指摘もなければ管理役がマージする。差分を変えた場合は新しい head を再検証・再レビューする。同じ指摘が 3 回連続で再出現したら Issue に記録し、往復は続ける。Issue 化しただけで指摘ゼロとは扱わない。Issue 全体の受入条件を満たしたときだけ close し、部分 PR は `Refs #番号` とする。完了 change の仕様反映と archive は対応スキルに従う。
6. 各Issueに成果・検証・未決事項・次の作業を反映する。作業記録はAGENTS.mdに従い、その作業のPRに含める。日程への影響と判断事項は #121 にまとめる。1件ごとに「続けて」を求めず、CI待ち・回答待ちには担当上限内で独立した作業へ進む。待ちがある場合は次の節に従う。

認証や権限の不足は記録し、利用者の認証設定を勝手に変更しない。承認不足の操作はその操作だけを保留し、通常の実装・検証で同じ承認を求め直さない。完成範囲の縮小とテストや品質設定の緩和は承認経路のない禁止とする。必要性が生じたら Issue に記録し、その変更は行わず独立した次の作業へ進む。開発の仕組みの変更は管理役が行い、npm公開・public化・リリース・規則の変更は [ADR 0006](../../../docs/adr/0006-standing-approval-for-autonomous-delivery.md) に従う。

### 承認待ちでも継続する

一部の承認待ちを理由にGoal全体をblockedにしない。承認を待つ実装・マージ・公開だけを保留し、次の候補をGitHubの依存・担当・worktreeと照合する。

- 依存が解けた別の対象Issue。
- 未承認の仕様を仮定せず先行できる再現、検証、設計の準備。
- 初回配布に必要な既存の不具合修正や文書の修理。

CI待ちは正常な待機として扱い、実行中の処理の結果を確認しながら独立した作業を進める。対象範囲外の仕事や意味のない検証を作って継続したことにしない。新しい情報や変更がなければ、同じ検査やレビューを繰り返さない。

すべての候補が人の判断や外部状態を待ち、有用な進捗が不可能な場合に限り、待ち項目・照合した候補・再開条件を #121 へ記録する。最初の回答待ちだけでblockedへ変更せず、同じ障害が3回連続のGoalターンで続いたか等、利用可能なGoalツールの条件に従う。ユーザーの停止指示と利用上限は優先する。別セッションやblockedのGoalを勝手に再開せず、常駐監視や無期限のポーリングが有効になったと報告しない。

### 確認事項とレビュー承認

確認事項・仮定は対応 PR の本文に項目 ID、問いと選択肢、おすすめと理由、影響、状態をまとめ、trace の同じ ID と結び付ける。[ADR 0006](../../../docs/adr/0006-standing-approval-for-autonomous-delivery.md) は利用者の包括承認であり、確認事項はおすすめ案で回答する。回答者は「利用者（ADR 0006 の包括承認）」とし、選択肢を残す。仮定は管理役が理由を添えて承認する。決定・承認者・日本時間の日付・ADR の参照を記録し、仮定の承認を利用者本人のレビューとして投稿しない。

必須 CI・自動 Codex レビュー・独立した Opus 最終レビューがマージ対象 head に揃い、Opus 最終レビューの指摘がゼロで自動 Codex の重大な未解決指摘もない PR は管理役がマージする。ゲート・要件対応テスト・tasks の完了を維持する。開発の仕組みの変更は管理役が行う。品質を弱めることと完成範囲の縮小は承認経路を設けず禁止する。

人の操作が残るのは npm 公開・リポジトリの public 化・リリース・規則の変更の 4 つだけとする。必要なときは対象、PR と項目 ID、検証結果、必要な操作と影響を #121 にコメントし、`@rrr-xxx` を呼ぶ。ADR 0006（2026-10-30）で指定された規約更新は承認済み。ChatGPT アプリへの通知設定を確認し、設定できなければ理由と代替を報告する。人の返答を待つ操作だけを保留し、独立した次の作業へ進む。返答がないことを新しい承認とは扱わない。

### 日程と中断時の記録

#121の段階別目標を基準にする。11月2日に最初の実装単位の実績で残工数を再評価し、11月13日を機能追加の締切、14〜16日を導入確認と修正に使う暫定目標とする。遅延の影響と対策は #121 に記録する。

毎日の確認では、受入できた成果、段階の出口までの残作業、依存・CI・判断の待ち時間、次の確認点を見る。Issue完了件数を工数や機能完成度の割合に読み替えない。必要なCIの修理を優先しつつ、追加の高速化は初回配布の実装と比較して優先順位を決める。

初回配布の判定には段階1〜5、A23の一周、別リポジトリへの導入検証を含める。公開サービス等の準備と、人が判断できる時間も確認する。中断時は変更ファイル、commit・未pushの有無、検証結果、未決事項、次の手順を記録し、再開時にGitHubの最新状態と照合する。

Goalの達成はIssueのclose件数や説明だけで判断せず、対象の受入条件と実行結果を確認する。完了前の停止・未実行の検査・承認待ちは明示する。期限や利用上限を超える無期限実行、PC停止後の自動再開は保証しない。ローカル実行は開発マシンと実行プロセスを維持する。離席中の長い作業には、利用できる場合はIDEからクラウドへの委譲を検討する。実行場所と起動したタスクを確認し、未設定の常駐実行を稼働中と報告しない。
