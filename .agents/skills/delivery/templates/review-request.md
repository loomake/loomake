# Opus へのレビュー依頼

管理役が実値に置き換えるのは、記入欄の `{{...}}` だけとする。貼った差分に含まれる `{{`・`}}` は変えない。該当しない欄には理由を書く。

依頼文の形は ADR 0006 のレビュー規則に従い、「変更差分 ＋ 変更した Requirement の ID 一覧 ＋ レビュアーが読むべきファイルの一覧（パス）」とする。記入欄を埋め終えてから、`git diff <base> <head>` で全差分を取得し、差分は変えずに依頼へ貼る。Requirement の全文や呼び出し側の抜粋は貼らず、レビュアーが Read・Glob・Grep で読むファイルのパスを載せる。記入済みの依頼を専用 worktree の `.loomake/` 内へ保存し、差分を貼った依頼全体にプレースホルダーの置き換えを再び行わない。

これ以外の資料は加えない。外部の資料が要るときは worktree 内へ置き、そのパスを読むべきファイルの一覧に加える。

管理役が記入を確認してから、既存の `ask-opus.mjs` に `--role review`、`--request`、`--head` で渡す。テンプレートの展開と記入は管理役が行う。

200KiB の上限は差分にだけ掛け、差分が 200KiB を超えるときは PR を分ける。ただし ask-opus.mjs が直るまでは、依頼全体が 200KiB 以内である必要がある（Issue #207）。1 PR に 1 依頼とし、工程ごとに分けた並列依頼はしない。

## 変更した Requirement の ID 一覧

管理役は変更した各 Requirement の要件 ID と、それを定める spec.md の worktree 内のパスを載せる。差分仕様を使う場合は ADDED/MODIFIED/REMOVED の区分も示す。開発の仕組みなどで Requirement がない場合は、その根拠と、適用する文書のパスを載せる。

```text
{{要件 ID・差分の区分・spec.md のパス}}
```

## レビュアーが読むべきファイルの一覧

管理役は、変更した Requirement の spec.md、変更した関数やモジュールを直接呼び出す側、受入条件の確認に要る試験や文書を、worktree 内の相対パスで並べる。本文は貼らない。

```text
{{相対パスと、読む理由}}
```

## レビューへの依頼

上記 head の差分を受入条件と照合し、要件との一致、過剰設計、無関係な変更、境界条件、テストや品質設定の弱体化を確認する。実装担当の完了宣言や、古い head の検証・レビューを、対象 head の合格根拠にしない。

指摘ごとに重大度、対象ファイルと行、問題が起きる条件、根拠、修正すべき内容を回答する。対象 head と、重大・軽微・情報それぞれの指摘件数を明記する。材料不足や未実施の確認がある場合は、その内容と判定の限界も書く。

レビューの回数とマージ条件は ADR 0006 に従う。L2 では 1 回（指摘があれば修正後に 1 回だけ再レビュー）、L3 では最大 2 往復とし、マージ条件は重大な指摘がゼロであること。軽微な指摘は Issue に記録すればマージできるので、重大と軽微の区別を明確にする。
